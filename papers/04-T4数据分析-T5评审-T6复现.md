# T4 科研数据分析、计算建模与仿真

## D1. MLE-bench: Evaluating Machine Learning Agents on Machine Learning Engineering

- **元信息**：Jun Shern Chan、Neil Chowdhury、Oliver Jaffe、James Aung、Dane Sherburn、Evan Mays 等（OpenAI）｜出处 **ICLR 2025**；arXiv:2410.07095（2024-10）｜年份 2024/2025｜代码：openai/mle-bench｜**核验状态：已核验**（arXiv API + comment "ICLR version"）[原文]
- **研究动机**：ML 工程是 AI 研究中最可自动化的部分，但缺少贴近真实工程的评测：Kaggle 竞赛含数据准备、训练、调参、提交全流程。[原文]
- **研究挑战**：① 任务要可执行、可复现、防泄漏；② 评分需要与人类奖牌线可比；③ agent 的算力/时间预算需受控。[推测]
- **技术贡献**：**75 个 Kaggle 竞赛**，按人类奖牌线评级；提供容器化环境与评分；评测多种 agent scaffold + 模型；最佳组合（o1-preview + AIDE）在 **16.9%** 的竞赛中达到铜牌水平。[原文]
- **讨论**：有效建立了"ML 工程能力"标尺；但 Kaggle 任务偏表格/传统 ML，不能代表前沿研究；agent 拿奖牌 ≠ 会做研究。不足：数据泄漏与公开方案污染（Kaggle 社区有大量公开 notebook），评分对算力敏感。[推测]
- **树定位**：milestone task = **ML 工程 agent 评测**；novelty = **1 类**。
- **challenge→insight**：C: 研究能力不可直接测。→ I: 用有奖牌线的真实竞赛做代理任务。

## D2. DS-Agent: Automated Data Science by Empowering Large Language Models with Case-Based Reasoning

- **元信息**：S. Guo、C. Deng、Y. Wen、H. Chen、Y. Chang、J. Wang（吉林大学 / 上海交大 / UCL）｜出处 **ICML 2024**；arXiv:2402.17453（2024-02）｜年份 2024｜**核验状态：已核验**（ICML 2024 引用 + 摘要）[原文]。⚠️ 组内写 NeurIPS 2024，**出处应为 ICML 2024**。
- **研究动机**：LLM agent 在自动化数据科学中成功率低、易幻觉；微调成本高且难获得反馈信号。[原文]
- **研究挑战**：① 复杂 ML 任务需要多步决策；② 失败后缺少可复用的经验；③ 无法为每个任务微调。[原文]
- **技术贡献**：把**案例推理（CBR）**引入 agent：检索历史相似任务的解决方案（案例库）→ 复用/改写 → 执行后把成功/失败经验写回案例库；开发阶段报告 **100% 成功率**（在其设定下），部署阶段用 GPT-3.5 降低成本。[原文/组内]
- **讨论**：CBR 是"经验记忆"的早期实现，思路正确；但案例检索依赖任务相似度，跨域迁移弱；"100% 成功"是开发集自报，需看任务难度。不足：案例库需要人工/半自动积累；没有真正的自我反思机制。[推测]
- **树定位**：milestone task = **案例驱动的数据科学 agent**；pipeline = **CBR 检索—复用—写回**；novelty = **2 类（pipeline）+ 3 类（案例记忆模块）**。
- **challenge→insight**：C: 每个任务都微调不现实。→ I: 用可检索、可增长的案例库替代参数更新。

## D3. AutoSDT: Scaling Data-Driven Discovery Tasks Toward Open Co-Scientists（AutoSDT-5K）

- **元信息**：Yifei Li、Hanane Nour Moussa、Ziru Chen、Shijie Chen、Botao Yu 等（Ohio State University SunLab）｜出处 **EMNLP 2025**（pp. 30384–30406）；arXiv:2506.08140（2025-06）｜年份 2025｜数据：AutoSDT-5K｜**核验状态：已核验**（ACL Anthology 作者页 + arXiv 摘要）[原文]
- **研究动机**：训练/评测 AI co-scientist 缺少高质量数据；真实数据驱动发现工作流的编码任务稀缺。[原文]
- **研究挑战**：① 真实工作流中的任务难以自动收集；② 任务说明与代码解需准确；③ 生态有效性（真实使用的包/数据）难保证。[原文]
- **技术贡献**：自动管线：LLM 搜索多样来源 → 选择生态有效任务 → 合成准确的任务说明与代码解；构建 **5,404 个任务**、覆盖 **4 个学科**、**756 个 Python 包**；256 个任务的人工专家反馈。[原文]
- **讨论**：这是"数据基础设施"型贡献，能直接用于训练 co-scientist；但任务是从公开代码/教程反向合成，难度与真实科研仍有差距；评测的是代码能力而非发现能力。[推测]
- **树定位**：milestone task = **数据驱动发现的任务数据集**；novelty = **1 类（新数据集/task 族）**。
- **challenge→insight**：C: 缺 co-scientist 训练数据。→ I: 用 LLM 从真实科研代码生态反向合成可执行任务。

## D4. SciCode: A Research Coding Benchmark Curated by Scientists

- **元信息**：Minyang Tian、Luyu Gao、Shizhuo Dylan Zhang、Xinan Chen、Cunwei Fan、Xuefei Guo 等｜出处 **NeurIPS 2024**；arXiv:2407.13168（2024-07）｜年份 2024｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：通用代码 benchmark 不能反映科研级编程：需要领域知识、数值方法、与论文一致的科学假设。[原文]
- **技术贡献**：科学家标注的 **80 个主问题 / 338 个子问题**，覆盖物理、数学、材料、生物、化学等 16 个子领域；用黄金解与单元测试评分；最佳模型仅解决 **4.6%** 的复杂问题。[原文]
- **讨论**：把"科研编程"与"LeetCode 编程"区分开，是重要标尺；但研究者自选问题、题目规模有限；"会写函数"仍不等于"会设计研究代码"。[推测]
- **树定位**：milestone task = **科研级代码生成评测**；novelty = **1 类**。
- **challenge→insight**：C: 通用编程分数虚高。→ I: 让科学家出题并给出黄金解，测真实科研代码能力。

## D5. DiscoveryBench: Towards Data-Driven Discovery with Large Language Models

- **元信息**：Bodhisattwa Prasad Majumder、Harshit Surana、Dhruv Agarwal、Bhavana Dalvi Mishra、Abhijeetsingh Meena、Aryan Prakhar 等（AI2）｜出处 **ICLR 2025**；arXiv:2407.01725（2024-07）｜年份 2024/2025｜代码：allenai/discoverybench｜**核验状态：已核验**（arXiv API + 项目页）[原文]
- **研究动机**：数据驱动发现是多步过程（假设→数据分析→结论），但缺少形式化评测；现有 QA benchmark 不要求从数据中"发现"。[原文]
- **技术贡献**：首个数据驱动发现 benchmark：**264 个任务**，源自真实论文工作流，覆盖多领域；要求 agent 在结构化数据上验证假设；最佳系统仅约 **25%** 得分。[原文]
- **讨论**：把"发现"操作化为"给定数据与领域背景，回答研究问题"；但任务仍偏"事后复现结论"，不要求提出新假设；评分依赖答案匹配。[推测]
- **树定位**：milestone task = **数据驱动发现评测**；novelty = **1 类**。
- **challenge→insight**：C: "发现"无法直接评分。→ I: 从真实论文抽取"数据+问题+结论"三元组，要求 agent 重建结论。

## D6. DS-STAR: Data Science Agent via Iterative Planning and Verification（部分核验）

- **元信息**：Google 团队（作者待补）｜出处 arXiv:2509.21825（2025-09）｜年份 2025｜**核验状态：部分核验**（arXiv HTML v3 存在；完整作者/venue 未核对）[原文]
- **技术贡献（据摘要/引用）**：确定性的 **7 模块**数据科学 agent（读数据、规划、写代码、执行、验证、修复、报告），强调迭代规划与验证；在 DABStep / KramaBench / DA-Code 上报告 **12% → 45%** 的提升。[组内+原文]
- **讨论**：[推测] 工程化、可复现是优点；但"确定性 7 模块"意味着灵活性低，遇到开放研究问题会退化；提升主要来自工程 scaffold 而非科学推理。
- **树定位**：pipeline = **确定性多模块数据科学流水线**；novelty = **2 类（pipeline）**。
- **challenge→insight**：C: agent 端到端不稳定。→ I: 把流程拆成固定模块 + 逐步验证。

## D7. Curie: Toward Rigorous and Automated Scientific Experimentation（部分核验）

- **元信息**：组内标 arXiv 2025-02、46 任务；本轮检索未定位到 arXiv 页面。**核验状态：未找到（仅见二手列表提及）**[未找到]。⚠️ 组内把它列为"最值得注意的思路"，但汇报前必须补原文。

## D8. DataSciBench: An LLM Agent Benchmark for Data Science

- **元信息**：Dan Zhang、Shijian Zhou、Minghao Cai、Feng Li、Linyi Yang、Wei Wang、Yue Yu 等（arXiv:2502.13897，2025-02）｜出处 arXiv 2025（组内标 ACL 2026，未核实）｜**核验状态：部分核验**（arXiv 编号与框架经二手引用确认；venue 未核）[原文]
- **技术贡献**：三组件：6 类任务 + prompt 收集/专家筛选；**Task-Function-Code（TFC）** 评估体系（25 个聚合函数 + 519 个带标签测试用例）；评测 23 个 LLM；强调不只看代码能否跑，还看是否实现预定数据分析功能。[原文]
- **讨论**：[推测] TFC 把"功能正确性"引入评测，比只看执行成功更严格；但测试用例由作者构建，覆盖有限；任务仍偏分析而非发现。
- **树定位**：milestone task = **数据科学 agent 评测**；novelty = **1 类（benchmark）+ 3 类（TFC 评估模块）**。
- **challenge→insight**：C: 代码跑通 ≠ 分析正确。→ I: 用功能级测试用例验证分析语义。

## D9. Asta DataVoyager（Ai2）

- **元信息**：Ai2 Asta 团队成员（AstaBench 论文 arXiv:2510.21652 中描述；产品 2025-10）｜出处 2025（产品 + AstaBench 论文）｜**核验状态：已核验**（Ai2 AstaBench 博客 + 论文 PDF）[原文]
- **技术贡献**：角色式多 agent 数据分析系统：规划 agent、编程/执行 agent、分析 agent；能语义理解数据集、程序化探索可验证假设、跑相关/回归、生成代码并解释结果；用多模态模型把图转成自然语言摘要供其他 agent 使用；基于 AutoGen。[原文]
- **讨论**：是"分析型 co-scientist"的产品化形态；AstaBench 显示数据分析是最难类别（无 agent 超过 34%），说明这类系统仍有明显上限。[原文]
- **树定位**：pipeline = **角色式多 agent 数据分析**；novelty = **2 类（pipeline）**；其评测属 **1 类（AstaBench）**。
- **challenge→insight**：C: 真实数据集的开放式分析难。→ I: 角色分工 + 可执行代码 + 图表语义摘要，让多个 agent 共享分析状态。

# T5 同行评审、学术反馈与成果改进

## E1. AgentReview: Exploring Peer Review Dynamics with LLM Agents

- **元信息**：Yiqiao Jin、Qinlin Zhao、Yiyang Wang、Hao Chen、Kaijie Zhu、Yijia Xiao 等｜出处 **EMNLP 2024 Main（Oral）**；arXiv:2406.12708（2024-06）｜年份 2024｜**核验状态：已核验**（arXiv API comment）[原文]
- **研究动机**：同行评审中的偏差与决策动力学难以在真实系统中解耦实验；需要可控的"评审模拟器"。[原文]
- **技术贡献**：reviewer / author / AC 三角色 LLM agent 仿真框架，可在论文、评审、 rebuttal、决策各环节注入变量；用真实会议数据校准；发现审稿人偏差可导致约 **37.1%** 的决策变化。[原文]
- **讨论**：它是**模拟器**而非评审器——价值在于研究评审机制（偏差、评分聚合），不是替代审稿人。不足：模拟的保真度无法验证；LLM 审稿人行为与真人差异大。[推测]
- **树定位**：milestone task = **评审过程仿真**；novelty = **1 类**。
- **challenge→insight**：C: 评审偏差无法在真实会议做对照实验。→ I: 用多角色 agent 做可干预的仿真。

## E2. DeepReview: Improving LLM-based Paper Review with Human-like Deep Thinking Process

- **元信息**：Minjun Zhu、Yixuan Weng、Linyi Yang、Yue Zhang（西湖大学）｜出处 **ACL 2025**；arXiv:2503.08569（2025-03）｜年份 2025｜代码：zhu-minjun/Researcher｜**核验状态：已核验**（Semantic Scholar 记 ACL 2025 + 论文主页信息）[原文]
- **研究动机**：LLM 评审存在领域知识有限、幻觉推理、缺少结构化评估；且缺少记录专家推理链的数据集。[原文]
- **技术贡献**：三阶段评审流程：**novelty 验证（检索对比文献+引用核查）→ 多专家多维评估 → 可靠性验证（逻辑一致性/反幻觉）**；构建 **DeepReview-13K** 结构化评审推理数据集；训练 **DeepReviewer-14B**，支持 fast/standard/best 三种推理模式；报告对 o1 胜率 88.21%、对 DeepSeek-R1 80.20%（作者自评）。[原文]
- **讨论**：把"评审"拆成可训练的多阶段推理是有效工程；但胜率是人类偏好还是自动评判需核实；14B 模型的知识截止与领域覆盖有限；"反幻觉"模块本身也可能幻觉。[推测]
- **树定位**：milestone task = **结构化 LLM 评审**；pipeline = **三阶段评审 + 合成推理数据 SFT**；novelty = **2 类（pipeline）+ 1 类（DeepReview-13K 数据集）**。
- **challenge→insight**：C: 评审反馈空泛、无证据。→ I: 强制先检索文献再评 novelty，并用结构化推理链训练评审模型。

## E3. ScholarPeer: A Context-Aware Multi-Agent Framework for Automated Peer Review

- **元信息**：Palash Goyal、Mihir Parmar、Yiwen Song、Hamid Palangi、Tomas Pfister、Jinsung Yoon、Nanyun Peng 等（Google）｜出处 arXiv:2601.22638（2026-01）｜年份 2026｜**核验状态：已核验**（arXiv HTML + Google Research 页面 + 多家报道）[原文]
- **研究动机**：投稿量激增，审稿人负担重；现有 LLM 评审把评审当文本生成，缺少领域背景与主动核验。[原文]
- **技术贡献**：双流程：**context acquisition**（子领域历史 agent 构建领域叙事 + 实时文献检索）+ **active verification**（baseline 侦察 agent 找遗漏的数据集/对比方法；多维问答引擎核验技术主张）；输出 summary / strengths / weaknesses / questions；定位为"co-scientist"：投稿前辅导作者 + 投稿后辅助核验。[原文]
- **讨论**：把"查文献、查 baseline"变成评审的显式步骤，是对 DeepReview 路线的补强；但"遗漏 baseline"的判定依赖检索覆盖；评估仍以与人类评审的一致性/胜率为主。[推测]
- **树定位**：pipeline = **检索增强的多 agent 评审**；novelty = **3 类（新模块组合）/ 4 类（在评审 pipeline 上加模块）**。
- **challenge→insight**：C: LLM 评审缺乏领域上下文、漏掉关键对比。→ I: 先构建领域叙事与 baseline 清单，再逐条核验主张。

# T6 科学验证、证伪与复现

## F1. PaperBench: Evaluating AI's Ability to Replicate AI Research

- **元信息**：Giulio Starace、Oliver Jaffe、Dane Sherburn、James Aung、Jun Shern Chan、Leon Maksin 等（OpenAI）｜出处 2025-04（arXiv:2504.01848；ICML 2025 待核）｜年份 2025｜代码：openai/preparedness（含 PaperBench）｜**核验状态：已核验**（arXiv API + OpenAI 发布）[原文]
- **研究动机**：AI 能否从零复现一篇研究论文，是"会做研究"的硬指标；现有评测只看代码或问答。[原文]
- **技术贡献**：**20 篇 ICML 2024 Spotlight/Oral** 论文，从零复现（理解贡献→写代码→跑实验）；与原作者共同设计 **rubric**，分解为 **8,316 个可评分子任务**；用 rubric judge 自动评分，并单独评测 judge；最佳 agent（Claude 3.5 Sonnet + 开源 scaffold）平均 **21.0%**，未超过人类 ML 博士基线。[原文]
- **讨论**：把"复现"操作化为细粒度 rubric，是 T6 的里程碑；但 rubric 评分仍由 LLM 完成，可能偏好表面相似的实现；20 篇论文的领域覆盖有限；复现 ≠ 理解。[推测]
- **树定位**：milestone task = **AI 研究复现评测**；novelty = **1 类**。
- **challenge→insight**：C: 复现质量难评分。→ I: 与原作者共建分层 rubric，把"复现"拆成可判分的子任务。

## F2. REPRO-Bench: Can Agentic AI Systems Assess the Reproducibility of Social Science Research?

- **元信息**：Chu-Xuan Hu、Li-Yun Zhang、Yeji Lim 等｜出处 arXiv 2025-07（编号待补）｜年份 2025｜**核验状态：已核验**（arXiv 摘要 + ACL 2025 Findings DOI: 10.18653/v1/2025.findings-acl.1210；最佳 agent 21.4%，REPRO-Agent 相对基线 +71%）。[原文]
- **研究动机**：社会科学论文的计算可复现性差，人工核查成本高；能否让 agent 自动判断"这篇论文的代码/数据能否复现结论"。[原文]
- **技术贡献**：构建社科论文复现性 benchmark；提出 **REPRO-Agent**；把复现性判定从二分类扩展为 1–4 评分；报告最佳 agent 准确率 21.4%、REPRO-Agent 相对基线 +71%（说明任务很难）。[原文]
- **讨论**：[推测] 与 PaperBench 互补：PaperBench 考"动手复现"，REPRO-Bench 考"判断可复现性"。21.4% 的准确率说明 LLM 还无法可靠做"复现审计"。不足：社科数据/环境异质性强，评分标准主观。
- **树定位**：milestone task = **可复现性评估**；novelty = **1 类**。
- **challenge→insight**：C: 复现性审计昂贵。→ I: 让 agent 读代码/数据/环境并给出分级复现性判断。

## F3. CodeScientist: End-to-End Semi-Automated Scientific Discovery with Code-based Experimentation

- **元信息**：Peter Jansen、Oyvind Tafjord、Marissa Radensky、Pao Siangliulue、Tom Hope、Bhavana Dalvi Mishra 等（AI2）｜出处 **ACL 2025 Findings**；arXiv:2503.22708（2025-03）｜年份 2025｜**核验状态：已核验**（arXiv API comment）[原文]
- **研究动机**：端到端 AI Scientist 的自由度太大、难以验证；能否把发现限制在**代码可执行实验**上，做半自动、可验证的搜索。[原文]
- **技术贡献**：把 ideation + 实验构造建模为**遗传搜索**：想法/代码/文章作为可变异个体，自动执行实验并筛选；批量产出 100+ 论文级制品，其中据报告有 1 篇被 workshop 接收；人工多轮评审验证新颖性/正确性。[原文/组内]
- **讨论**：code-first + 遗传搜索是"可验证性"较好的一条路线；但"论文级制品"的门槛低，workshop 接收是小样本；遗传搜索的适应度函数仍由 LLM/规则定义。[推测]
- **树定位**：milestone task = **代码实验驱动的半自动发现**；pipeline = **遗传搜索 over code/articles**；novelty = **2 类（pipeline）**。
- **challenge→insight**：C: 开放式发现无法验证。→ I: 把假设限制为可执行代码实验，用执行结果做筛选信号。
