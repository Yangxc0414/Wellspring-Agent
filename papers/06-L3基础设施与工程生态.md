## F1. ToolUniverse

- **元信息**：Shanghua Gao、Richard Zhu、Pengwei Sui、Zhenglun Kong、Sufian Aldogom、Yepeng Huang、Ayush Noori、Reza Shamji、Krishna Parvataneni、Theodoros Tsiligkaridis、Marinka Zitnik（Harvard Medical School / MIT 等）｜arXiv:2509.23426（2025-09）｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：AI scientist 系统高度定制、与固定工作流耦合，工具、数据、分析无法在生态中复用；每建一个系统都要重新接一遍工具。需要一个**统一的 AI–工具交互标准**与开放工具生态。[原文]
- **研究挑战**：① 科研工具接口异构（Python 包、API、数据库、仪器）；② 工具描述需要让 LLM 能正确选择与填参；③ 工具质量与安全性参差；④ 生态需要持续扩展而不破坏兼容。[原文+推测]
- **技术贡献**：提出**工具交互标准**：每个工具用自然语言声明用途、**typed schema** 描述输入输出、并提供后台执行实现；核心是 **Find Tool / Call Tool** 两个原语，配合 **Tool Discoverer**（把新工具接入生态）与 **Tool Optimizer**（优化工具描述）；MCP 原生；论文报告聚合 **600+ 工具**（项目后续扩展到 2,700+）[数量为论文/项目页口径，动态变化]；支持开放与闭源模型。[原文]
- **讨论**：
  - **是否有效**：它解决的是“工具生态的接口标准”问题，是基础设施级贡献；但工具数量不等于工具可靠，缺少统一的工具正确性认证。[原文+推测]
  - **还能怎么解决**：给工具加“验证用例 + 失败模式”元数据；用执行轨迹自动改进描述；建立工具版本兼容与安全审计机制。[推测]
  - **不足**：① 工具质量/覆盖率随领域不均；② typed schema 仍难表达复杂科学对象；③ 工具调用错误的科学后果未评估；④ 生态治理（谁能发布、如何审核）未解决；⑤ 评测多集中在生物医学。[推测]
- **树定位**：L3-T6 的里程碑工作；milestone task = **科研工具生态与调用标准**；pipeline/representation = **工具声明 schema + Find/Call 原语 + MCP**；novelty = **1 类（新 task/标准）**。
- **challenge→insight**：C: 工具接口碎片化、无法复用。→ I: 用统一 schema 声明工具，把“找工具/调工具”变成两个标准动作。C: 新工具接入成本高。→ I: Tool Discoverer 自动包装 + Tool Optimizer 优化描述。

## F2. ScienceAgentBench

- **元信息**：Ziru Chen、Shijie Chen、Yuting Ning、…、Yu Su、Huan Sun 等 20 人（Ohio State / 多机构）｜arXiv:2410.05080（2024-10）｜**ICLR 2025**｜**核验状态：已核验**（arXiv API + 组内注）[原文]
- **研究动机**：端到端自动化的口号越来越响，但缺少对**单个科研工作流任务**的严格评估：agent 到底能不能把一步数据分析做对？成本多少？在什么条件下可解？[原文]
- **研究挑战**：① 任务要来自真实论文，保证科学真实性；② 输出是代码/结果，判定标准复杂；③ 不同任务成本差异大，需控制预算；④ 要区分“模型能力不足”与“任务本身不可解”。[原文]
- **技术贡献**：从 **44 篇同行评审论文**抽取 **102 个数据驱动发现任务**，覆盖生物信息、计算化学、GIS、心理学等；配套**结构化 rubric、执行评估、成本追踪**；提出 **solvable set** 与预算控制设置，避免“无限试错”；系统评测多个 agent 框架，暴露其在真实科研代码任务上的低成功率。[原文]
- **讨论**：
  - **是否有效**：它把“科研 agent 评测”从 demo 拉到可复现的任务级；102 个任务规模有限但质量高。[原文+推测]
  - **还能怎么解决**：增加过程评估（中间产物是否正确）；把任务组织成依赖图而非孤立任务；引入跨任务迁移测试。[推测]
  - **不足**：① 任务偏向数据分析/编码，不覆盖实验设计；② rubric 由作者制定，可能存在评分偏差；③ 任务可解性受环境依赖影响；④ 未评估长时程研究。[推测]
- **树定位**：L3-T1 的 1 类工作（任务级科研 agent benchmark）；pipeline = **论文抽取 + rubric + 执行评估 + 成本控制**。
- **challenge→insight**：C: 端到端口号无法定位失败环节。→ I: 把科研拆成 102 个可执行单任务，先测单步能力。C: 试错成本无上限。→ I: 用预算与 solvable set 约束评测。

## F3. AstaBench

- **元信息**：Jonathan Bragg、Mike D'Arcy、Nishant Balepur、Dan Bareket、Bhavana Dalvi、Sergey Feldman 等（Allen Institute for AI）｜arXiv:2510.21652（2025-10）｜组内注 2025-08，实际预印本为 2025-10｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：科研 agent 评测碎片化：每个 benchmark 只覆盖一个环节、环境与评分不可比。需要一个**统一的、严格的科研任务套件 + harness**，让不同 agent 在同一标准下比较。[原文]
- **研究挑战**：① 任务跨检索、代码、数据分析、写作多个环节；② 评分要可复现且抗 gaming；③ 运行成本与时间差异大；④ 不同任务的“正确”定义不同。[原文+推测]
- **技术贡献**：AstaBench = **科研任务套件 + 统一评测 harness + 成本/时间记录**；以统一接口承载检索、代码、数据分析等多类科研任务（组内材料称复用 SciCode、MLE-bench、PaperBench 等；具体套件构成以论文为准），提供标准化运行与评分；持续维护排行榜与任务版本。[原文+组内补充]
- **讨论**：
  - **是否有效**：作为“评测操作系统”有价值，让结果可比；但它本身不提出新能力，且套件覆盖仍以可自动判定的任务为主。[推测]
  - **还能怎么解决**：加入过程级评分与失败归因；把开放式任务交给专家 rubric；版本化任务防止过拟合。[推测]
  - **不足**：① 自动评分偏终态；② 任务难度分布不透明；③ 运行成本高；④ 对“科学重要性”无评估；⑤ 套件更新可能导致排行榜不可比。[推测]
- **树定位**：L3-T1 的**评测基础设施**；novelty = **2 类（统一 harness/表示）**，并继承多个 1 类 task。
- **challenge→insight**：C: benchmark 各自为政、不可比。→ I: 用统一 harness 承载多套件，标准化环境、预算与评分。

## F4. SkillFoundry

- **元信息**：Shuaike Shen、Wenduo Cheng、Mingqian Ma、Alistair Turcan、Martin Jinye Zhang、Jian Ma（Carnegie Mellon University 等）｜arXiv:2604.03964（2026-04）｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：科研 agent 每次任务都从零规划，领域内的可复用操作（技能）没有被沉淀；异构科学资源（论文、代码、数据库）中的程序性知识难以转成可调用技能。[原文]
- **研究挑战**：① 技能粒度难定；② 从异构资源抽取的技能可能错误；③ 技能库会膨胀/冲突；④ 需要验证技能在新任务上真的有用。[原文+推测]
- **技术贡献**：**树引导的技能库构建与维护**：把领域任务分解为技能树，从异构资源生成技能候选，做去重/合并/剪枝，并在执行中更新；技能以可调用模块形式存储，供 agent 复用。[原文]
- **讨论**：
  - **是否有效**：把“技能”从提示词技巧变成可维护资产，方向正确；但技能正确性与跨任务收益的验证仍是薄弱环节。[推测]
  - **还能怎么解决**：给每个技能绑定验证用例与失败条件；用执行成功率做技能淘汰；技能组合的兼容性检查。[推测]
  - **不足**：① 依赖初始任务分布；② 技能树维护成本；③ 错误技能可能被反复调用；④ 缺少与强基线（无技能库）的大规模对比细节。[推测]
- **树定位**：L3-T2/T3 的**技能记忆表示**；novelty = **2 类（技能库表示与构建 pipeline）**。
- **challenge→insight**：C: 领域操作无法沉淀、每次重学。→ I: 用技能树组织程序性知识，并从异构资源自动构建。

## F5. ScienceClaw（持续自进化 benchmark）

- **元信息**：Mingda Zhang、Wenjin Liu、Tiesunlong Shen、Zikai Xiao、Zhenghong Lin、Qing Xu、Erik Cambria、Xiaoying Tang、Haoran Luo｜arXiv:2610.08691（2026-10）｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：LLM agent 能完成科学任务，但**一次成功执行很少转化为程序层面的持久改进**；现有评测只看单任务，不测“跨任务序列中是否越做越好”。[原文]
- **研究挑战**：① 如何定义“自进化”（改提示？改代码？改技能？）；② 进化必须经过科学验证，否则会把错误固化；③ 要测保留（不遗忘）与跨数据集迁移；④ 进化成本要可接受。[原文]
- **技术贡献**：把 ScienceClaw 形式化为**固定参数的程序自进化**：统一任务求解、科学验证、程序更新三件事；**ScienceClaw-Eval 覆盖 23 个学科**，用序列任务流与独立 reset 评估科学正确性、**进化增益、保留、跨数据集迁移、进化成本**；框架修复可执行工作流并沉淀为 Skill–Operator 更新；以**可复现性 / 跨任务收益 / 科学约束三重验证**作为沉淀门槛。[原文]
- **讨论**：
  - **是否有效**：它第一次把“自进化”做成可测的 benchmark，而不是一句口号；三重验证门槛是对“错误固化”的直接回应。[原文]
  - **还能怎么解决**：加入负面迁移测试（进化后更差）；让人工审计高风险技能；把进化限制在可验证子空间。[推测]
  - **不足**：① 23 学科但任务深度有限；② “程序自进化”不含参数学习，能力上限受限；③ 进化成本与收益的权衡未给普适结论；④ 跨机构/跨工具迁移未测。[推测]
- **树定位**：L3-T3 的 1 类工作（自进化评测 task）+ 2 类（验证驱动的技能沉淀 pipeline）。
- **challenge→insight**：C: 成功执行不沉淀、跨任务无复利。→ I: 把执行修复写成 Skill–Operator 更新，并用三重验证决定是否入库。C: 自进化可能固化错误。→ I: 先验证再沉淀，并测保留与迁移。

## F6. AutoResearchClaw

- **元信息**：Jiaqi Liu、Shi Qiu、Mairui Li、…、James Zou、Zeyu Zheng、Cihang Xie、Mingyu Ding、Huaxiu Yao 等 36 人（UNC / Stanford 等）｜arXiv:2605.20025（2026-05）｜**核验状态：已核验**（arXiv API；GitHub 项目与组内描述一致）[原文]
- **研究动机**：真实科研是迭代的：假设会被多角度挑战、实验失败会改变下一步、经验应跨轮次积累。现有自主科研系统多为**线性流水线**：单 agent 推理、失败即停止、不携带跨 run 经验。[原文]
- **研究挑战**：① 失败后如何归因并继续；② 多 agent 辩论如何避免冗长无效；③ 人类干预的粒度；④ 生成论文的引用与数据造假风险；⑤ 跨 run 经验如何不遗忘。[原文]
- **技术贡献**：五机制多 agent 流水线：**结构化多 agent 辩论**（假设生成与结果分析）、**self-healing executor**（失败诊断与重试/改道）、**Stage-15 PIVOT/REFINE 决策**（继续/调参/换向）、**HITL Co-Pilot 六档干预 + SmartPause 置信度触发**、**MetaClaw 跨 run 自学习**（教训抽取 + 30 天时间衰减）；工程上加入 **4 层引文核验**（arXiv→CrossRef/DataCite→S2→LLM 相关性）与 VerifiedRegistry 强制使用真实实验数据；ARC-Bench 覆盖 55 主题多域。[原文+组内补充]
- **讨论**：
  - **是否有效**：它是“自治度可调 + 跨 run 记忆 + 反伪造”最完整的开源工程范本；但这些机制的独立贡献缺乏严格消融，效果多为项目自评。[原文+推测]
  - **还能怎么解决**：把失败归因做成可审计的因果图；用外部团队复现；将引用核验扩展到数据/图表。[推测]
  - **不足**：① 36 人工程项目，复现成本高；② 23 阶段流水线复杂、错误传播路径长；③ 辩论可能产生“共识幻觉”；④ 跨 run 记忆的时间衰减是启发式；⑤ 缺独立第三方评测。[推测]
- **树定位**：L3-T2/T3 的**系统级集成**；novelty = **2 类（带记忆与自愈的 pipeline）**；PIVOT/REFINE、MetaClaw、引文核验分别可算 **3 类模块**。
- **challenge→insight**：C: 线性流水线遇失败即停、经验不积累。→ I: 自愈执行器 + PIVOT/REFINE + 跨 run 教训库。C: 生成论文可能造假。→ I: 多层引文核验 + 真实实验数据注册表。

## F7. SwarmRSI

- **元信息**：Qianru Meng、Xi Zhang、Konstantinos Papakostas、Congfeng Cao、Wenxiang Hu、Tianyi Lu、Xiao Zhang、Lun Zhou、Zaiqiao Meng、Zhaochun Ren、Xiaohui Yan、Yougang Lyu｜arXiv:2610.20431（2026-10-14）｜**核验状态：已核验**（arXiv API；非常新，未经同行评审）[原文]
- **研究动机**：单 agent 的递归自我改进（RSI）受限于个体能力与上下文；科学发现需要多种专长与并行探索。能否让**agent 蜂群**通过进化实现递归自我改进？[原文]
- **研究挑战**：① 蜂群中的改进如何传播而不退化；② 如何评估“群体智能”而非个体；③ 进化过程可能奖励投机策略；④ 计算成本随群体规模爆炸。[原文+推测]
- **技术贡献**：把科学 agent 组织成可进化的蜂群：个体承担不同研究角色，通过**变异/选择/交叉**与共享结果迭代；以科学任务表现作为选择压力，实现群体层面的递归自我改进；论文报告在多类科学任务上的改进。[原文]
- **讨论**：
  - **是否有效**：概念上把“多 agent”与“自进化”结合，是 2026 年新出现的方向；但预印本极新，实验规模与基线强度需谨慎看待。[推测]
  - **还能怎么解决**：引入多样性保护防止蜂群同质化；把选择压力从分数改为可验证发现；限制进化自由度以保证安全。[推测]
  - **不足**：① 缺同行评审与独立复现；② “递归自我改进”的操作化定义可能过宽；③ 成本高；④ 安全风险（自我修改代码）未讨论。[推测]
- **树定位**：L3-T3 的探索性工作；novelty = **2 类（蜂群式进化 pipeline）**，是否构成 1 类新 task 待时间检验。
- **challenge→insight**：C: 单 agent 自我改进上限低。→ I: 用群体变异/选择把改进放到种群层面。

## F8. SafeScientist + SciSafetyBench

- **元信息**：Kunlun Zhu、Jiaxun Zhang、Ziheng Qi、Nuoxing Shang、Zijia Liu、Peixuan Han、Yue Su、Haofei Yu、Jiaxuan You（UIUC 等）｜arXiv:2505.23559（2025-05）｜组内注 **NeurIPS 2025**｜**核验状态：部分核验**（arXiv 元数据；NeurIPS 录用与“安全 +35%”数字为组内材料，未独立核对）[原文+组内数据，未核验]
- **研究动机**：科研 agent 会被要求执行有风险的实验/操作（危险化学品、生物制剂、双用途研究）。现有 agent 框架以“完成任务”为目标，缺少风险感知与监督。[原文]
- **研究挑战**：① 科学风险类别多且领域相关；② 过度保守会阻碍合法研究；③ 多 agent 协作中风险可能被拆分绕过；④ 缺少风险评测集。[原文+推测]
- **技术贡献**：**提示监控 + 多智能体协作监督**的风险感知框架；配套 **SciSafetyBench** 覆盖多类科学危害场景；在保持任务完成度的同时降低不安全行为；论文/组内材料报告安全性较传统框架提升约 **35%**。[组内数据，未核验]
- **讨论**：
  - **是否有效**：把科研安全从“内容过滤”推进到“过程监督”，方向正确；但风险分类与红队覆盖有限，规则式监督易被绕过。[推测]
  - **还能怎么解决**：把风险预算与实验审批流结合；用形式化约束限制工具调用；建立跨机构事件库。[推测]
  - **不足**：① 安全提升数字缺独立复现；② 评测场景可能泄露给模型；③ 对双用途研究的判定争议大；④ 未覆盖湿实验物理安全。[推测]
- **树定位**：L3-T4 的 1 类工作（科研安全评测 task）+ 2 类（监督 pipeline）。
- **challenge→insight**：C: 科研 agent 可能执行危险操作。→ I: 在提示层监控 + 多 agent 互相监督，并建立风险 benchmark。

## F9. Paper2Agent

- **元信息**：Jiacheng Miao、Joe R. Davis、Yaohui Zhang、Jonathan K. Pritchard、James Zou（Stanford）｜arXiv:2509.06917（2025-09）｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：论文的价值不仅是文本，更是**可复用的分析方法**；但读者要复现代码、理解参数、适配新数据，成本极高。能否把一篇论文自动变成可交互、可靠的 agent？[原文]
- **研究挑战**：① 从论文+代码库抽取可执行工作流；② 把方法封装成有输入输出契约的工具；③ 保证在新数据上不胡编；④ 评测“论文 agent”是否真的复现了方法。[原文+推测]
- **技术贡献**：自动把论文与其代码转成**可交互 agent**：解析方法、生成工具封装、构建测试用例、提供自然语言接口；让用户用自己的数据调用论文方法；在多个生物医学论文上展示可用性。[原文]
- **讨论**：
  - **是否有效**：它把“论文复用”变成“论文即 agent”，是知识基础设施的有趣形态；但自动化封装的成功率与适用边界仍受限。[推测]
  - **还能怎么解决**：把论文 agent 注册进 ToolUniverse 一类生态；用原始论文结果做回归测试；标注适用范围与外推风险。[推测]
  - **不足**：① 依赖代码质量与可运行性；② 只覆盖计算方法类论文；③ 测试用例多由 LLM 生成，可能自洽；④ 缺少大规模成功率统计。[推测]
- **树定位**：L3-T2/T6 的**知识复用表示**；novelty = **2 类（论文→agent 的转换 pipeline）**。
- **challenge→insight**：C: 论文方法难复用、复现成本高。→ I: 把论文+代码自动封装成带测试的 agent。

## F10. AgenticSciML

- **元信息**：Qile Jiang、George Karniadakis（Brown University）｜arXiv:2511.07262（2025-11）｜**核验状态：已核验**（arXiv API）[原文]
- **研究动机**：科学机器学习（SciML）需要多步骤协作：选模型、造数据、训练、诊断、改进。单 agent 难以覆盖；多 agent 协作可能产生“涌现发现”。[原文]
- **研究挑战**：① 角色如何划分；② 多 agent 讨论如何收敛；③ 科学机器学习任务的成功判据；④ 计算成本。[原文+推测]
- **技术贡献**：协作式多 agent 系统用于 SciML 的**涌现发现**：不同角色 agent 分工提出/实现/评估模型，通过协作迭代产生新方法；论文报告在若干 SciML 任务上的发现与改进。[原文]
- **讨论**：
  - **是否有效**：提供了“多 agent 做方法发现”的案例；但“涌现”一词难以证伪，需看是否产生人类未预设的新机制。[推测]
  - **还能怎么解决**：用消融证明协作优于单 agent；把发现形式化为可检验假设；公开失败案例。[推测]
  - **不足**：① 领域窄（SciML）；② 评估以性能为主，缺新颖性判断；③ 计算成本；④ 预印本未经评审。[推测]
- **树定位**：L2-T2 的领域化多 agent 工作；novelty = **4 类（把多 agent 模块用于 SciML）**，除非证明新协作机制。
- **challenge→insight**：C: SciML 方法设计需要多步专家协作。→ I: 用角色化多 agent 把设计—实现—评估并行化。

## 本批小结

**基础设施层已经“有”的东西**：工具标准（ToolUniverse）、任务级 benchmark（ScienceAgentBench / AstaBench）、技能库（SkillFoundry）、自进化评测（ScienceClaw）、安全 benchmark（SafeScientist）、论文复用（Paper2Agent）。

**基础设施层真正缺的东西**：
1. **统一证据/溯源账本**：工具调用、文献、代码、实验结果分散在各系统，没有跨系统的 provenance 本体。
2. **过程级与长周期评测**：现有 benchmark 以终态为主，月级任务、失败恢复、人员交接未测。
3. **自进化的安全边界**：SkillFoundry/ScienceClaw/SwarmRSI 都在改程序，但没有“哪些改动必须人工审批”的规范。
4. **技能/记忆的互操作**：技能库、世界模型、论文 agent、工具生态各说各话，没有统一 schema。
5. **湿实验 sim2real 基准**：安全、廉价的实验仿真环境缺失，导致实验策略无法大规模预训练。
