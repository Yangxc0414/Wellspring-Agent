# 研讨纪要对齐（调研反思）：证据即研究本质，顺序由要素依赖推导

> 状态基线：2026-11-21。承接 149/150（方法原模型与 MDD 三层）与本次"智能体系统设计研讨"会议纪要（刘博涵/周鑫汐/杨想成）。
> 本文新增前端"要素组合视图"（`apps/web`）并完成纪要观点 ↔ 系统现状的调研映射；注册表本体与后端编排逻辑未动。

---

## 0. 一句话结论

纪要里最锋利的三问——"为何当前流程顺序如此？"、"研究的本质是什么？"、"自进化系统还需要固定架构吗？"——本系统各有一个结构性回答：**顺序 = 要素依赖图的拓扑序**（本轮新增要素组合视图，单测钉死拓扑性质）；**研究本质 = 证据**（整个内核就是证据治理：span/EA/capsule/claim/closure/lineage）；**固定与动态的边界 = 用户侧槽位固定、内部活动按方法组合可变**（SESSION PATH + 方法矩阵 + 要素图）。剩余缺口是"要素组合的租约化提案"（roadmap，需后端 SPEC 先行）。

## 1. 调研反思：纪要观点 ↔ 系统现状逐条映射

| 纪要观点 | 系统现状 | 差距与本轮动作 |
|---|---|---|
| 原模型核心是**要素组合而非固定阶段**；顺序调换（问题/假设 ↔ 研究方案）会改变输入输出关系 | 九槽位顺序此前"看起来像经验预设"——尽管它实际是依赖序，但**没有把依赖显式化** | 新增**要素组合视图**：每个治理要素声明消费/产出，15 条边逐条标注后端出处；单测断言"每个被消费的上游必须更早出现"（拓扑性质）——顺序是被推导的 |
| **研究的本质 = 证据**；以证据为指导区分研究方法 | 内核即证据治理（span-only、capsule/EA、claim 三元组、closure、lineage）；方法注册表按方法声明产物与 cannot_support | 已对齐；147 把"主张+范围"上屏，本视图把"证据从哪来、到哪去"上屏 |
| 实验 = **受控 + 随机**两要素 | controlled-experiment profile 的 protocol_fields 含 randomization/blocking/power_analysis；cannot_support 排除"未操控变量的因果" | 已对齐；方法模型详情卡可见 |
| **评估效力差异**（问卷 vs 实验；SOTA ≠ 用户觉得好用） | 每方法声明 cannot_support（survey: 行为因果/未响应者代表性；benchmark: 真实开发效率） | 已对齐；147/149 把能力边界渲染到详情卡 |
| **用户侧固定、智能体侧动态**；静态架构图画不了动态智能体 | SESSION PATH（用户侧，槽位固定）+ 方法矩阵 + 播放器（内部演示态） | 已对齐；149/150 给出呈现形式 |
| **Agent 自主改进阶段编排**（被纠正为"仅内部活动可动"） | RSI 租约目前只覆盖两个注册参数（检索预算、S5 seeds）；**编排组合的提案机制不存在** | 明确登记为 roadmap（见 §4），本轮不实现——需要后端 SPEC 先行 |
| 建模须基于**学术界既有结论**，不能拍脑袋 | 注册表每方法带文献依据（Kitchenham 2007 / Wohlin 2014 / PRISMA 2020 / Runeson & Höst 案例指南等引用已在 guidelines 块） | 已对齐；方法详情卡展示 |

## 2. 本轮实现：要素组合视图

每个治理槽位改写为**研究要素**（回答"产出/消费什么"而非"第几步"）：

- **消费边**（15 条）逐条标注后端出处，例：S5 消费 S4 的"冻结协议（protocol_sha256 必须一致）"（run SPEC v0.8.0）；S5b 消费 S5 的 EA + 人给 human_reason（空理由 CLI 拒绝）；S8–S12 消费已签 claim（未签 → allowed_result_numbers 空）；S13–S16 消费四件产物一致性；
- **产出**用产物 chips（RunCapsule / EA immutable / ClaimRecord signed / 图+manifest…）；
- **人工要素**（6 个）琥珀色标"人"——与门禁一一对应；
- 顶部说明直接回应纪要："调换两个要素会改变输入输出关系——所以顺序是被推导的，也是可按方法组合的"。

**单测钉死的结构性质**（4 例）：拓扑序性质（每个被消费的上游必须更早出现）；链路闭合断言（S5 < S5b < S6/S8–S12 < S13–S16，S4 < S5）；人工要素恰为六个门；每条边必须带出处。这把"顺序为什么是这样"从口头辩护变成了可执行断言。

## 3. 设计主张（可证伪）

1. **顺序 = 拓扑序**：一旦某个要素的输入依赖改变（如案例研究里语料收集先于假设精化），合法组合可以不同——治理槽位不变、组合可变，这正是纪要"要素组合而非固定阶段"的落地；方法注册表的 fit_stages 是组合声明的第一步，编排器消费组合是下一步；
2. **证据是贯穿元模型的第一名词**：要素图上流动的东西全部是证据制品（span→矩阵→假设→协议→capsule→EA→claim→稿件→closure），没有一条边流动的是"经验"或"直觉"；
3. 网页内演示签署（146）+ 要素图共同回答"自进化系统是否需要固定架构"：**用户面（槽位/门/面板）固定，组合面（编排/参数/候选）在租约与门禁下可变**。

## 4. Roadmap：要素组合的租约化提案（需后端 SPEC 先行）

- RSI 候选类型扩展：`composition-proposal`——agent 基于历史任务反馈提出要素组合变更（如"案例研究任务将 S1b 移至 S5 之后做二次综合"），附 dry-run 的输入输出对照；
- 准入证据：与现有 public/hidden/regression 同构——组合提案必须在历史任务回放上不破坏任何治理不变式（门/链/签）；
- 人签：组合变更与参数变更同级，走租约 + 人签；到期可撤销（回滚到原拓扑序）；
- 验收：一条真实任务在提案组合下跑完并保持 31 项 python 门 + readiness 全绿。
