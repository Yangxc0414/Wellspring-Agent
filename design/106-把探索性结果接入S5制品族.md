# 106-把探索性结果接入 S5 制品族：桥到人签之前

> 状态基线：2026-11-18。承接 103（五个缺口之五：结果接不进门的后半段）与 104。
> 本轮把 ESE 执行结果封成与 run-contract 同族的制品，并用项目自己的校验器验过：**0 阻塞**，只剩 1 条应保留的警告。
> 边界：产物只写文件；签名仍是人签 CLI 步骤，本轮没有、也不应该代签。

## 1. 缺口的最后一段

之前：执行器只产出 result.json/result.md，S5 的 RunCapsule/EA 是另一套（ML 实验用）。两套产物无法互相验证，所以"ESE 结果"永远停在探索性 note。

本轮：新增 `ese_exec.emit_run_artifacts`，把一次研究结果写成：

| 文件 | 内容 |
| --- | --- |
| `run-capsule.json` | run_id、protocol_id/sha256、dataset_id/sha256（三个仓库 HEAD 的哈希）、code_sha256（执行器源码）、metric_name、seeds、mean/std、status=completed、warnings |
| `metrics.json` | 每仓库的 commits/rate/CI + HEAD → 作为 EvidenceArtifact 的字节来源 |
| `ea.json` | EvidenceArtifact：kind=metric、path=metrics.json、sha256、source=ese-exec、scope=S5/... |
| `run-contract.json` | 用 `build_run_contract` 生成（含 contract_sha256） |
| `run-contract-check.json` | 用 `verify_run_contract` 校验的结果 |

触发：`python scripts/run_ese_study.py --emit-run-artifacts ...`。

## 3. 人签仍然差什么

`run claim` 的接口是：

```text
python -m research_agent run claim --capsule .../run-capsule.json --ea .../ea.json \
  --statement "..." --human-reason "..." --scope S5/ESE-MS-20261118-03
```

差三件事，且都应由人来做：

1. **写 statement**：把"37.5% [36.2, 38.8]，bug-fix +4.6pp，分层调整 +6.8pp 且异质"写成一句可签署的断言；
2. **结构化 assertion 的映射**：当前 claim 校验器按 run capsule 的 metrics 重算数值断言；ESE 指标的断言需要映射成它认识的 metric/比较器（或明确用 legacy 断言并接受"未重算数值"的标注）；
3. **human-reason 与 scope**：确认适用范围（三仓库、Python、特定标签规则）与不适用范围。

所以本轮做到的是"**桥到人签之前**"：系统能把探索性结果封成可校验的 S5 制品，但**不代签**。

---

## 4. 对设计的意义

1. 之前 S5 只有一种执行面（CSV/ML 实验）；现在 repository-mining 也能产出同族制品。S5 从"实验执行器"变成"**执行面 + 结果契约**"。
2. `metrics.json` 作为 EA 的字节来源，意味着"结果表"本身就是证据；run-capsule 把协议、数据（仓库 HEAD）、代码三个哈希绑在一起，任何一项变了都能被发现。
3. 仍然缺：ESE 指标在 claim assertion 里的映射；closed-loop 的 closure/lineage 尚未消费 ESE 胶囊。这两项是下一轮。
