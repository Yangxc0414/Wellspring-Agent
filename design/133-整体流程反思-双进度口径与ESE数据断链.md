## 2. 走查发现并修掉的问题

### 2.1 ESE 数据从未加载成功（严重，已修）

全程走查抓到 4 个 404：`/ese-runs.json`、`/ese-history.json?v=1`、`/ese-studies.json?v=1`、`/api/ese/runs`。

根因：这些 JSON 实际在 `site/app/ese-*.json`（与 index.html 同级），但 `EseRunsPanel.tsx` 用**绝对路径** `/ese-*.json` 请求 → 解析到站点根 `site/` → 404。也就是说 ESE 运行视图的数据在**本地和线上都没有真正加载过**，只是靠静态文案撑着。`/api/ese/runs` 则是静态构建下必然失败的 runtime 调用，白白发请求。

修：
- 三处 bundled 快照改为相对路径 `./ese-*.json`；
- `/api/ese/runs` 用 `runtimeAvailable` guard，静态构建下直接跳过，不发注定失败的请求。

实测走查 `PROBLEMS: none`。132 §4 曾把这个绝对路径问题归为"下一步"，当时判断是"子路径部署会 404"——**实际连本地根部署都 404，比预估严重**。教训：路径 bug 要在真实部署结构下验，不要凭直觉推断影响范围。

### 2.2 两个「/9」进度同屏、口径不明（中等，已修）

任务头显示「8/9 stages · gate pending」，同一时刻 RESEARCH FLOW 显示「待签 · 第 0/9 步」。132 曾判"两套独立状态、可接受"，独立审查推翻了这个判断：

- 两者**同为 /9 口径**、都被读成"九阶段完成几个"；
- FlowDemo 虽有横幅解释"进度各自独立"（文件行号有、确实可见），但数字先于小字被读到，观众必须先理解"回放 vs 教学重演"才能读懂；
- 按 design/127 自己"S1–S3 标签配 8/9 算自相矛盾并修复"的同一标准，这里只是把矛盾从标签挪到右栏，修得不彻底。

但这是**呈现缺陷而非数据/门禁错误**。否决"让 step 跟随任务进度"（牺牲从零演示这一核心能力）。采纳最小改法：
- 任务头 → 「**回放** 8/9 stages」（带 title 说明两处口径不同）；
- FlowDemo → 「**教学重演** · 待签 · 第 0/9 步」，卡片头 `IN PROGRESS` → `REPLAY · 教学重演`。

两个数字各自带口径，观众一眼能区分，且完全不动状态机。

### 2.3 阻塞任务谎称已到 META（中等，已修）

任务头面包屑显示「RESEARCH / META · 自进化提案」，但同一任务 `G5` 仍是 blocked、`auto.gate="claim"`、META 阶段为 waiting——**人签门没过，根本没到 META**。根因是 kicker 直接取 `task.stage=8` 对应的 autoStages[8]=META，而没有与门禁状态交叉核对。

修：当 `task.status === "blocked"` 时，kicker 改为「RESEARCH · **人签门待人签**」，不再硬指一个没真正清掉的阶段；非阻塞时保留原阶段显示逻辑。

### 2.4 确认诚实的部分（无需改）

演示人签链路：推进到 S5b 后点击「模拟人签」，状态变为「已签 · DEMO」，全程不出现"SIGNED CLAIMS"假象，DEMO 字样明确。**演示态不会被读成真实签名**——这是前面几轮一致性改造的成果，走查确认守住。

## 3. 反思

1. **逐模块审视会漏掉"同时出现"的问题**。单独看任务头和 FlowDemo 都合理，同屏看才有口径冲突；单独看 ESE 面板有降级文案，跑全程才知道它的数据从没加载。端到端走查必须作为独立一道工序。
2. **"已解释"不等于"不困惑"**。FlowDemo 横幅确实写了独立推演，但解释在长面板顶部、数字在眼前，读者顺序是反的。判断呈现问题要看"读者先看到什么"，不只是"文案是否存在"。
3. **绝对路径 bug 的影响范围要靠实测**。132 判"只影响子路径部署"，实际本地就 404——部署结构和资源层级没有在推断时被验证。
4. **第三方 API 有缓存**。WebFetch 连续返回上一个 commit 的 CI run，改用 curl 直查才拿到真实状态。验证 CI 结论时必须确认 commit hash 对齐。

3. 继续排查其他 tab 是否还有"有降级文案但数据从没加载"的隐藏断链（本轮只覆盖了 ESE）。
