### 1.2 实现：StagePlan 驱动执行

### 1.3 空产物替身为什么必要

依赖分析（Explore 逐行核查）发现 `run()` 是 279–1360 行的巨型线性函数，阶段间靠**局部变量**传产物：
跳过 literature 会在 `literature.to_dict()` 崩，跳过 idea 在 `asdict(idea)` 崩，跳过 experiment 在
`asdict(design)` 崩，跳过 figure/paper 在 `figure.figure_id` / `manuscript_bundle["audit"]` 崩。
所以不能简单 `continue`——用与真实产物**同构但显式 not_applicable** 的替身，让下游照常访问
`.spans / .candidates / .status`，既零崩溃，又不携带任何证据。

## 2. 判据 A 的实测结果

同一 topic「分析开源仓库提交历史与缺陷修复」，四个方法跑出的真实 `stage_start` 序列：

| 方法 | stage_start 序列 | 被跳过的门 |
|---|---|---|
| controlled-experiment | `idea → experiment → run → paper` | 无（该法覆盖这些阶段） |
| repository-mining | `literature → experiment → run` | G1 = not_applicable |
| systematic-literature-review | `literature → paper` | G1, G2 = not_applicable |
| case-study | `literature → experiment → run → paper` | G1 = not_applicable |

**序列真的不同了**，且每个差异都能被 `composition_plan.covered_stages` 解释——这正是 165 判据 A 的字面要求。

5 个测试全绿（判据 A 两条 + 顺序一致一条 + 判据 B 治理面与产物面两条）。

## 3. 不变项（没有改坏的东西）

- **run/EA/claim 人签不变量**：被跳过的 run 不执行 S5、不产 capsule/EA/claim draft，无法 claim；
  未被跳过时原路径一字未改。
- **门禁语义不漂移**：跳过阶段的门标 not_applicable 而非 pass——门禁不会"因为方法没走这阶段就算通过"。
  未跳过阶段的 Q0/G1/G2 原逻辑保留（strict 下仍 needs_human/blocked 早停）。
- **向后兼容**：未声明 `method_id` 时 `covered=None`，全部阶段照常执行；组合解析失败也回退全阶段（fail-open，与 164 一致）。
- **导出/写盘**：`write_pipeline_artifacts` 对替身产物正常写盘（status=not_applicable 明示），
  `evidence_packages` 汇总时空 hits/spans → 0 证据，不冒充。

## 5. 边界与下一步（诚实）

1. **阶段顺序仍不完全等于组合接线顺序**：当前实现只决定"跑/不跑"某阶段，执行顺序仍按 pipeline
   物理顺序（literature→idea→…）。要按 wiring 顺序真正重排（如探索式先 experiment 后 literature），
   需要把巨型函数拆成阶段方法——下一轮工程。判据 A 字面满足，判据"顺序一致性"的更强版本仍未达。
2. **判据 B 只覆盖治理面与产物面**：跳过阶段的门与产物已验证；"被跳过阶段不得在后续产物留空绑定"
   的完整审计（closure/lineage 全链路）尚未做完。
3. **方法绑定冲突仍未裁决**：ESE 会话顺序与 repository-mining 组合的矛盾（169 §1.1 / 172）依然存在，
   本轮只让"按方法跑"成真，不改方法绑定。
4. **172 的元模型扩展提案**（evidence_regime、效力词表、DSR 接线）仍封存——按 173 的收敛，
   判据 A 变绿后才启动，且属 schema minor 需人工确认。
