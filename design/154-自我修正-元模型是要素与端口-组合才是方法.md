# 自我修正：元模型是"要素与端口"，组合才是方法——回应研讨纪要的完整版

> 状态基线：2026-11-21。承接 151（要素组合图）、152（研究本质推导）、153（三维建模）与研讨纪要完整版逐句重读。
> 本文是对 **151 的一处自我修正**：151 的要素图虽然叫"组合视图"，但它只呈现了一条固定拓扑链——按纪要原话，这仍是"在元模型上强行体现顺序差异"。本轮把模型拆成 **要素端口（不变）× 接线（可变）** 两层，并给出两种合法组合的端口级对比。注册表与后端未动。

---

## 0. 一句话结论

纪要里刘老师明确反对把顺序差异做进元模型，并连续追问"元模型的视角是否仅局限于这些阶段"。151 的要素图没有回答这个问题——它把顺序仍画成了链。修正后的模型：**元模型 = 要素 + 类型化端口（消费什么/产出什么，可多选）**；**方法 = 端口的接线方式**；**顺序 = 接线的自然结果**。验证式与探索式两种组合共享全部治理要素与门，差异只在方案/假设的接线端口——"变与不变"由此成为可校验的数据，而不是两张不同的图。

## 1. 自我修正：151 错在哪

| 151 的做法 | 纪要的要求 | 修正 |
|---|---|---|
| 要素图是一条**单链**（拓扑序固定） | 元模型是**要素组合**，顺序是派生的、可变的 | 元模型降为"要素 + 端口"；顺序成为组合的属性 |
| 假设只有一种接线（消费问题+矩阵） | 探索式研究里假设**从证据中事后提炼**（扎根式），是合法形状 | 假设声明两个输入端口：研究问题（先验）→ 候选假设；RunCapsule+EA（事后）→ 提炼式假设 |
| 方案只有一种产出 | 验证式的方案产出**判别式协议**；探索式的方案产出**数据收集协议**——产出随输入端口变化 | 方案的 outputs 按 consumed 端口选择（这正是"顺序调换改变输入输出关系"的结构化表达） |

## 2. 端口模型（composition.ts）

- 每个要素：`inputKinds`（可消费的输入端口，可多选）+ `outputs`（按 consumed 选择的产出端口，可多条规则）+ `human` 标记；
- **组合 = 接线序列**：每步声明消费哪个端口；`validateComposition` 做端口匹配校验——每步消费的端口必须（a）是该要素声明的输入种类、（b）已被上游产出满足。**非法接线（如探索式里让方案消费尚未存在的假设）会被校验拒绝**——"顺序由依赖推导"从口头辩护变成可执行断言；
- 两种参照组合（Easterbrook/Creswell 方法学分类的实证形态）：**验证式**（假设在前，方案消费假设→判别式协议，9 步）与**探索式**（方案先做数据收集设计→证据→假设事后提炼，8 步）。两者的治理要素、门语义、人签点完全一致——不变层。

## 3. 已实测

- `node --test tests/composition.test.ts` 4/4：两种参照组合都是合法接线；**分歧点断言**（方案的消费端口：验证式="候选假设（可判别）"、探索式="研究问题"；假设位置随接线移动）；非法接线可检出（探索式里方案消费假设 → "上游尚未产出"违规）；人工/自动要素归属正确。

## 4. 设计主张（可证伪）

1. **元模型不含顺序**：顺序属于组合。若未来某方法的合法组合无法通过端口校验，说明端口模型错了——这是可证伪的建模主张，而非图表偏好；
2. **"变与不变"的形式化**：不变 = 要素集、端口语义、门与签核；可变 = 接线（含假设的先验/事后两种合法来源）。毕设的方法论创新由此可形式化：智能体架构 = 端口图上的合法接线集合；
3. **自改进的形式化路径**：agent 提出新接线 = 组合提案；准入 = 端口校验 + 治理门 + 历史回放 + 人签租约（151 §4 的 roadmap 由此获得精确的形式定义）。

## 5. 边界与下一步

- 两种参照组合是方法学的**形态分类**（confirmatory/exploratory），不对应特定注册表方法；方法→组合的映射等 runtime 任务元数据；
- 端口类型目前是展示级分类（非类型系统）；组合提案的真实校验需后端按产物契约检查端口类型——SPEC 先行；
- 151 §4 roadmap（组合租约化提案）形式定义已精确化，实现顺序不变。
