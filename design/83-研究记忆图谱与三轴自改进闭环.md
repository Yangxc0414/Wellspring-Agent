# 83-研究记忆图谱与三轴自改进闭环：让"经验"真正进入 idea / 实验 / 论文

> 状态基线：2026-11-18。承接 81（ESE 内核）、82（demo 叙事与图）。
> 本轮交付：类型化研究记忆原型 `prototypes/ese/memory_graph.py`（69 测试）+ 只读扫描器 `scripts/research_memory_scan.py` + 本文。
> 边界：原型未注册；扫描器只读、不写项目产物、不改门禁。本文的数值全部来自真实产物扫描，不掺示意值。

## 0. 结论先行

1. **当前系统的"记忆"是五个孤岛**：单项目 artifacts、`literature_memory`、`guideline_memory`、`feedback` 账本、`verdict-ledger`。它们各自正确，但没有一个能被"下一次研究"当作**有类型、有出处、会过期**的输入。
2. **自改进缺的不是候选生成，而是"经验 → 配方 → 结果"的可测链路**：现在的 RSI 候选改检索参数/harness，改不到 idea 生成、实验设计、论文写作这三件事上；而这三件事恰恰是研究产出的全部。
3. 本轮给出并在真实项目上跑通的设计：**类型化记忆图（12 类节点 / 9 类关系 / 准入 / 哈希过期 / 预算化 pack）→ 阶段配方（recipe）→ held-out 研究任务评估 → 人签采纳 + 回滚**。扫描器在 `runtime_data/e2e-closed-loop` 上得到 **17 节点 / 3 边 / 三阶段 pack**，全部可追溯到文件与 sha256。
4. **创新点（可证伪）**：把"研究记忆"从自由文本/向量检索，变成**带准入与过期的类型化证据图**，并让它成为**阶段配方**的唯一输入；配方演化用**held-out 研究任务**评估，而不是 public 分数。若做不到"记忆进入配方后三轴指标可测提升"，该主张即被证伪。

## 1. 现状：记忆的五个孤岛

| 孤岛 | 存什么 | 谁能读 | 问题 |
| --- | --- | --- | --- |
| 项目 artifacts（`runtime_data/<project>/runs/**`） | idea / experiment / capsule / EA / claim / closure / lineage | 各模块自己、`loop_ledger`、前端 | 没有统一类型与关系；跨 run 不可查询；失败不沉淀 |
| `literature_memory`（`research_agent/literature_memory.py`） | 检索过程记忆、query 顺序 | literature / orchestrator | 只服务检索，不服务设计/写作 |
| `guideline_memory`（`guideline_memory.py`） | 写作/评审准则 | idea / writing | 无来源哈希、无过期、无准入（`memory_port` 是后加的半步） |
| `feedback` 账本（`feedback.py`） | 四环的 observe/propose/gate/apply 记录 | feedback / idea | 只影响生成约束，不是可检索知识 |
| `verdict-ledger`（`verdict_ledger.py`） | 三态判定、stale、override | next_actions / runtime | 判定正确，但"判定"没有和"经验"连成图 |

**后果（都能在真实产物里看到）**：
- 同一个 run 里，idea 的 `evidence_refs` 与 claim 的 `evidence_refs` 是两套字符串，没有边把它们连起来；
- 论文审计的 blocker（`manuscript-audit.json`）不会被下一次 idea 生成读到；
- 设计审计的警告（`design-audit.json`）只在当次 run 的报告里出现，不进入下一次设计；
- 失败 run 被保留，但没有"类型 + 适用范围 + 重试条件"，于是不可复用。

## 2. 设计目标：三个产出轴 × 四种记忆作用

**三个产出轴**（用户要的效果就在这里）：

| 轴 | 产出 | 现在靠什么 | 记忆应当提供什么 |
| --- | --- | --- | --- |
| **idea** | 候选假设、否证条件、与先行工作的差异 | LLM + 文献 span | 过去哪些假设被什么证据杀掉；哪些 lens 已饱和；哪些 gap 已闭合 |
| **experiment** | 设计、预注册、功效、执行、证据 | design card + study/run | 哪些设计缺陷反复出现；哪些数据集有坑；哪些指标不测构念 |
| **paper** | 稿件、引用、数值、图表、闭合 | writing pack + audit | 哪些句子类型反复缺证据；哪些 overclaim 被审稿人抓；哪些图表不可引用 |

**四种记忆作用**（每种都要能说清"它改变了哪一步"）：

1. **避免重复失败**：durable 失败 + 重试条件 → 下一次设计前强制读取；
2. **复用可迁移模式**：跨项目/跨数据集的成功模式（配方、检查项、阈值）；
3. **约束适用范围**：scope / 失效条件 / 数据集卡 → 防止把 Java 结论外推到 Python；
4. **传递判定**：三态判定、stale、override → 让"上一轮的结论"成为"这一轮的前提"。

> 一条纪律：**记忆不是上下文填充**。每条进入 pack 的条目都必须能回答"它改变了哪一步"；回答不了的，留在图里但不进 pack。

## 3. 记忆数据模型

### 3.1 节点（12 类）

| 类型 | 关键字段 | 来源（现有产物） |
| --- | --- | --- |
| `idea` | idea_id / status / evidence_count / lens / testability / falsification | `idea.json` candidates |
| `experiment` | design_id / primary_metric / seeds / idea_id / status | `experiment.json` |
| `run` | run_id / status / capsule hash | `run-capsule.json` |
| `evidence` | ea_id / sha256 / scope | `ea.json` / `evidence-packages.json` |
| `claim` | claim_id / statement / scope / human_reason / evidence_refs | `claim/claim.json` |
| `closure` | report_id / status / failed_checks | `closure/closure-report.json` |
| `paper` | slots / bound claims（派生，永不作为证据） | `paper.json` |
| `failure` | kind / context / retry_condition / scope | 新增（`FailureRecord`） |
| `dataset` | license / sampling / time_split / known_biases | 新增（`DatasetCard`） |
| `recipe` | stage / sections / checks / thresholds / heldout_passed / human_reason | 新增（本设计） |
| `decision` | 人/委托的决策 + 理由 + 依据节点 | autopilot / g1 / protocol |
| `finding` | check_id / severity / detail | `design-audit.json` / `manuscript-audit.json` |

**硬字段**：`source`（仓库相对 POSIX 路径）+ `sha256`。没有哈希的节点不允许进入图——否则无法判定"这条经验是不是已经过期"。

### 3.2 关系（9 类）

| 关系 | 含义 | 消费方 |
| --- | --- | --- |
| `tests` | 实验检验某 idea | idea 阶段（避免重复检验已否证假设） |
| `supports` / `falsifies` | 证据支持/否定断言 | claim / paper |
| `supersedes` | 新结论取代旧结论 | 全部阶段（旧结论降级） |
| `invalidates` | 上游变更导致下游失效 | lineage / 导出 |
| `depends_on` | 派生依赖 | closure / 复算 |
| `contradicts` | 两条记忆冲突 | 必须显式上报，不得静默取一 |
| `reuses` | 复用某模式/配方 | recipe 演化 |
| `derived_from` | 产物派生（claim→EA→capsule） | 证据链 |

关系不是装饰：**每条边都声明"它让哪一步改变"**（`evidence` 字段）。

### 3.3 准入矩阵（fail-closed）

| 节点 | 准入条件 | 不满足时 |
| --- | --- | --- |
| claim | status=supported 且 human_reason 非空；或 status=undecidable（负结果也是结果） | pending |
| idea | status=selected 且 evidence_count≥1 | pending / rejected |
| experiment | status ∈ {ready_for_g2, frozen} | pending |
| run / evidence | completed / verified 且带哈希 | pending |
| closure | ready / signed | rejected（blocked 不得被引用） |
| failure | kind ∈ durable 集合 | rejected（operational 只进日志） |
| dataset | license + scope 非空 | pending |
| recipe | heldout_passed 且 human_reason 非空 | pending |
| finding | 任何 severity | admitted（上下文，不是证据） |
| paper | 永远 | pending（投影不是证据） |

**为什么 pending 也要留在图里**：评审者需要看见"还没签的东西"；但生成阶段不许用它。这是"可见 ≠ 可用"。

### 3.4 过期（staleness）

- 节点记录 `source + sha256`；
- 重新扫描时，哈希变 → `stale` + tag `source_changed`；文件消失 → `stale` + `source_missing`；
- stale 节点**不进 pack**，但计入 `stale_excluded`，pack 末尾必须报出来；
- 与 `lineage` 的关系：lineage 管"导出是否还成立"，记忆图管"经验是否还可用"；两者都从同一批 sha256 出发，但目的不同，不能互相替代。

## 4. MemoryPack：预算、优先级、出处

### 4.1 阶段顺序（不是一套顺序）

```text
idea       : failures → contradictions → scope → datasets → recipes → claims → ideas
experiment : failures → contradictions → datasets → recipes → scope → claims
paper      : claims → failures → scope → recipes → contradictions
```

差异的原因：
- idea 阶段先看"过去怎么死的"，再谈新假设；
- experiment 阶段先看"数据坑与配方"，再谈设计；
- paper 阶段先看"已签 claim"，再谈写法。

### 4.2 硬规则

1. `failures` 与 `contradictions` **永不裁剪**；
2. 其他节按预算裁剪，并报 `dropped` 数；
3. 每行必须带 `src=path#sha12`；
4. 包尾必须报 `stale` / `pending` / 总长；
5. 包是"生成上下文"，**不是证据，不可引用**（写入 pack 的 `boundary`）。

### 4.3 focus：让包"关于这个任务"

给定 focus 节点（例如 `RUN-E2E-02-idea-IDEA-01`），与它相连的节点排前；finding 限定在该 run 前缀。没有 focus 时按 id 排序，保证确定性。

### 5.2 真实扫描（`runtime_data/e2e-closed-loop`）

命令：

```bash
python scripts/research_memory_scan.py --project runtime_data/e2e-closed-loop
```

实测输出：

```text
artifacts: 10 | nodes: 17 | edges: 3
  claim/admitted: 1
  closure/admitted: 1
  experiment/admitted: 2
  finding/admitted: 9
  idea/admitted: 1
  idea/pending: 3
pack[idea]: 2574/8000 chars | stale=0 pending=3 | sections=claims:1, contradictions:7, ideas:1, scope:3
pack[experiment]: 2245/8000 chars | stale=0 pending=3 | sections=claims:1, contradictions:7, scope:3
pack[paper]: 2245/8000 chars | stale=0 pending=3 | sections=claims:1, contradictions:7, scope:3
```

第二个项目（`runtime_data/topconf-research-2026`，宿主原生 run，只有 `task.json`）用来验证另一种产物形状：

```text
artifacts: 3 | nodes: 3 | edges: 0
  run/admitted: 3
pack[idea]: 876/8000 chars | stale=0 pending=0 | sections=scope:3
```

这说明两件事：扫描器不假设一种布局；以及"只有 run、没有 claim/failure"的项目，pack 只剩 scope——**这正是该补记忆的项目**（它没有任何可复用的失败或结论）。

**怎么读这些数**（避免自欺）：
- 17 节点说明**图是通的**，不是空壳；3 条边说明当前产物里显式关系很少（`experiment→idea`、`claim→run`），这本身就是发现：**大部分证据关系目前只存在于代码逻辑里，不在产物里**；
- 9 条 finding 全是 manuscript-audit 的 blocker（引用未核、证据缺失、fixture 不可引用）——它们第一次以"contradictions"身份进入 idea 阶段的包；
- 3 条 idea 是 pending，因为 status 不是 selected 或证据不足——这正是"可见不可用"；
- 没有 failure 节点：**当前产物里没有 durable 失败记录**，这是下一轮最该补的缺口（失败图谱）。

### 5.3 它改变了什么（具体动作）

| 之前 | 之后 |
| --- | --- |
| idea 阶段只读 `idea.json` 与文献 | 先读上一轮 paper blocker（引用/证据/fixture）与已签 claim scope |
| experiment 阶段只看 design card | 先读数据集卡与配方；失败节永远在最前 |
| 论文阶段从稿件开始 | 先读已签 claim 与 stale 状态，再决定哪些句子可写 |
| 失败 run 留在磁盘 | （下一步）以 durable `failure` 节点进入图，永不裁剪 |

## 6. 自改进闭环：Recipe（阶段配方）

### 6.1 Recipe 是什么

```json
{
  "recipe_id": "REC-idea-v1",
  "stage": "idea",
  "sections": ["failures", "contradictions", "scope", "datasets", "recipes", "claims"],
  "checks": ["grounding", "falsifiability", "testability", "prior_art_delta"],
  "thresholds": {"min_evidence": 1, "max_overlap": 0.8},
  "prompt_version": "idea-0.3",
  "heldout_passed": true,
  "human_reason": "two leakage failures showed that the prior-art check must run before drafting"
}
```

Recipe 是**数据**，不是代码：改配方不改模块；配方有 id、版本、证据、回滚点。

### 6.2 候选从哪来

只从 **durable 失败 + 复现结果**来（与 81 §8 一致）：

| 触发 | 改动层 | 例子 |
| --- | --- | --- |
| 同一 leakage 在两个项目复现 | recipe（idea/experiment） | 增加"去重 + 隐藏 fix diff"检查 |
| underpowered 连续出现 | recipe（experiment） | 预注册前强制功效计算 + 最小可检测效应 |
| paper blocker 反复是"引用未核" | recipe（paper） | 写作前先跑 bibliography verify |
| 复现失败但原 claim 未覆盖 | scope / recipe | 收窄 scope，或加"独立数据"检查 |

### 6.3 怎么评估（这是与现有 RSI 最大的差别）

| 维度 | 现在（rsi） | 本设计 |
| --- | --- | --- |
| 评估任务 | retrieval recall / S5 seed budget / harness 任务 | **held-out 研究任务**（未参与候选设计的真实研究问题） |
| 指标 | 代理指标 | 三轴指标（idea / experiment / paper），见 §7 |
| 判据 | public 排序 + hidden 门槛 | 预注册判据 + 区间 + 功效 + underpowered 守卫 |
| 采纳 | 人签 + 租约 | 人签 + 租约 + 回滚点 + 方法指纹 |
| 失败 | 记录 | 记入记忆图，驱动下一次候选 |

**held-out 研究任务从哪来**：三个来源，按成本排序：
1. 已有但未参与演化的历史 run（例如 `pipeline-chemlab`、`topconf-research-2026`），用其已知结局做金标准；
2. 仓库内的 fixture 任务（idea review 用例、writing 审计用例），只作机制检查，不作效果结论；
3. 新采集的小型真实任务（需要人工确认数据与伦理边界）。

### 6.4 采纳与回滚

- 采纳必须：held-out 无回归 + 至少一个正向 + 成本可接受 + 人写理由；
- 版本 + 回滚点 + **方法指纹**（覆盖 recipe 文件、prompt、检查清单，而不只是 `research_agent/**/*.py`）；
- 在途研究不被静默换版：项目记录采用的 recipe 版本。

### 6.5 与现有 RSI 的接线

现有 `rsi` 的 `SAFE_SCOPES` 可以扩一个 `recipe.<stage>`，候选类型从 retriever/budget 扩到 recipe 变更；准入证据从 public/hidden 扩到 held-out 研究任务。**门禁语义不变**：仍是人签 + 租约 + 撤销。

## 7. 三轴效果指标

### 7.1 idea 轴

| 指标 | 定义 | 现在能否测 | 数据来源 |
| --- | --- | --- | --- |
| grounding rate | 有至少一个真实 span 支撑的候选 / 全部候选 | 能（词法+引用检查） | `idea.json` evidence_refs |
| falsifiability | 有具体否证条件的候选 / 全部 | 能 | `falsification` 字段 |
| prior-art delta | 是否明确写出与最近先行工作的差异 | 能（字段非空） | `prior_art_delta` |
| 人工排序一致性 | 人排序 vs 系统排序的 Kendall τ | 需人 | G1 决策 |

### 7.2 experiment 轴

| 指标 | 定义 | 现在能否测 | 数据来源 |
| --- | --- | --- | --- |
| design completeness | design-audit pass 项 / 总项 | 能 | `design-audit.json` |
| pre-registration | 是否有冻结协议 + 停止规则 | 能 | `protocol.json` |
| power | 是否有功效计算且 n 达标 | 能（若记录） | study/experiment |
| claim assertion pass | 签署前重算通过的断言 / 总断言 | 能 | `claim.json` |

### 7.3 paper 轴

| 指标 | 定义 | 现在能否测 | 数据来源 |
| --- | --- | --- | --- |
| blocker count | manuscript-audit blockers | 能 | `manuscript-audit.json` |
| claim coverage | 已注册 claim / 应该引用的 claim | 能 | `claim-registry.json` |
| numeric provenance | 每个数值是否可追到 EA/claim | 能 | audit + claim |
| 引用核验率 | verified 引用 / 全部引用 | 能 | bibliography |

### 7.4 反指标（必须同时报）

- 点估计绕过区间门的次数（应为 0）；
- stale 建议被采纳的次数（应为 0）；
- 人签分钟数（不能被自动化转嫁）；
- 每个 claim 的审阅/复核成本。

**纪律**：能力指标没测出来之前，页面与论文只允许写"机制已接入"，不允许写"更好/更强"。

## 8. 与同目录其他科研智能体工作的差异

| 工作 | 它强在 | 与我们的差异 |
| --- | --- | --- |
| **MathRSI**（`math-rsi-main/`） | 五阶段 + 领域插件 + 单题 wiki + 独立 meta-evolve；证明/证书做终审 | 我们是 ESE 语义：无证明 oracle，三轴 + 统计 + 复现；记忆要跨项目 |
| **SciForge-OSS** | skill 库 + 代码强制控制环 + RSI 层；每阶段 verdict 文件（leakage audit 等） | 它的 verdict 是阶段门；我们把 verdict 变成**记忆图上的节点与边**，并让失败进入配方 |
| **IdeaScientist** | grounded ideation 编排、idea 数据集 | 它优化"生成"，我们优化"生成之后能不能被证据与记忆约束" |
| **TTME** | test-time memory evolution 的对照实验 | 它研究"记忆演化 vs 测试时训练"；我们做"记忆准入 + 过期 + 配方"，可直接复用其对照方法 |
| **FlashRSI** | 13 个 RSI 算法统一接口、31 benchmark | 它演化 harness/skill；我们演化研究配方，用研究任务评估 |
| **Harness²** | 递归自改进的预算恒等式与留出任务 | 我们把它当执行引擎，判据与人签留在平台 |
| **Cortex** | 长任务工作台、多机、文件持久 | 工程可借鉴；科研语义（证据/判定）不同 |

**一句话差异**：别人优化"生成 / 技能 / harness"；我们优化**"研究记忆 → 研究配方 → 研究产出"**这条链，并且要求每一步都能溯源、会过期、可回滚。

## 9. 创新点（可证伪）

1. **类型化研究记忆图**（12 类节点 / 9 类关系 / 准入 / 哈希过期 / 预算 pack）。
   *证伪*：如果 pack 相对"直接把全部 JSON 塞进上下文"没有更好的三轴指标，或准入/过期规则从不触发，则该主张不成立。
2. **失败驱动的配方演化**（durable 失败 → recipe 候选 → held-out 研究任务 → 人签 + 回滚）。
   *证伪*：如果 held-out 任务上配方改动无正向、或与随机改动无法区分，则该主张不成立。
3. **证据链原生**（节点带 source+sha256，边带"改变了哪一步"，与 claim/EA/lineage 同源）。
   *证伪*：如果多数节点无法从产物重建，或 stale 传播与 lineage 判定不一致，则该主张不成立。

三条都写成"什么情况下算失败"，便于论文里如实报告。
