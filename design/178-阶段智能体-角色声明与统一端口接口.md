# 阶段智能体：把 AgentRole 变成元模型声明，而不是 pipeline 里的 if/else

**状态基线（2026-11-22）**：承接 design/177（元模型驱动编排）。用户问：
"能不能对不同阶段做不同的智能体，让它们通过输入输出交互？"

答案是：**我们本来就已经是"每阶段一个 agent"，但它不是可寻址的角色，而是被 `pipeline` 用
if/else 硬编码串起来的；接口还不统一（`RunAgent.execute` vs 其他 `run`）。** 本文把这一层显式化。

---

## 1. 核查：现状离"角色化"有多远

| 问题 | 核查结果 | 证据 |
|---|---|---|
| 是否已有阶段 agent？ | **是**，7 个：literature / idea / experiment / run / figure / paper / grant | `research_agent/modules/*.py` 的 `*Agent` 类 |
| 角色是否声明为数据？ | **否**。`_agent(module_id)` 里一张字典硬编码 if/else | `pipeline.py:233-244` |
| 接口是否统一？ | **否**。`LiteratureAgent.run()`、`RunAgent.execute()`、`PaperAgent.run()` | 各 `*Agent` 类 |
| 输入输出是否成契约？ | **半**。各 agent 有自己的 Request/Result dataclass，但没有声明"这是该阶段的端口" | `contracts.py` / 模块内 Request 类 |
| "谁执行"与"谁签"是否分开？ | **否**。契约里只有一个 `human: bool`，无法表达"agent 生成 + 人签确认" | `process_orchestration.py` §177 |
| AgentRole 是否是元模型元素？ | **否**。registry 的 elements 只有端口，没有角色 | `registry.json` elements |

所以用户的问题不是"要不要做"，而是**"把已经存在的东西显式成元模型"**。

---

## 2. 设计：角色绑在 (stage, role)，不是 element

一个 element 可能对应多个角色：**「证据」在 S1 是 literature-researcher，在 S5 是 experiment-runner**。
所以角色不能挂在 element 上，必须挂在治理阶段上。

### 2.1 角色声明（`stage-roles.json`）

每个阶段一行，四个关键字段拆开了原来混在一起的语义：

| 字段 | 回答 | 例 |
|---|---|---|
| `role` | 谁 | `experiment-designer` |
| `executor` | 是 agent 还是人 | `agent / human / hybrid` |
| `module` | 用哪个实现 | `experiment`（human 时为空） |
| `human_sign` | 哪道门签 | `G2`（无签为空） |
| `interface` | 用什么接口 | `run / execute / check / sign / propose` |

这张表让三种此前无法表达的形态变得可声明：

- **agent + 人签**：S2-S3 假设由 `idea` agent 生成，选哪个由 G1 签；
- **纯人签无 agent**：S5b 判定只有 `claim-signer`，`module` 为空，`interface=sign`；
- **agent + 强制门**：S8-S12 由 `paper` agent 写，导出由 G5 签。

### 2.2 统一端口接口

```python
class StageAgent(Protocol):
    module_id: str
    def run(self, request) -> result: ...
```

`as_stage_agent()` 把 `RunAgent.execute()` 这类专用方法适配成统一 `run()`；
`assert_bindable(role, agent)` 按声明的 module/interface 校验，**人签阶段直接拒绝绑 agent**。

这不是"多智能体自由对话"（actor model / message passing），而是**数据流 + 编排器**：
每个阶段 agent 是"输入端口 → 输出端口"的纯步骤，编排器按 177 的拓扑序调用、按契约校验产物。
理由：科研流程的可审计性要求"谁在什么时候拿到什么、产出什么"必须可追溯，
自由对话的消息传递会把这条链打散。老师的框架也把 Role 绑定在 Activity 上，而不是让 agent 互相聊天。

---

## 3. 治理不变量（fail-closed，不是配置）

1. 每个治理阶段必须有且仅有一个角色；缺一个就拒绝加载。
2. `executor=human` 时不得绑定 module；`executor=agent/hybrid` 时必须绑定真实存在的 module。
3. `interface` / `executor` / `human_sign` 都来自封闭词表。
4. **S5b 必须是 human 且无 module**——即使有人改数据，也不允许把 claim 签署变成 agent 行为。
5. `binding_for()` 拒绝"给 agent 配 sign 接口"或"给人签阶段配 agent"。

第 4 条是本轮最重要的：它把"agent 不得代签 claim"从一句口号变成**加载期就会失败的校验**。

## 4. 实测结果

`controlled-experiment` 的契约（已并入角色）：

| 阶段 | 要素 | 角色 | 执行 | 签核 | 实现模块 |
|---|---|---|---|---|---|
| S0 | 问题 | problem-framing | agent | Q0 | task-agent |
| S2-S3 | 假设 | hypothesis-designer | agent | G1 | idea |
| S4 | 方案 | experiment-designer | agent | G2 | experiment |
| S1 | 证据 | literature-researcher | agent | — | literature |
| S5 | 证据 | experiment-runner | agent | — | run |
| S5b | 判定 | claim-signer | **human** | S5b | **无** |
| S6 | 图表 | figure-renderer | agent | — | figure |
| S8-S12 | 写作 | paper-writer | agent | G5 | paper |
| S13-S16 | 闭包 | closure-checker | agent | G5 | closure |

前端「编排契约」块现在每行显示：阶段 → 要素 → 角色 → 执行者（agent / agent+人签 / 人）→ 签核门 → 实现模块 → 输入输出 → 任务。
截图确认布局无重叠。

测试 14 例：角色覆盖完整、模块存在性、人签不绑 module、S5b 不可转 agent、
缺失阶段拒绝、未知接口拒绝、run/execute 适配、sign 不可委派、契合并入不丢字段、纯函数。

---

## 5. 边界

- 本文**不重构** `pipeline.py` 的调用方式（仍用 `_agent(module_id)`）；统一接口已就绪，
  但让编排器完全按契约寻址仍需拆 `run()`（与 174 §5 同一工程）。
- 角色是**单执行者**模型；老师的框架允许一个 Activity 多个 Role（如"实验设计"由设计者 + 统计师），
  当前未建模多角色协作。这是明确的 roadmap，不假装已支持。
- 不是 actor model：agent 之间不直接发消息，产物通过编排器按端口传递——为了可审计。
