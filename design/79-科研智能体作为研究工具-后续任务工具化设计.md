# 79-科研智能体作为研究工具：后续任务的工具化设计

> 状态基线：2026-11-16。触发：用户转向——"我希望咱们的科研智能体服务于这个研究"。本文反思"对象 vs 工具"错位，并把后续论文任务设计为**经系统受治理管线执行**，学生签核、agent 执行。承接 78（导师方法论矩阵）。

## 1. 反思：对象与工具的错位

**之前我把系统当"研究对象"（论文研究它），用户要的是它当"研究工具"（用它做论文）。** 更具体的错位：这几天的论文工作是在对话里直接干的，**没走系统的受治理管线**——

| 本该走管线 | 实际怎么干的 | 后果 |
| --- | --- | --- |
| 反思文档经 writing pack→audit | 我直接写 76/77/78 文件 | 不是治理产物，无审计链 |
| FlashRSI 经 experiment approve→run→ingest→claim | 直跑 CLI | 真实 run 但没成为 signed claim |
| 文献经 literature run→synthesize（SLR） | 设计文档里罗列 | 有覆盖无协议、无 Span 证据 |
| 真实闭环经 S5b/G5 人签 | 挂着没签 | topconf claims/closure 至今为空 |

**根因判断**：模块测试绿，但系统**没当过任何一次真实研究的工具**。75 的三缺口（人签质量/反馈效果/独立验证）正是这个错位的症状——不是机制不行，是机制没被真实研究驱动过。

**用户要求的深层价值**：让系统服务自身论文研究 = **自反案例研究（reflexive case study）**，这是最强验证——论文既是系统的报告，又是系统的产物。任务书(3)要求的"完整闭环案例"可以**就是论文研究本身**。

## 2. 设计原则

1. **每个论文任务走受治理管线**：任务→模块/命令→人工门→治理产物（claim/evidence/lineage）→论文章节。
2. **角色固定**：学生=签核者（G1/G2/S5b/G5），导师=第二签核者，agent=执行工具。agent 不签核（边界不变）。
3. **产物双重身份**：既是研究证据（可复核/可撤销），又是论文素材（喂章节）。
4. **负结果同样是产物**：not_supported/underpowered 如实签署入链，论文如实报告（任务书要求）。

## 4. 第一条真实端到端 loop（把论文核心实验跑成 signed loop）

**推荐核心实证问题：反馈约束是否改善生成质量**——`memory ab`（guideline 块配对 A/B）已建、M2 方法学现成、RUN-M2-MULTI 骨架在（experiment.json/design-audit/evidence-packages 齐全），最 turnkey。

驱动步骤（一条 loop 解五个缺口）：
```
S1  literature（8篇SLR，冻结语料）→ Span 证据
S2  idea（研究问题卡：反馈约束效应）→ G1 学生选
S4  experiment scaffold + protocol freeze-design → G2 学生批（预注册判据）
S5  memory ab with/without → RunCapsule/EA（含 underpowered 守卫）
S5b experiment claim → 学生签 + 导师二签（方向如实，负结果也签）
S13 closure check + lineage build/verify
S8  writing pack → 第6章草稿（只引 signed claim，数值受保护）
```
**一石五鸟**：① 真实闭环人签（指标6/任务3 转完整）② 反馈效果测量（75 §3.3）③ 写作闭环真实使用（78 自反证据）④ 导师二签缓解单人签核（75 §3.2）⑤ 完整闭环案例=论文研究本身（任务书3）。

**诚实注**：M2 单会话 n=3 曾 underpowered；本 loop 不保证正效应，目标是**产出可签署的诚实判定**（含 not_supported/underpowered），论文如实报告。自反案例的效度威胁=研究者即开发者（行动研究偏差），以预注册+第二签核+审计单调缓解。

**第二选择**：受治理准入是否改善自改进产出 → localqa 难题池（76），需先注册 flashrsi 面（§5）。建议作为 Phase 3 的第二个实验。

## 5. 需要的 glue（诚实缺口，最小修改）

1. **exec-port flashrsi 面注册**：改 `modules/exec-port/SPEC.md`→最小 diff→测试，让 FlashRSI/localqa 成为 experiment 引擎而非独立 demo（今日直跑绕过了 dispatch 记账，76 §5①）。
2. **SLR 协议形式化**：literature 模块跑冻结 CC-BY 语料/真实检索 + Kitchenham 协议（研究问题/纳入排除/质量评估），S1 从 fixture_mode 走向 real。
3. **翻译作为受治理生成任务**：无专门翻译命令，用 host-model turn + 引用保护审计契约承载（≥3000 字，Levels of Autonomy，78 §6）。
4. **论文级写作聚合**：writing pack 面向单 run；45 页论文需多 run 证据聚合 + 章节级 revision。写作闭环已建，规模需多包聚合（不新造机制）。

## 6. 进度对齐（接 78 §5）

- **Phase 1（现在）**：启动第一条 loop（memory ab→signed claim）+ SLR 协议 + 外文翻译 + flashrsi 面注册。
- **Phase 2**：开题报告（届时已有 signed 初步结果→证据型开题）。
- **Phase 3**：第二个实验（localqa 难题池效应，flashrsi 面）+ 详细设计对齐接口章。
- **Phase 4**：论文 50% 经写作闭环产出 + 中期报告 + 保 1487 绿。
- **Phase 5**：完整案例=这条自反 loop 打包（signed claim+capsule+lineage+复跑命令）+ 论文≥45 页 + 答辩。

## 7. 结论

系统服务自身论文研究是最强案例（自反）。后续每个论文任务走受治理管线、学生在门禁、产物双身份（证据+论文素材）。**第一条 loop 推荐 memory ab 到 signed claim，一石五鸟解五个缺口**；glue 四处如实登记、最小修改。这一步把 75 的"测量缺口"、77 的"人签缺口"、78 的"写作闭环"收束到同一条真实研究 loop 上——系统终于当自己论文的工具。
