# 102-用科研智能体探索 ESE：从问题到反思的一次完整运行

> 状态基线：2026-11-18。承接 99/100/101。
> 本轮不是"加模式"，而是让**智能体自己走完一次 ESE 探索**：SE 问题 → SE 文献 → 候选 idea → 方法合规协议 → 真实执行 → 反思与下一问。
> 边界：产物到"探索性结果 + 研究 note"；没有 Claim/EA/签名，没有 G2/S5b 人签。

---

## 1. 智能体这次实际做了什么

一条命令：

```bash
python scripts/ese_explore.py \
  --question "Do bug-fix commits touch tests more often than other commits in Python open-source projects?" \
  --corpus-dir runtime_data/se-corpus/pdfs \
  --repos runtime_data/msr-corpus/click,runtime_data/msr-corpus/requests,runtime_data/msr-corpus/httpx \
  --output-dir runtime_data/ese-explore-20261118
```

内部四步（全部由系统执行）：

1. **S1-S4**：用真实 arXiv cs.SE 语料（8 篇 flaky-test 论文，6198 span）跑 pipeline，生成 grounded 候选与 S4 设计；
2. **协议起草**：从 idea/experiment 产物生成八字段齐全的 repository-mining 协议（sampling_frame / project_selection / time_window / time_split / dedup_policy / label_source / license_check / extraction_script）；
3. **执行**：`ese_exec` 对 click / requests / httpx 的完整 git 历史做提取、Wilson 区间、置换检验；
4. **反思与写作**：生成 `note.md`，写明结果、不支持的结论、下一问。

产物：`runtime_data/ese-explore-20261118/{pipeline/,protocol.json,result.json,result.md,note.md}`。

---

## 2. 智能体给出的候选（S2，真实模型 + SE 文献）

1. **Bug-fix commits and test-file touch frequency in Python projects with flaky-test exposure**（mechanism）
2. **Flaky-test context as a boundary condition for test-touching bug fixes**（boundary）
3. **Commit-size and test-only changes as measurement confounds**（measurement）

三条都带 evidence_ref（可解析到 S1 的 8 篇 SE 论文 span），且 falsification 明确；其中第 3 条自己提出了"差异可能是提交大小/测试重构造成的度量假象"——这正是反思该有的样子。

---

## 3. S4 设计（真实模型草稿）

- hypothesis：bug-fix 提交比非 bug-fix 更可能改测试；
- baseline：同项目的非 bug-fix 提交；
- primary_metric：bug-fix 与非 bug-fix 改测试比例的差值；
- controls：项目、时间、提交大小、作者、是否同时改生产代码；
- status：`needs_human`（未 G2）。

---

## 4. 真实执行结果

| 仓库 | 源码提交 | 同改测试 | 比率 | 95% CI |
| --- | --- | --- | --- | --- |
| click | 1328 | 588 | 0.443 | [0.416, 0.470] |
| requests | 2824 | 760 | 0.269 | [0.253, 0.286] |
| httpx | 980 | 576 | 0.588 | [0.557, 0.618] |

- 合并：**1924/5132 = 37.5%**，95% CI [36.2%, 38.8%]；
- bug-fix **41.4%**（352/851）vs 其他 **36.7%**（1572/4281），差 **+4.6pp**，置换检验 **p=0.015**；
- 时间切分：早期 30.9% → 晚期 44.1%，差 +13.2pp，p=0.001。

## 5. 智能体的反思（note.md 第 6 节，原文）

- RQ1/RQ2/RQ3 的读数与区间；
- **不支持的结论**：因果、跨语言泛化、关于个体开发者的任何陈述；
- **标签是启发式**（路径 + 提交消息），误分类未量化；
- **下一问**："does the observed bug-fix difference survive when controlling for commit size and repository (stratified analysis)?"

这句话把本轮结果直接变成下一轮的可执行问题——这就是"探索"而不是"跑一次"。

---

## 6. 这次探索证明了什么 / 没证明什么

**证明**：

1. 智能体可以把一个 SE 问题落成真实的 repository-mining 研究：文献 → 候选 → 设计 → 协议 → 执行 → 反思；
2. 协议八字段齐全，方法检查可通过；
3. 执行结果有区间与检验，不是"看起来合理"的叙述；
4. 反思能指出自身威胁并提出下一问。

**没证明**：

1. 不是可签署结论：没有 G2 冻结、没有 RunCapsule/EA、没有 S5b 人签、没有独立复现；
2. 三仓库是目的性抽样，不能外推；标签启发式会误分类；
3. 候选/协议字段由模型起草，人工未审；
4. 没有与基线方法（例如人工仓库分析）做对照。

## 7. 下一步：把探索接进门的后半段

| 步骤 | 动作 |
| --- | --- |
| 1 | 把 `protocol.json` 登记为 S4 设计，人签 G2（冻结协议） |
| 2 | 执行器产出 EA 兼容结果胶囊（run-capsule/ea），或经 `experiment` 链接入 |
| 3 | 人签 S5b Claim → closure/lineage → 写作包与预审 |
| 4 | 按"下一问"跑第二轮（控制提交大小与项目的分层分析） |

**一句话**：智能体现在能自己把一条 ESE 研究从问题推到"有区间、有反思、有下一问"的探索性结果；距离可签署的论文结论，还差人签与独立复现这两道门。
