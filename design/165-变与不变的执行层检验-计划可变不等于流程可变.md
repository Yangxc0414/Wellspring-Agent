# 变与不变的执行层检验——计划可变不等于流程可变

> 状态基线：2026-11-21。承接 162（组合驱动计划）、163（五维三列控制表）、164（pipeline 组合解析 advisory 层）与研讨纪要的原始直觉。
> 本文不新增功能，只回答一个问题：**我们把"变"放到了哪一层，它有没有真的到达行为层。**

---

## 0. 一句话结论

研讨纪要说得很准：**聊天窗口可以不变，内部智能体的逻辑要随任务改变**——不同的研究内容应该引出不同的思考方式与实验方式，而不是同一条固定流程换一批文案。

目前的进展是：这套"变"已经进了**数据层**（方法注册表、组合接线、阶段计划）和**可读层**（方法详情卡、控制表、事件流），但还没进**执行层**——`pipeline.py` 的阶段块仍全部执行，`stage_skip` 只是事件，不是跳过。

所以现在的诚实表述是：**计划可变，流程未变。**

---

## 1. 把用户的直觉拆成四种"变"

"不同任务不同流程"这句话里其实混了四件事，它们的变化成本完全不同：

| 变的东西 | 例子 | 当前落点 | 控制者 |
|---|---|---|---|
| **研究内容** | 主题、语料、数据、本次断言 | 任务实例（L1） | runtime |
| **研究阶段** | 这条任务实际走到哪些槽位 | 组合 slot_map → 计划（L2） | 注册表数据 |
| **研究方法** | SLR / 仓库挖掘 / 准实验 / ML 迭代 | 方法对象（fit / 协议字段 / 检查 / 标签） | 注册表数据（L2） |
| **过程逻辑** | 这些阶段**按什么顺序、是否真的执行** | ⚠️ 仍硬编码在 `pipeline.py` | 代码（L3 未声明为可变） |

前三项已经有表示：方法模型页能看到十方法各自的阶段计划（SLR 是验证式 `S0→S1→S1b→S8–S12`，仓库挖掘是探索式 `S1→S4→S5→S5b`）。第四项没有——两种方法的计划不同，但跑起来经过的阶段块一样。

这正是“聊天窗口不变、内部逻辑也不变”的风险：**界面上看起来可变，行为上没变。**

---

## 2. 164 到底做了什么，没做什么

本轮（design/164）的改动有三部分：

1. `PipelineRequest.method_id`：把方法绑定传进执行器；
2. `pipeline_stage_plan()`：把组合的槽位计划投影成 pipeline 阶段名集合（SLR → `literature, paper`；仓库挖掘 → `experiment, literature, run`）；
3. `stage_skip` 事件 + `modules["composition_plan"]`：把"这个方法本该跳过哪些阶段"写进事件链和产物。

**做到的**：变化从数据层推到了**事件层**，可被审计、可被截图、可在组会上指给人看。

**没做到的**：这些事件后面的代码块照常执行。文档自己写明了"完整跳过执行块仍为 SPEC 先行 roadmap"——这是诚实的，但标题叫"组合驱动执行器"稍微越界：**它现在是一个组合驱动的计划投影器，不是执行器。**

另外一个必须纠正的词：164 草稿原写"fail-closed：解析失败回退全阶段"。回退不阻断是 **fail-open**；注册表加载校验才是 fail-closed。两者混用会让"我们的门禁是严格的"这种话失去精确含义。已改。

## 3. 为什么"真跳过"不能只是加几个 if

看起来只要在四个阶段块外面套 `if stage in covered` 就够了。上次这么改破坏了 `pipeline.py` 的缩进，回退后才改用事件层——但真正的原因不是缩进，而是**跳过的语义没有定义**：

- **证据悬空**：`paper` 阶段从 `run` 阶段取 claim/EA。如果某方法不该走 `run`（例如调查方法产出应答集而非 RunCapsule），跳过 `run` 之后 `paper` 该绑定什么？这正好回到 163 的发现——**治理要求（可固定/可复算/可核查）不变，证据形态随方法变**。跳过一个阶段，必须同时提供它的证据替代形态，否则写作槽位会去绑定不存在的产物。
- **门依赖**：G5 的 closure 核对四件产物。探索式路径假设后置（先证据后假设），那 G1 的门位置是否还一样？163 的控制表说"槽位语义与门位置固定"——如果执行顺序变了而门位置不变，是顺序绕过了门还是门约束了顺序？这需要在 SPEC 里说死，不能在代码里临场决定。
- **负结果可审计**：跳过的阶段必须在事件链上留下"为什么没走"，而不是简单地没有事件。`stage_skip` 事件是这一步的正确起点。

所以"真跳过"的前提是**证据形态多态 + 门依赖显式化**，两者都是规格问题，不是控制流问题。这也是 PROGRESS 把"组合驱动执行器"列为依赖"后端 SPEC 先行"的原因。

## 4. 一个可证伪的判据

要判断"变与不变"是否真正落地，不要看控制表画得多清楚，看这两条：

> **判据 A（行为差异）**：同一份研究内容、两个不同方法跑一遍，事件流里的**阶段序列必须不同**，且差异能被 `composition_plan` 解释。计划卡不同但事件流相同 → 不算做到。

> **判据 B（无悬空引用）**：被跳过的阶段不得在后续产物里留下空绑定；如果某方法没有 `run`，它的写作/断言阶段必须绑定到该方法声明的证据形态（163 的 `artifactForm`），而不是 null。

这两条都能写成测试，也都能在组会上现场演示：切两个方法 → 事件流不同 → 产物里每个引用都有目标。

## 5. 变与不变的最终表述

综合 152/154/162/163/164，控制关系可以压成一张表：

| 层 | 不变 | 可变 | 变更路径 |
|---|---|---|---|
| **L3 治理语义** | 九槽位与五门、证据三元组、EA 不可变、closure/lineage、claim 人签 | 无（这一层故意不可变） | 代码 + SPEC + 人签 |
| **L2 方法数据** | 注册表 schema 与 fail-closed 校验 | 方法 fit、协议字段、检查、标签、组合接线、证据形态 | 组合提案租约（仍 roadmap） |
| **L1 任务实例** | 治理门的控制权 | 主题、语料、实际走过的槽位、本次断言 | runtime 产生，只读投影 |
| **交互外壳** | 聊天窗口、侧栏、面板结构 | 展示内容随 L1/L2 变 | 前端渲染 |

**关键**：交互外壳的不变是为了让观众不被界面变化干扰；内部逻辑的变必须发生在 L1/L2，并且最终要体现在**事件流**里。L3 不变不是保守，而是让"可变"有可复核的边界——没有固定的尺子，就无法说清什么真的变了。

## 6. 对工作方法本身的反思

这轮收尾时发现的三个问题，都指向同一条纪律的松懈：

1. **重号**：中断的会话留下一份 `design/163-组合驱动执行器…`，与已上线的 `design/163-变与不变控制表…` 撞号，`docs_audit` 当场变红。现改为 164。教训：`docs_audit` 只校验计数，**不校验目录唯一性**；重号会被它放过吗？不会——这次就是它报的。但计数和索引是由人手工改的，漏一次就会出现 PROGRESS 说 164 份、实际 165 份。
2. **术语**：advisory 回退被写成 fail-closed。一句话里的术语错位，比漏一个字段更危险，因为它会污染后续所有"我们很严格"的论证。
3. **Changelog 串台**：164 草稿把 153/155/162 的测试与校验写成本轮改动。复盘时无法判断哪些是这一轮真正做的，可证伪性就没了。

对应动作：本轮已按"一次改动一篇反思"补齐 164，并给新增函数补了五例测试；但**索引与计数仍需逐轮人工同步**，这一点应做成脚本检查，而不是靠记性。

---

## 7. 边界与下一步

- 164 是**advisory 事件层**，不承诺行为变化；PROGRESS 的差距 #1 仍为未完成，只是从"完全没做"变成"可观测层已做"。
- 真正的执行器迁移需要先在 SPEC 里定义：跳过阶段的事件语义、证据形态替代规则、门依赖不随顺序漂移的证明。
- 组合提案租约（L2 的修订权）仍依赖执行器迁移——**先把流程变成可执行的变量，再开放修改它的权限**，顺序不能反。

一句话收尾：

> **不变的是尺子，变的是被量的东西；如果尺子下面的行为没动，那只是把标签换了。**
