# 执行流程必须对应研究方法：把 RESEARCH FLOW 从"一条通用流水线"改成"方法编排 + 治理固定 + 计划外"

**状态基线（2026-11-21）**：承接 design/164（组合驱动计划）、165（计划可变不等于流程可变）、
166（效力类型）、167（效力模型落地）、168（研究内容→方法推荐）。本文改**前端 RESEARCH FLOW 的
数据来源与呈现结构**，不改注册表契约、不改执行器、不改门禁语义，也不产生任何 Claim。

一句话：**面板原来只有一条轴（会话标签），十条方法共用同一张图；这条轴必须换成"这条任务声明的
方法 → 它的组合接线 → 阶段顺序与每阶段任务"，并把与会话实际路径的差异显式摆出来。**

---

## 1. 问题不是"样式"，是"数据源错了"

截图里的 RESEARCH FLOW 是 ESE 会话，9 个节点：S1 → S2–S3 → S4 → S5a → S5b → S6 → S8–S12 →
S13–S16 → META。它看起来很完整，但它回答不了导师会问的那句话：

> 这条任务的执行流程，跟你说的"不同方法不同阶段"，对得上吗？

对不上，而且不是显示层没写清楚，是**取数根本没用方法**：

| 事实 | 证据 |
|---|---|
| 面板的阶段列表来自 `demoStagePlan(messages)`：会话里出现过的 stage 标签去重 | `FlowDemo.tsx` 会话路径分支 |
| 方法注册表早就解析出了每方法的阶段顺序 | `method_registry.stage_plan` / `pipeline_stage_plan`（164） |
| 前端也早就有同一份投影 | `methodModel.stagePlanFor`（162），当时只用于推荐卡的 plan 摘要 |
| 真实 run 已经把用过的组合写进产物 | `pipeline.py` → `modules["composition_plan"]["method"]`（164） |

也就是说：**数据已经存在，只是 RESEARCH FLOW 没接。** 于是十条方法在同一个面板里长得一模一样，
"探索式先定方案再收集证据、假设事后归纳"这个最关键的方法差异，在演示里完全看不见。

### 1.1 一个必须说出来的发现

把 ESE 会话（`methodId = repository-mining`，探索式组合）喂给 `buildMethodFlow` 之后，面板给出的
计划顺序是：

```
计划（探索式）：S4 实验/研究设计 → S1 多源检索 → S5 执行与证据 → S5b Claim 草稿与签核
会话实际：      S1 语料组装     → S2–S3 断言收敛 → S4 冻结分析协议 → S5a 执行 → S5b 判定
```

两处不一致：
1. **S1 在 S4 之前**：探索式接线是「方案消费研究问题（先定抽样与时间切分）→ 证据」，会话却是先组语料；
2. **S2–S3 在 S4 之前**：会话是"先有断言、再冻结协议"，这正是**验证式**的形状（假设先于设计），
   而 `repository-mining` 绑的是**探索式**组合。

这不是面板 bug，是**注册表绑定与真实叙事之间的真实矛盾**。面板不替人裁决哪个对，只负责把它摆在
台面上。两个可能的解释都必须由人确认：

- 读法 A：挖掘研究实际上是"先有可检验断言、再做分层协议"→ 方法绑定应改为 `controlled-experiment`
  或为该研究方式新增一个"回顾性观察 + 预注册分析"的组合；
- 读法 B：方法绑定正确，是这条会话的叙事顺序按执行器固定链写的（S1→…→S16），没有按探索式重排
  → 属于 design/165 那条待改的执行层。

在写这份文档时，**没有改绑定，也没有改叙事**。原因是：两种读法对应的证据不同（一个是方法学判断，
一个是执行层实现），任何一边都需要人拍板；面板的职责到"显式呈现差异"为止。

## 2. 三条轨道：把"变 / 不变 / 现实"分开

一个新面板如果只是把会话标签换成计划标签，会立刻产生第二个误导：**好像执行器已经按方法剪裁过**。
所以展示结构必须三分，且三段的语义各自独立：

| 轨道 | 内容 | 为什么必须单独一段 | 数据源 |
|---|---|---|---|
| ① 方法声明编排 | 该方法的组合接线走到的槽位，按接线顺序；每步带 `stage_tasks[slot]`（这一步该做什么）与 `wiring[].rationale`（为什么排在这里） | 这是**随方法变**的部分，也是"不同方法不同阶段"唯一站得住的证据 | `stagePlanFor(method, registry)` |
| ② 治理固定 | 闭包与签核（S13-S16）、经验与自改进（META） | 它们不在任何方法的 `fit_stages` 里，所有方法都走——属于**不变层**。混进①会把"治理"说成"方法选择" | 会话标签中提到且属于 `GOVERNANCE_STAGES` 的阶段 |
| ③ 计划外 | 会话实际走过、但既不在①也不在②的阶段 | 执行器当前仍全阶段执行（165）。把它删掉=假装流程已剪裁；把它混进①=把执行器行为说成方法编排 | 会话标签差集 |

轨道②的判定是硬编码的 `GOVERNANCE_STAGES = {"S13-S16", "META"}`，不是从数据里猜的。依据：
`registry.methods[*].fit_stages` 里**没有任何一个方法**包含 S13-S16；META 连槽位都没有
（`slot_map` 只有 问题/假设/方案/证据/判定/图表/写作/闭包 八项）。这两条是治理层事实，不是方法差异。

## 3. 顺序差异要显式化，不能只列两个列表

只把计划列表和会话列表并排，读者仍要自己做序列比对。面板直接算第一处分歧：

```ts
// stagePlan.ts buildMethodFlow
actual   = 会话标签按出现顺序映射到槽位、去重、只留计划内
expected = 计划顺序中实际出现过的槽位
orderMismatch = 第一个 actual[i] !== expected[i] 的位置
```

ESE 得到 `at = 0`，提示条写：

> 顺序与计划不一致：计划 `S4 → S1 → S5 → S5b`；会话 `S1 → S4 → S5 → S5b`。

控制组（`controlled-experiment`，验证式）在 full-chain 会话上得到 `orderMismatch = null`，提示条
变成「✓ 在会话已走的阶段上，顺序与计划一致」。两条会话放在一起演示，方法差异和实现差距同时可见——
这比任何一句"我们支持多方法"都有说服力。

**注意用词**：一致时只说"在会话已走的阶段上"，不说"流程完全符合计划"——因为计划外的阶段仍然存在
（full-chain 的 S1、S6 就在③里）。这是刻意留的口径，避免把"顺序对"读成"编排已执行"。

## 4. 取数与归一化：不新增契约

### 4.1 方法 id 现在挂在任务上

`ResearchTask.methodId?: string`（类型层新增）。三个有 stage 标签的种子会话显式声明：

| 会话 | methodId | 组合 |
|---|---|---|
| `ese-ms-20261118-03` | `repository-mining` | 探索式 |
| `e2e-closed-loop` | `controlled-experiment` | 验证式 |
| `full-chain-demo` | `controlled-experiment` | 验证式 |

`methodModel.SESSION_METHOD` 保留为**兜底表**，理由写在代码注释里：本地持久化的旧工作区快照写于
该字段存在之前，不兜底会让用户刷新后突然退回通用模板。新任务不再登记到这张表。

真实 runtime 任务不靠这张表：`applyRuntimeSnapshot` 从 `modules.composition_plan.method` 读
（`--method auto` 时再退到 `modules.method_selection.proposed`）。两处都是 pipeline 已经写进产物的
字段，前端只读，不推断。

### 4.2 两套阶段写法的归一化

注册表槽位写 `S2-S3`、`S5`；会话标签写 `S2–S3`（en dash）、`S5a`（执行）。归一化规则集中在
`stagePlan.ts`：

- `normalizeStageId`：`–`/`—`/`−` → `-`；
- `slotForStage`：先查注册表目录，再查别名 `S5a → S5`；查不到返回 `null`（META 与未来新增阶段都走这条，
  面板显示「注册表未映射」而不是猜一个槽位）；
- `slotCommand`：从 `AUTO_STAGE_CATALOG` 反查命令；S5 槽位复用 `run.work`；`S1b` 没有命令就**不显示**命令行；
- `contractKeyFor`：S5 → `S5a`，其余把连字符换回 en dash；查不到契约就不显示契约块。

这四条都有单测（`tests/stagePlan.test.ts`），因为这一层最容易"看起来对、其实是猜的"。

## 5. 面板上真正新增的东西

```
研究编排 · METHOD PLAN
  研究方法 软件仓库挖掘 / Mining Software Repositories
  探索式组合 · 停止规则 · 固定阶段
  证据在前：方案只消费问题（数据收集设计），假设从证据中提炼

⚠ 顺序与计划不一致
  计划 S4 → S1 → S5 → S5b；会话 S1 → S4 → S5 → S5b。

RESEARCH FLOW                                METHOD PLAN · 4 + 2 治理
① 方法声明编排   顺序来自组合接线，不是通用模板
  S4  实验/研究设计   3 条  G2        ← 本方法任务：时间切分必须先于建模…
  S1  多源检索与全文阅读 2 条          ← 本方法任务：确定抽样框…
  S5  执行与证据      4 条
  S5b Claim 草稿与签核 2 条 人签
② 治理固定       不随方法变：闭包与经验回流对所有方法一致
  S13-S16 闭包与签核  治理固定 G5
  META 自改进提案     治理固定
③ 会话还走了 3 个计划外阶段（折叠）
  S2–S3 假设收敛 / S6 结果图 / S8–S12 写作槽位   各标「本方法未声明」
```

每个计划节点展开后仍保留原有的四项：**人的表述**（该阶段的人话，可点回会话）、**命令**、
**后端契约**（模块 + 硬约束）、以及新增的**本方法任务**与**接线理由**。也就是说：方法层与工程层
在同一个节点上对齐，读者不需要在两个页面之间对照。

节点标记也做了一处诚实化：计划内但本会话没有消息的阶段，圆点改成**虚线空心圈**、右侧写
「本会话未出现」，且不渲染跳转箭头（`focusInThread` 本来会弹"没有该阶段的消息"，那是在用 toast
掩盖一个应该静态显示的事实）。

## 6. 边界（本文没有做什么）

1. **执行器仍全阶段执行**：`pipeline.py` 只记录 `covered_stages` 与发 `stage_skip` 事件，阶段块一个不少
   （164/165 的边界未变）。面板③轨就是把这条边界画出来，而不是抹掉。
2. **不自动改方法绑定**：ESE 的计划/会话顺序矛盾按 §1.1 交由人判定，代码里没有"检测到不一致就改
   methodId"这种自以为是的修复。
3. **不把"计划外"说成"无效"**：③轨的文案固定为「计划外 ≠ 无效：这些阶段真实发生过，但不属于本方法
   声明的编排」。是否按方法跳过，是执行层改造。
4. **`uncovered` 是空缝，不是功能**：`stage_plan` 会把"fit 声明了但接线没走到"的槽位追加在计划尾部并
   标 `uncovered`。当前十个方法都没有这种槽位（有单测断言），所以这条分支没有任何演示数据；它保留
   是为了将来加方法时不静默丢阶段。
5. **没有动注册表与 Python**：schema 仍是 0.7，`method-registry.json` 未改（因此不需要重跑
   `workspace export` 的数据变更；发布树同步仍需执行，因为 apps/web/src 变了）。

## 7. 验证（可复现）

| 检查 | 结果 |
|---|---|
| `npm run typecheck` | ✅ |
| `npm run test:unit` | ✅ 75/75（15 个测试文件；新增 `stagePlan.test.ts` 9 例） |
| `npm run build` / `build:site` | ✅ |
| 新增单测覆盖 | 两方法顺序不同（`S4→S1` vs `S2-S3→S4`）、每步任务卡+wiring 理由、同一转录在两方法下得到不同 extras、治理层不进入计划、首个顺序分歧、未运行会话全标未出现、id 归一化、命令/契约缺失返回 null、十方法都有组合 |
| 手工实测 | ESE 会话面板：`METHOD PLAN · 4 + 2 治理`、顺序不一致提示、③轨 3 个计划外；full-chain：`5 + 2`、"顺序与计划一致"；单步推进时 S1（计划外）行自动展开并高亮 |

**同域顺带修复**：本轮跑前端契约测试时发现 3 个在 HEAD 上就已红、且都与流程面板同域的断言——
ESE 侧栏长标签（`真实研究·待签` → 实际是 `真实研究·闭环回放`，待签在 `short` 里）、
`contextTab` 切换断言（实现被折成多行，行为未变）、跳转提示（补回"切到「完整闭环」会话"的引导语）。
前两条是测试与代码漂移，按当前行为修正并保留原意断言；第三条改代码恢复引导语。三条都在本文一并记录，
不藏在"顺手改了测试"里。

### 可证伪主张

1. 若把 `repository-mining` 的 `fit_stages` 补上 `S8-S12`，面板①轨应立刻多出「写作与评审」节点，
   ③轨少一项——不需要改任何前端代码。这是"加方法=加数据"的可检验形式。
2. 若未来执行器按计划跳过阶段，ESE 的③轨应缩小到空；若面板仍显示③轨，说明 `composition_plan`
   没被真正消费，而不是面板没更新。
3. 若某方法的 `stage_tasks` 缺一个槽位，注册表 fail-closed 校验会先红（`stage_tasks` 必须覆盖 fit_stages），
   面板不会渲染空任务卡。
