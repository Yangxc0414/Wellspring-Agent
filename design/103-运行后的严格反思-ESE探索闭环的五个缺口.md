## 1. 运行后才发现的事实（不是推测）

### 1.1 候选与执行问题是对齐的（0.857）

我原先担心"pipeline 的候选在讲 flaky test，执行的却是 bug-fix 共变，两者脱节"。实测词面重叠 **0.857**（6/7 个问题词元同时出现在候选的 title/hypothesis/falsification 中），状态 **aligned**。

结论：这一次不存在"候选与执行两张皮"；但仍需要记录**选择动作**（见 1.3），因为"对齐"不等于"人选过"。

### 1.2 S4 的控制变量没有进入执行（真缺口）

S4 设计写了 5 个 controls：

- Project identity
- Calendar time period
- Commit size (lines changed or files touched)
- Author identity
- Whether the commit also modifies production code

但执行器只算：合并/分仓库比率、bug-fix vs 其他、时间前后半。**controls 被记录、未被实现**——也就是说，执行的研究比设计问的问题更简单。已在 note 新增「3b. Design-protocol gap」明确写出，不假装执行了分层分析。

### 1.3 候选选择没有签署

探索循环直接取 top-1 候选生成协议。note 现在记录：

- selected candidate 标题；
- **selection is unsigned: no G1 decision is recorded**（选择未签署：没有 G1 决定）。

这不是可省的形式：G1 是"选哪个问题值得做"的人签门，agent 取 top-1 只能算建议。

### 1.4 方法检查只查"字段在不在"，查不出"字段是否可操作"

协议 advisory_ok（8/8）通过了，但其中：

- license_check 是一句"repository LICENSE checked before analysis"，不是逐仓库许可事实；
- extraction_script 是路径字符串；
- time_window 的 end 是 2026-11-18，恰是运行日，未说明与仓库最新提交的关系。

**字段存在 ≠ 协议可执行**。方法检查目前只能防"漏字段"，防不了"填模板"。

### 1.5 结果接不进门的后半段

执行产物是 result.json/result.md，不是 RunCapsule/EA；没有 G2 冻结、没有 S5b Claim、没有 closure/lineage；S8 写作也无法把这些数字当证据引用（它们不是 span 也不是已签 claim）。所以 note 只能称"探索性结果"。

## 3. 对整体设计的反思

1. **系统的研究单位正在从"阶段"变成"协议 + 执行器 + note"**：S1–S4 负责"想什么、怎么设计"，真正产出知识的是执行器 + 结果。产品架构仍把 S5 当 experiment runner，ESE 执行目前是并行实现——这是需要决策的分叉：把 ese-exec 作为 S5 的一个执行面（推荐，产出 EA 兼容件），还是另立模块。
2. **"能执行"暴露了"设计不落地"**：S4 的 controls 是给人和统计看的，执行器不认识它们。若不做映射，设计越完整、执行越简化。
3. **方法合规 ≠ 研究可执行**：方法注册表能要求字段，但字段可以由模板填充；下一版检查应区分"字段存在"与"字段引用了真实路径/哈希/逐仓库事实"。
4. **demo 图与这一层的关系**：双循环图的"执行 + 指纹 → 区间 + 复现"其实是 S5 的承诺；ESE 执行是它的一个实例，但门后半段没接上。图注需要说清，否则又把"探索性执行"读成"已签结论"。
