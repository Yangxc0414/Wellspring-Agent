# 130-演示体验专项：空态、错误态、信息重复与按钮措辞

日期：2026-11-19
承接：`129-能力边界收敛与右侧面板审计`（§6 下一步把能力表达用到全站）
边界：本文只改「表达与状态呈现」；不改门禁语义、不接后端、不改数据模型。

## 0. 审查方式

前几轮查的是「按钮逻辑对不对」「能力是否真实」。这一轮换到**体验层**：截图逐 tab 巡检 + 读码核对，按你列出的六个维度逐项过——页面结构、信息层级、交互流程、按钮样式与文案、状态反馈、空/错/加载。

## 1. 发现的问题与处置

### 1.1 空态：一整屏白 + 一行没样式的小字（严重，已修）

PROJECTS tab 打开后是一屏空白，只有一行灰色小字。继续查发现根因：**`.context-note` 这个类名被 12 处当作空态使用，但 CSS 里根本没有它的规则**——它一直在吃浏览器默认样式。

处置：
- 新增 `components/EmptyState.tsx`，统一「图标 + 标题 + 说明 + 可选动作」三段式，提供 `block` / `note` 两种密度。
- block 形态**复用已有的 `.context-empty-card`**（一个早已写好但没人用的空态样式），避免同一产品出现两套空态视觉。
- 给 `.context-note` 补上正式规则，12 处既有调用一次性获得一致外观。
- 替换 PROJECTS、EVIDENCE PACKAGES、GUIDANCE QUEUE 三处最关键的空态。

实测：PROJECTS 空态现在 `display:grid / justify-items:center / 标题 600 字重 / 含图标`，高度 118px，具备真实视觉重量。

### 1.2 错误态：中英混杂的原始技术错误（严重，已修）

静态构建下 PROJECTS 实际走的是 **error 分支**而不是空态分支，用户看到：

> 项目实验链不可用：/api/projects requires the local runtime; this build was compiled without it

这是 `requireRuntime` 的英文异常被原样拼进中文界面。同类问题另有 3 处（设置页记忆/子智能体/命令/模型绑定）。

处置：在 `capabilities.ts` 增加 `describeRuntimeError()`——静态构建下直接返回中文说明，有 runtime 时保留「读取失败：xxx」的调试信息但走同一入口。5 处调用点全部改为调用它。

这条也修正了我上一轮的一个判断：当时只修了「空态分支」，没意识到静态构建根本走不到那里。**按代码分支推断 ≠ 看实际渲染结果**，是这次靠 DOM 探测才发现的。

### 1.3 信息重复：同一个门禁列表印两遍（中等，已修）

EVIDENCE 的 ADMISSION 与 RUN 的 GATES 是同一份 `task.gates` 全量列表，两个 tab 各印一遍。

处置：EVIDENCE 只列**未通过**的门 + 顶部给 `4/5 PASS` 统计 + 底部「在 RUN 面板查看全部 6 道门与命令」。全通过时用紧凑空态说明"仍需 CLI 签署"。

原则：详情页可以更详尽，但不该整段复制另一个页面；重复的分工应是「摘要 vs 全量」。

### 1.4 按钮措辞：承诺了构建做不到的事（严重，已修）

输入框上方的建议按钮「运行真实 pipeline」在静态构建下点击只会失败。

处置：静态构建下文案改为「**推演一次 pipeline（演示）**」，并且**真的改为调用本地阶段推进**（`startAuto`），而不是继续调会失败的 `startLiveRun`。按钮说什么就做什么。

### 1.5 疑问句当标题（轻微，已修）

EVIDENCE 折叠区标题「这五段是什么意思？什么时候需要人签？」读起来像产品在自问自答。改为陈述式：「五段的含义与人工签署时点」。

### 1.6 空态占位过大（轻微，已修）

GUIDANCE QUEUE 为空时占满一个 section。改用 `note` 密度的空态，并补上"只改执行策略，不改 claim 与门禁"的边界说明。

## 2. 检查后确认无需改的

- **加载态**：只有 PROJECTS / ESE 真正异步，都已有「读取…」提示；其余 tab 用种子数据同步渲染，不存在白屏等待。未新增骨架屏——没有等待就没有必要。
- **按钮命名**：`运行任务`（真 runtime）整块被 `!__STATIC_ONLY__` 包住，静态 demo 不可见，不存在误导。`运行 3 seeds` 未冻结时禁用且有 title 解释。`启动全自动` 是真实生效的本地推演。三者语义边界清楚。
- **术语**：「签署（动作）/ 人签（主体）/ 签名（产物）」是有意区分，不是混用。
- **右侧面板长度**：RUN 有 4 个 section 需滚动，但折叠 STAGE TRACE 会削弱演示效果，保留。

## 3. 建议但本轮不做

- **统一"非真实"的表达**：「演示态 / 演示数据 / DEMO / 模拟」四种说法共 80 处。收敛需要逐句判断语境（数据性质 vs 动作性质），属文案系统化工程，不适合夹在功能改动里做。
- **全站术语表**：EA / capsule / span / closure 等缩写首次出现处加 hover 解释，需先定一份术语表，再批量接。
- **骨架屏**：仅在未来接入更多异步源时才有意义。

## 4. 反思

1. **空态是被忽视的一等状态**。功能态和错态都有人管，空态长期是「一行小字」，而演示时观众最常看到的就是空态（演示会话之外的 tab 大多是空的）。
2. **类名存在 ≠ 样式存在**。`.context-note` 用了 12 次没有规则，这类「影子类名」只能靠"看渲染结果"发现，读代码看不出来。
3. **上一轮我按分支推断，这一轮靠 DOM 探测**。前者让我以为修好了空态，实际用户看到的是 error 分支。以后涉及"用户实际看到什么"的判断，必须以渲染结果为准。
