# 网页内签署与可见反应：演示不必离开工作台

> 状态基线：2026-11-21。承接 141（人工门对话化）、143（会话阶段路径）、145（人的表述上屏）。
> 边界不变式：真实签名仍只能由本地 CLI 产生；网页内签署是**页面内存里的演示预览**（静态构建限定、刷新即回、处处标注）。本文只改前端（`apps/web` + readiness 脚本断言）。

---

## 0. 一句话结论

演示里最有价值的瞬间是"人按下签署，界面立刻有反应"。此前三个缺口：门对话框签署后只是关掉、S5b 之外的门没有网页内签署、协议卡把真实冻结产物误标为"演示已推进"。本轮：G1/G2/G5 在静态构建内可**在网页上应用决策**并触发可见反应（签署卡片进会话、BRIEF KPI / 证据链 / 门徽章随之变化）；S5b 的演示签署从"埋在 ③ 区"提为第一动作；切到带阶段标签的会话时右栏直接落在该会话的 SESSION PATH 上。

## 1. 网页内签署的边界设计

**能做什么**：静态构建（= Pages 部署形态）里，G1/G2/G5 对话框填完决策后点「应用决策（演示预览）」——
- 会话追加签署卡片（agent 消息 + gate 卡，status pass，正文注明"页面内存演示"）；
- BRIEF KPI、EVIDENCE 证据链、门徽章、TaskHeader 全部随 task.gates/claim 重新派生（G5 演示签署后 CLOSURE 从 blocked → pass 实测）；
- toast 确认 + 对话框关闭。

**不能做什么**（不变式，实现与文案双重钉住）：不写 g1-decision.json / protocol-card.json / closure-signature.json；不产生真实签名；runtime 构建无此按钮（`applyDemoGateDecision` 有 `__STATIC_ONLY__` 守卫）；刷新即回待签；每张演示卡片的正文都带"真实生效仍须 CLI 命令"。

S5b（claim）沿用既有 `previewDemoClaim`（origin="demo"），本轮把它从"埋在 ③ 区的两个块"合并为对话框**第一个动作**「在网页上签署（演示预览）」，并精简了 ①②③ 编号文案。

## 2. 流程面板 ↔ 会话对应：从"保持"到"直达"

selectTask 原规则是"非 full-chain 任务从演示流程回落 BRIEF"（design/137 的防错）。但 143 之后流程面板在带标签会话上就是**这条会话自己的路径**——防错理由已消失。新规则：**切到带 stage 标签的会话 → 右栏直接落在该会话的 SESSION PATH**（实测：E2E 7 阶段、ESE 9 阶段、教学 9 阶段）；无标签会话才回落 BRIEF。节点点击跳转原机制不变（实测 E2E 点 S4 → 会话定位到 S4 消息并闪烁）。

## 3. 诚实性修复（审计截图逼出）

E2E 的协议卡（真实冻结产物）此前渲染 "DRAFT · 演示已推进" + "待人工冻结"——把真实产物误标为演示、把已过的门显示为未过（137 的误标类）。修复：按 `replay.basis` 分流——真实/fixture 语料 → "FROZEN · 真实产物 + 已冻结 + capsule 绑定 protocol sha256"；演示推进 → "FROZEN · 演示推进"；未冻结 → "DRAFT + 待人工冻结"。

同轮精简：TaskHeader blocked 时去掉第三个 "HUMAN GATE"（kicker 与 chip 已双重表达）。

## 5. 设计主张（可证伪）

1. "网页内签署"与"签名只在 CLI"不冲突：前者是**页面内存的演示预览**（static-only、可刷新、标注密集），后者是唯一写入证据层/产物层的路径——把两者的边界写进按钮文案与卡片正文，而不是藏在构建开关里；
2. 签署的可用性 = 反应链完整性：按钮 → 会话卡片 → 面板派生 → toast，缺一环演示者就要口头补"其实这里会变"；
3. 面板的默认落点应跟随会话性质：带路径的会话落 SESSION PATH，无路径的落 BRIEF——防错规则（137）在前提消失后必须主动退役。
