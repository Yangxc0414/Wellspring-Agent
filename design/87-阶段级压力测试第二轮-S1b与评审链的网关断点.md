## 2. 修复 1：S1b 综合必须走与其他阶段相同的模型解析

### 2.1 根因

`literature_synthesis.default_synthesis_model()` 自己读 `DEEPSEEK_API_KEY`、自己构造 `DeepSeekModel`，完全绕过 `models/store.py` 与 `adapters/research_models.py`。而 S2/S3（idea）、S4（experiment）、S8（paper writer）、S5b（judge）都已经走网关。

后果：用户配好网关后，S1→S4 能跑，S1b 在综合阶段硬失败；这正好是"实际使用效果不好"的典型——**不是能力不够，而是同一件事两套供给路径**。

### 2.2 修复

`default_synthesis_model(profile_id=None, store_path=None)` 现在按同一顺序解析：

```text
1) 显式 --profile <id>                     （model_for_profile）
2) 网关 literature binding                  （default_model_for）
3) DEEPSEEK_API_KEY 旧路径                  （保持兼容）
4) 都没有 → SynthesisError，错误里带网关侧原因
```

CLI 增加 `literature synthesize --profile`；`synthesize_literature(..., profile_id=...)` 把选择传下去。

### 2.3 验证（真实调用）

```text
python -m research_agent literature synthesize --project runtime_data/e2e-closed-loop \
  --run-id RUN-E2E-02 --max-themes 4 --profile deepseek-v41
→ model: autodl:DeepSeek-V4.1-Flash-1017
→ theme_count: 4，每个主题至少 2 个不同来源，stances 与 span 证据齐全
```

无 key 时的新错误：

```text
literature has no usable model (literature model provider autodl has no key (AUTODL_API_KEY);
using deterministic template): bind a gateway profile for it ... or set DEEPSEEK_API_KEY
```

## 3. 修复 2：评审链的错误必须指向真正缺的东西

### 3.1 根因

`manuscript_review.review_model()` 先试网关，再回落 `default_review_model()`，但把网关的 note 丢掉了（`port, _note`）。于是"网关绑定存在、只是 key 没设"被报成一句笼统的 "requires DEEPSEEK_API_KEY"。

### 3.2 修复

- `review_model()` 保留 note；回落失败时把网关原因拼进错误；
- `default_model_for` 的兜底消息也带上网关侧 note（影响所有调用方，不只是评审）。

新错误示例：

```text
manuscript review requires DEEPSEEK_API_KEY or an injected model port
(paper has no usable model (paper model provider autodl has no key (AUTODL_API_KEY); ...):
bind a gateway profile for it (a host_agent profile needs no API key) or set DEEPSEEK_API_KEY)
```

## 6. 一句话总结

真正拖垮"实际使用效果"的，往往不是模型能力，而是**同一系统里两条供给路径**：一条走网关、一条只认旧 env。S1b 与评审链就是这种断点；现在它们与其余阶段共用同一套解析顺序，并在失败时告诉用户"到底缺哪个 key"。
