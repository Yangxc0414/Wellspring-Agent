# 129-能力边界收敛与右侧面板审计：从"修一个漏一个"到单一判定源

日期：2026-11-19
承接：`128-模块真实可用性审计`（§6 列出的下一步 1、2 项）
边界：本文改「能力判定位置」与「右侧面板的一致性/可达性」；不改任何门禁语义、不接后端、不放宽 claim 规则。

## 0. 这一轮要解决的两个结构问题

`128` 修掉了 `modelRuntime` 漏掉静态构建保护导致 404 的问题，但那只修了一个实例。真正的问题有两个：

1. **能力判定散落在各处**：`__STATIC_ONLY__` 在 17 个文件里出现 42 次，4 个 adapter 各写一遍同样的守卫。漏一处就产生一个"看起来坏了"的 demo 缺陷——`modelRuntime` 就是这么漏的。
2. **同一事实在多个界面上说法不同**：右侧面板里同一个 claim，RUN 说"演示态预览（未签名）"，BRIEF 说"已签署（证据来自 CLI）"，EVIDENCE 计数里算作 1 条已签。演示态被读成真实证据，这是本项目最不能犯的错。

## 1. 能力判定收敛到单一源

新增 `apps/web/src/domain/capabilities.ts`：

- `runtimeAvailable`：`!__STATIC_ONLY__`，整个前端唯一的构建标志读取点（`__STATIC_ONLY__` 只在这个文件里以字面量出现，Vite 仍可在构建期折叠）。
- `requireRuntime(what)`：发请求前统一抛错，调用方的既有 catch 分支负责降级文案。
- `CapabilityLevel` + `CAPABILITY_META`：把"本地可用 / 演示态 / 需本地 CLI / 需 runtime"四档连同解释声明在一处，供 UI 直接引用。

4 个 adapter（`runtimeApi` / `modelRuntime` / `hostModelApi`）全部改为调用 `requireRuntime`，**adapter 层已无任何 `__STATIC_ONLY__` 直接判定**（有测试钉住）。

## 2. 设置页：每个模块自报能力

`SettingsPage` 新增 `SECTION_CAPABILITY`（16 项），面包屑旁渲染角标：绿「本地可用」、琥珀「演示态」、橙「需本地 CLI」、灰「需 runtime」。带 hover 解释。

关键细节：`runtime` 档在有 runtime 的构建里自动收敛为 `real`——同一份代码在静态 demo 和本地工作台给出不同但都正确的标注，不需要两套文案。

实测 16 个模块角标：9 本地可用 / 6 演示态 / 1 需 runtime，与 `128` 的三档结论一致。

## 3. 右侧面板审计（8 个 tab）

### 3.1 同一个 claim 三种说法（严重，已修）

- BRIEF：`claim.status === "signed"` → 写"已签署（证据来自 CLI）"。
- EVIDENCE 链节点：`signed` / `unsigned` 二态；SIGNED CLAIMS 计数把 demo 算 1。
- RUN：已正确用 `claimLabel.demo` 标"DEMO · 无真实签名"。

修法：三处统一走 `claimSignatureLabel()`。BRIEF 现在区分 `signed-demo` / `signed-cli` / `signed-import`；EVIDENCE 节点显示"演示态预览（未签署）"，计数只认 cli / cli-import。实测三个 tab 说法已一致。

### 3.2 只读按钮会改运行状态（严重，已修）

RUN 阶段卡在 claim 已签时按钮文案是"查看 claim 签署来源"，但仍调 `actions.signClaim`——该 action 无条件 `paused=true`、`gate="claim"`、并把 G5 改回 blocked。全自动跑到后面时点一下"查看"就被暂停、门禁被回退。

修法：新增只读入口 `openClaimGate()`（只开面板，不碰 run 状态），按钮按 `claimLabel.state` 分流：未签走 `signClaim`，已签走 `openClaimGate`。

### 3.3 窄屏下 3 个 tab 点不到（严重，已修）

`.context-tabs` 是 `display:flex` 且无换行/滚动，8 个 tab 在 <1150px 时溢出被截断，EVOLUTION / EVAL / ESE 无法点击。修法：`flex-wrap: wrap`。实测 1100px 下 8/8 tab 全部可点，`scrollWidth == clientWidth`。

### 3.4 静态构建仍把禁用说成"服务没启动"（中等，已修）

`GovernancePanel`、`EseRunsPanel`、`ContextPanel` 的 observation 空态三处仍写"启动 python -m …"。统一改用 `runtimeAvailable` 判定，静态构建下改说"构建时已禁用"。这是 `128` §3.2 同类问题的残留点。

### 3.5 projects tab 空列表整块消失（中等，已修）

`ProjectExperimentInventoryPanel` 在无项目时 `return null`，导致 PROJECTS tab 全白。改为显式空态：说明这一栏读的是 runtime 清单，并区分静态构建与本地工作台。

## 4. 明确不改的

- **flow 与 brief 的进度"不一致"**：FlowDemo 明说是从 0 步独立推演，与左侧回放各自独立，属设计而非缺陷。
- **EVIDENCE 链节点命名（来源/片段/断言/证据/闭合 vs 说明里的五段）**：措辞可再统一，但两处指代的是同一组对象，不构成误导，留待文案统一时一并处理。
- **EseRunsPanel 的 `/ese-runs.json` 绝对路径**：子路径部署会 404。修它要先确定部署基路径策略，属独立任务。
- **ESE 列的键盘可达性**：`li` 不可聚焦，属可访问性改进，与 `128` 的 focus trap 一并做更合适。

## 5. 反思：这次真正学到的

1. **修一个实例不等于修一类问题**。`128` 修了 `modelRuntime` 的 404，但没有回答"为什么只有它漏了"。答案是判定散落——所以这轮把判定收进 `capabilities.ts`。判断标准应该是：同一个约束出现第二次时，就该抽出来。
2. **一致性缺陷比功能缺陷更隐蔽**。三个 tab 各自算 claim 状态，每个单独看都"能跑"，合起来却在撒谎。这类问题没有报错、没有红测试，只能靠"同一事实多处显示"的对照审查发现。
3. **只读操作必须结构上只读**，不能靠文案约束。按钮写"查看"却调了会改状态的 action，是文案与实现各走一边；把入口拆成两个 action 才是结构保证。

2. `EseRunsPanel` 的静态资源路径改用 `document.baseURI`，与 `LineagePage` 对齐。
