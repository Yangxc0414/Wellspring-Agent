# 元模型驱动的编排：阶段不是名字，而是带端口、角色与门禁的契约实例

**状态基线（2026-11-22）**：承接 design/156（元模型先行）、163（三层控制表）、174（判据 A 剪裁）、
176（三层对齐审计）。本文回答一个此前只写在控制表里、没有真正实现的问题：

> 控制表说"流程顺序的不变层是**端口依赖推导（拓扑）**"，
> 但 174 只让方法决定"跑/不跑"，顺序仍按 `pipeline.py` 的物理序硬编码。
> 元模型声明了端口，编排却没有消费端口——**元模型与编排之间断了一根线**。

本文把这根线接上：**阶段不再是一个名字，而是元模型的一个契约实例**（输入端口 / 输出端口 /
是否人签 / 对应门禁 / 迭代规则 / 该阶段的方法任务与检查）；**顺序由端口依赖推导**，而不是数组顺序。

---

## 1. 现有资产：元模型已经足够推导，只是没人用

`registry.json` 的 `elements` 每个都带完整端口：

| 要素 | 输入端口 | 输出端口 | 人签 |
|---|---|---|---|
| 问题 | — | 研究问题 | 否 |
| 假设 | 研究问题、RunCapsule+EA | 候选假设（可判别）、提炼式假设（事后） | **是** |
| 方案 | 候选假设（可判别）、研究问题 | 判别式协议、数据收集协议 | **是** |
| 证据 | 判别式协议、数据收集协议 | RunCapsule+EA | 否 |
| 判定 | RunCapsule+EA | ClaimRecord | **是** |
| 图表 | RunCapsule+EA | 图 manifest | 否 |
| 写作 | ClaimRecord、图 manifest | 稿件绑定 | **是** |
| 闭包 | ClaimRecord、RunCapsule+EA | closure+导出 | **是** |
| 经验 | closure+导出 | 任务反馈 | **是** |

`validate()` 已经做了**声明顺序的合法性校验**：每个 wiring step 的 `consumes` 必须属于该 element 的
`input_kinds`，且必须"在上游已产出"（`consumed in available`）。也就是说：
**元模型已经能判断"这个顺序合不合法"，但编排层没有用它来"推导顺序"或"生成阶段契约"。**

---

## 2. 编排器要回答的三个问题

| 问题 | 现状 | 本文的做法 |
|---|---|---|
| **顺序从哪来？** | `wiring` 数组顺序（人写的） | 从 `consumes/produces` 做拓扑排序；若声明顺序违反依赖则 fail-closed（validate 已有此校验）；若声明顺序合法但非唯一，拓扑序给出**确定的**执行序 |
| **每个阶段要做什么？** | `stage_tasks` 一句文本 + 全局 checks | 生成**阶段执行契约**：requires / produces / human / gate / iteration / tasks / checks，全部从元模型与方法数据继承，不另写一份 |
| **什么不能越过？** | 散落在 pipeline 的 if 与 LOCKED_SCOPES | 契约里显式标 `human=true` 的阶段不得由 agent 代签；`gate` 字段指向治理门；`locked_outputs` 列出不可被策略改写的产物 |

---

## 3. 阶段执行契约的形状

```json
{
  "stage": "S4",
  "element": "方案",
  "requires": ["候选假设（可判别）", "研究问题"],
  "produces": ["判别式协议"],
  "human": true,
  "gate": "G2",
  "iteration": {"kind": "fixed", "detail": "预注册的 seeds 与停止规则固定"},
  "tasks": "预注册：随机化、区组、主指标、分析计划…",
  "checks": ["experiment.design", "experiment.power"],
  "locked_outputs": ["判别式协议"],
  "skipped": false,
  "not_applicable_reason": ""
}
```

**关键设计**：契约不是新的事实源，而是**元模型 + 方法数据的投影**——
- `requires/produces` 来自 `elements[].input_kinds/outputs`；
- `human` 来自 `elements[].human`；
- `gate` 来自阶段到门的固定映射（Q0/G1/G2/G3/G5），不由方法决定；
- `iteration` 来自 `method.iteration_rule`；
- `tasks` 来自 `method.stage_tasks`（该阶段才有）；
- `checks` 来自 `method.checks`（按阶段归属过滤）。

因此**改元模型会改变所有方法的编排契约**，改方法数据只改它自己——这正是 MDD 的分层。

---

## 4. 与 174 的关系：剪裁与顺序，两个正交维度

```
方法 fit_stages  →  covered（跑哪些阶段）        ← 174 已实现
元模型端口依赖   →  order（按什么顺序跑）        ← 本文实现
```

两者独立：一个方法可以覆盖 3 个阶段，顺序仍由端口依赖决定；
一个方法覆盖全部阶段，顺序也由端口依赖决定。`exploratory` 的
`问题→方案→证据→假设` 不是"方法偏好"，而是**"假设消费 RunCapsule+EA，
所以证据必须先于假设"** 这条端口约束的必然结果。

这就是"元模型设定编排逻辑"的确切含义：**顺序不是人排的，是端口依赖逼出来的。**

---

## 5. 可证伪主张

1. 若把 `exploratory.wiring` 里的"证据"与"假设"对调，`validate()` 必须拒绝加载
   （因为假设 consumes RunCapsule+EA，证据不再上游）——负例测试。
2. 若删掉某 element 的 `outputs`，依赖它的 wiring step 必须在加载期失败，而不是运行时 KeyError。
3. 拓扑序必须与当前合法 wiring 顺序一致（confirmatory 与 exploratory 各一条断言）——
   若不一致，说明要么 wiring 有隐藏依赖，要么拓扑实现有错。
4. 同一方法在两个 composition 下的契约数必须等于 `fit_stages` 数（不多不少）。

## 6. 实测结果（本轮已落地）

三个方法的推导序（`ordered_stages`，按端口依赖）与物理序对照：

| 方法 | 元模型推导序 | 契约条数 | 人签阶段 |
|---|---|---|---|
| controlled-experiment | idea → experiment → run → paper | 5 | 假设/方案/判定/写作 |
| repository-mining | **experiment → literature → run** | 4 | 方案/判定 |
| systematic-literature-review | literature → paper | 4 | 写作 |

**最重要的一条**：repository-mining 的推导序把 `experiment`（S4 方案）排在 `literature`（S1 证据）之前——
这是端口依赖的必然结果（方案产出"数据收集协议"，证据消费它），而 `pipeline.py` 的物理序仍是
literature 在前。`run_start` 事件现在分别声明 `stages`（物理序）与 `declared_order`（推导序），
差距保持可见，不假装已重排。

前端方法详情卡新增「编排契约（元模型推导）」块：实际顺序、完整接线差异、每阶段的
人签/agent、门禁、输入/输出端口、方法任务与检查，全部来自元模型投影。

测试 10 例：拓扑序等于声明序、环拒绝、缺失上游端口拒绝、空接线拒绝、
契约数等于 fit_stages、人签阶段不可降级、门来自治理层、check 唯一归属、order 排除未覆盖要素、纯函数只读。

## 7. 边界

- 本文**不重排 `pipeline.py` 的代码块物理顺序**（那需要把巨型函数拆成可重入阶段，
  仍属 174 §5 的 roadmap）。本文产出的是**编排计划与契约**，并让 `stage_plan` 携带
  `order` 与 `contracts`，供前端/后续执行器消费。
- 拓扑排序只处理 DAG；若未来 wiring 引入循环（探索式的真实回退），需要 SCC/迭代节点，
  本文 fail-closed 拒绝环而不是假装支持。
- 契约不产生 Claim、不读门禁、不代替人签。
