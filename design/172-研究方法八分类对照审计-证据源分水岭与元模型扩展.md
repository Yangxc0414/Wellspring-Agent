# 研究方法八分类对照审计：证据源分水岭、效力词表与组合接线的结构性缺口

**状态基线（2026-11-22）**：承接 design/171（四层模型与设计裁决）。本文用用户提供的
**八类研究方法框架**对照当前 `modules/method-registry/registry.json`（schema 0.7，10 方法 +
9 项效力词表 + 2 种组合接线），做覆盖度审计并给出**分层改进路线**。
**本文不改代码、不改注册表、不改 SPEC**；凡涉及契约（schema）与 L3 语义的改动都明确标注
"需人工确认"，符合 AGENTS.md 的门禁。

---

## 1. 一句话结论

我们的注册表不是"研究方法元模型"，而是**"软件工程经验方法的特化实例"**：
10 个方法全部落在用户框架的「经验类（观测/实验/定性/DSR/文献）」里；
**定量观测（通用）、混合、理论、仿真四类没有对应方法**；
效力词表 9 项覆盖不了定性可信性、整合质量、逻辑自洽、模型保真度；
组合接线只有验证式/探索式两种，**装不下以"需求约束"为起点的 DSR，也装不下非经验证据**。

这不是"多补几个方法"就能解决的——缺的是**分类维度本身**（证据源 / 起点假设强度 / 评估逻辑）。

## 2. 覆盖度审计：8 类框架 × 当前 10 方法

| 用户框架类别 | 证据源分水岭 | 当前注册表对应方法 | 覆盖 |
|---|---|---|---|
| 1 定量实验（RCT/A-B） | 经验 · 受控操纵 | `controlled-experiment`（✅ 内部效度 primary）、`quasi-experiment`（无随机） | 充分 |
| 2 定量观测（相关/队列/横断面） | 经验 · 自然观测、无干预 | `repository-mining`（**SE 场景特化**，非通用相关研究）；`survey`（自报，非行为观测） | **缺口**：无通用观测方法 |
| 3 定性（访谈/民族志/扎根/案例） | 经验 · 质性文本 | `case-study`（偏定性，transferability primary）、`survey` 含访谈 | **部分**：无民族志/扎根理论 |
| 4 混合（解释式/探索式/嵌入式） | 两类证据 + 整合 | 无。`compositions` 是**接线顺序**，不是双证据流整合 | **缺口** |
| 5 理论（思辨/形式化/公理） | 逻辑与已有理论 | 无 | **完全缺失** |
| 6 仿真/计算建模 | 人工规则生成轨迹 | 无 | **完全缺失** |
| 7 设计科学 DSR | 制品使用记录 + 反馈 | `design-science`（utility primary, cycle） | **有方法但接线错配**（见 §4.3） |
| 8 文献/SLR/元分析 | 二次证据 | `systematic-literature-review`（reproducibility primary） | 部分：无元分析（合并效应量/异质性） |

### 2.1 一个量化观察

- 当前 9 项效力词表：`internal / external / construct / statistical / transferability / utility /
  cycle / reproducibility / discriminability`。
- 其中 7 项来自 Cook & Campbell 四分 + Hevner + Lincoln & Guba + Kitchenham，**只有 discriminability
  是 ESE 扩展**。整套词表的隐含前提是"证据来自对现实的经验测量"。
- 用户框架中理论研究的 5 项评估标准（逻辑自洽、概念清晰、理论新颖性、与既有知识相容性、解释力）、
  仿真的 3 项（模型校验/保真度、参数敏感性、假设合理性）、混合的整合质量、
  定性的可信性/反思性/资料丰富度——**在词表里一项都没有一等位置**。

## 3. 三个结构性缺口（不是"加方法"能补的）

### 3.1 证据源不是一等字段

用户框架明确把证据源作为"最底层分水岭"：经验记录 / 逻辑推演 / 人工规则轨迹 / 已有研究结论。
当前 `evidence_sources` 是**自由文本数组**（如"受控环境下对实验单元的一手测量"），
没有类型标签，所以：

- 无法回答"这个方法的证据来自哪一类世界"；
- 无法在执行层决定该方法的证据形态（span / capsule / EA / 逻辑推演记录 / 仿真轨迹）；
- 171 讨论的"非经验证据如何进入治理链"无法形式化。

**建议（契约变化，需人工确认）**：新增一等字段 `evidence_regime`，封闭词表四值：
`empirical / logical / simulated / secondary`。每个方法必填且只能一个主值（DSR 可标混合但需声明主证据）。
`validate()` fail-closed 校验该字段在词表内。这不是"加数据"，是 schema minor 升级。

### 3.2 效力词表是经验方法特化

**建议（契约变化，需人工确认）**：效力词表从 9 项扩到覆盖四类证据源，至少补：

| 证据源 | 新增效力项（建议 key / 中文） | 对应评估标准 |
|---|---|---|
| logical | `coherence` 逻辑自洽、`explanatory_power` 解释力、`novelty` 理论新颖性 | 理论研究的 5 项标准 |
| simulated | `fidelity` 模型保真度、`sensitivity` 参数敏感性 | 模型校验/假设合理性 |
| qualitative | `credibility` 可信性、`reflexivity` 反思性 | 定性标准的 3 项（可转移性已有） |
| mixed | `integration` 整合质量 | 两套证据是否真正对话而非拼接 |
| secondary | `bias_risk` 偏倚风险、`heterogeneity` 异质性 | SLR/元分析特有 |

注意：这不是把词表无限膨胀。原则是**每个一级证据源至少有自己独特的效力判据**，
且新项必须能被具体方法的一等字段/检查引用，不能只是装饰性标签（这是 166 立下的规矩）。

### 3.3 组合接线只有两种，装不下 DSR / 理论 / 仿真 / 混合

当前两种接线的要素序列：

- `confirmatory`: 问题 → **假设** → 方案 → 证据 → 判定 → 图表 → 写作 → 闭包 → 经验
- `exploratory`: 问题 → 方案 → 证据 → **假设** → 判定 → 图表 → 写作 → 闭包 → 经验

两者都以"假设"为枢纽，但用户框架指出三类方法**根本不以假设为起点**：

- **DSR 以"需求约束"代替因果假设**：起点应是 问题 → 需求/约束 → 制品设计 → 演示评估 → 设计知识；
- **理论以"命题/公理"为起点**：问题 → 既有命题 → 逻辑推演 → 理论陈述 → 相容性检验；
- **仿真以"规则与初始条件"为起点**：问题 → 模型规则 → 运行轨迹 → 校验 → 敏感性分析；
- **混合是双轨 + 整合节点**：定量轨与定性轨并行，在"整合"要素处汇合，新增一等要素与端口。

**建议（契约变化，需人工确认）**：把 `composition` 从"两种参考接线"扩展为"按起点类型分类的
接线族"，至少 4 族：`hypothesis_driven`（现 confirmatory）、`evidence_first`（现 exploratory）、
`requirement_driven`（DSR）、`premise_driven`（理论/仿真，再用 `evidence_regime` 区分）。
混合研究不是第五族，而是**在任一族上叠加双轨与整合节点**——这要求 `elementGraph` 的端口模型
增加"汇合端口"（两条不同证据流合并），是当前 fail-closed 校验不支持的新拓扑。

## 4. 逐类改进建议（按用户框架）

### 4.1 先做分类维度，再补方法

用户框架的三个分水岭应成为注册表的三个一等维度：

1. **证据源**（§3.1）→ `evidence_regime`
2. **起点假设强度** → 已由 `composition_id` 表达，但需扩展到需求驱动/前提驱动
3. **评估逻辑** → 已由 `validity_focus.primary` 表达，但词表需扩展（§3.2）

有了这三个维度，"加方法=加数据"才成立；没有它们就加方法，只会让 10 个方法继续压扁成一张表。

### 4.2 建议新增的方法（数据层，逐个需 SPEC Changelog）

| 类别 | 建议方法 id | 建议 evidence_regime | 建议 validity_focus.primary | 说明 |
|---|---|---|---|---|
| 定量观测 | `observational-study` | empirical | `construct`（混杂/选择偏倚需新效力项时再扩） | 补"相关≠因果"的一等边界；与 repository-mining 区分（后者是 SE 场景特化） |
| 定性 | `grounded-theory` | empirical | `credibility`（需先扩词表） | 补"资料→概念"的归纳路径；与 case-study 的"深描+三角验证"区分 |
| 理论研究 | `theoretical-study` | logical | `coherence`（需先扩词表） | 证据是文献与逻辑推演；**必须先解决非经验证据如何进入治理链** |
| 仿真 | `simulation-study` | simulated | `fidelity`（需先扩词表） | 证据是规则生成的轨迹；须声明假设保真度与真实世界校验 |
| 混合 | `mixed-methods-study` | empirical（双轨） | `integration`（需先扩词表） | 需双轨+整合节点的新接线拓扑 |

元分析可作为 `systematic-literature-review` 的一个 variant 或独立方法，建议独立，
因为 `heterogeneity` 与 `bias_risk` 是它特有的一等判据。

### 4.3 DSR 的接线必须改（这是最该先做的一项）

用户特别强调：**DSR 首要目标是造一个有用的东西，实验首要目标是检验假设**。
当前 `design-science` 绑定 `exploratory`（方案→证据→假设），把 DSR 说成了"先做设计、再收集证据、
最后提炼假设"——这混淆了"设计知识"与"事后假设"。

**建议**：新增 `requirement_driven` 接线，要素序列：

```
问题 → 需求与约束（人的治理点）→ 制品设计 → 制品演示/评估 → 设计知识提炼 → 写作 → 闭包 → 经验
```

对应槽位建议：需求与约束→`S0/S2-S3`，制品设计→`S4`，演示评估→`S5`，
设计知识→`S5b`（但断言形态是"设计原则"而非因果 claim，需 SPEC 定义）。
迭代规则 `cycle` 已正确（DSR 是循环改进，不是固定阶段），不要改。

### 4.4 非经验证据进入治理链：SPEC 先行

理论/仿真方法不走"span→capsule→EA→claim→closure"这条经验证据链。
要么为它们定义**证据替代形态**（逻辑推演记录 / 仿真轨迹 + 校验报告），
要么明确它们在本治理元模型下**不可完全闭合**（只能作为辅助材料，不产生 SIGNED CLAIM）。

这正是 design/163 缺陷链里"证据形态多态"那条未闭合问题的延续。
**在 SPEC 定义清楚之前，不应把理论/仿真方法写进注册表**——否则会出现"方法声明了，
但执行器产不出它要求的证据"的假支持。

## 5. 对当前前端设计的具体改进（可立即做，不涉及契约）

| 项 | 现状 | 改为 | 依据 |
|---|---|---|---|
| 推荐卡 | 直接对 10 个方法打分排序 | 两级：先选**证据源/问题型态**，再在候选类别内选方法 | 用户框架"方法没有高下只有适配"+ 起点强度分类 |
| 效力矩阵 | 10×9（方法 × 效力项） | 增加"证据源"分组列，按四类分水岭组织 | §3.1 |
| ③轨措辞 | "本方法未声明" | "本方法在此阶段无特异约束（过程仍经过）" | 171 §3.1（已裁决） |
| 顺序提示 | 归因于执行器 | "计划顺序 vs 会话顺序；可能是混合设计，需人判断" | 171 §3.2（读法 C） |
| ②轨名称 | "治理固定" | "治理决策点 · 不属于方法差异" | 171 §3.4 |

这些是 design/171 §5 修正清单的延续，仍**未执行**。

## 6. 分层路线图（标注代价与确认要求）

| 层 | 动作 | 代价 | 确认要求 |
|---|---|---|---|
| L3 元模型（SPEC + schema） | 加 `evidence_regime`、扩效力词表、扩 composition 族、定义非经验证据形态 | **契约 minor 升级**，涉及 claim/EA/导出不变量 | **必须人工确认**（AGENTS.md §契约变化条） |
| L2 方法数据 | 补 5 类方法 + 每种 stage_tasks 逐字有据 | 数据工作量大；需逐条回溯方法学文献 | 每个方法一次 SPEC Changelog |
| 前端投影 | `stagePlan` / `recommendMethods` / 效力矩阵按新维度改 | 中等；测试需重写而非微调 | 依赖 L3 定稿，否则返工 |
| 执行器 | 按 `evidence_regime` 分派证据形态 | 大；需先定义替代形态 | 依赖 L3 + 165 执行层改造 |

**顺序不能反**：先 L3 定维度 → 再 L2 加方法 → 再前端/执行器消费。
反过来先写前端会重演 169 的"把四层压成一条轴"。

## 7. 可证伪主张

1. 若把 `evidence_regime` 作为一等字段，`recommend_methods` 的三态拒答会**更准**
   （因为多了"证据源不匹配"的排除条件）——待实测。
2. 若 DSR 改用 `requirement_driven` 接线，`design-science` 的 `stage_plan` 首节点会从 `S4`
   变成 `S0/S2-S3`（需求框定），不再把设计知识说成事后假设——可在数据改完后验证。
3. 若理论/仿真方法在 SPEC 定义替代证据形态之前进注册表，执行层**必然产不出对应 EA**——
   这是反对"先加方法后补 SPEC"的可证伪判据。

## 8. 边界

- 本文**不改任何代码、数据或 SPEC**。§4.2 的建议方法是**提案**，没有写进注册表，
  当前系统仍只有 10 个方法、9 项效力词表、2 种接线。
- 用户提供的八类框架是**分类参考**，不是唯一真理；不同体系（如 Creswell 的 approach）
  分类轴不同，171 已声明术语体系，本文沿用。
- 理论研究/仿真是否应纳入本治理元模型，本身是产品边界问题——
  本文给出"先定证据形态"的技术前提，不替用户决定要不要纳入。
