# 框架创新：从"固定流程"到"治理元模型 + 方法组合"——论文创新点的正式表述

> 状态基线：2026-11-21。承接 149–155（方法原模型/要素端口/组合/标签层）与研讨纪要完整版。
> 本文完成架构落地的第一步：**治理元模型（elements 端口模型）与方法组合（接线）进入注册表 0.4，加载时 fail-closed 端口拓扑校验**；前端组合卡改为消费注册表数据。`pipeline.py` 的执行编排尚未切换到组合驱动（SPEC 先行，见 §4）。

## 0. 一句话结论

研讨纪要的要求——"框架设计需要改进，而不是固定的一个框架；从研究的本质出发进行设计创新"——本轮落地为可执行形态：**治理元模型（9 个带类型化端口的治理要素，不变）与方法组合（接线数据，可变）进入方法注册表（schema 0.4），加载器对每种接线做端口拓扑校验，非法接线（如探索式里让方案消费尚不存在的假设）在数据层即被拒绝。** 至此"框架 = 元模型上的合法接线集合"从设计主张变成被加载器执行的约束。

## 1. 论文创新点的正式表述（可直接用于毕设论文）

**创新点：以研究本质为原模型的"治理元模型 + 方法组合"架构。**

1. **原模型层（不变）**：研究的本质被形式化为证据三元组——问题 → 能判别候选答案的证据 → 经审查、带范围的主张 → 公共知识积累（Popper 可否证性、Merton 组织化怀疑、Longino 社会性客观化）。治理语义（人签门、证据边界、签署权属）对该层所有实例恒定。
2. **方法层（数据声明）**：每种研究方法在注册表中声明三件事——它适配哪些治理要素（fit_stages）、须冻结的协议字段与检查（protocol_fields/checks）、它的证据类型与能力边界（cannot_support/evidence profile）+ 标签。加一种方法 = 加一份数据，不改执行器。
3. **组合层（接线即流程）**：流程顺序不是写死的，而是要素端口上的接线——组合数据声明每一步消费哪个上游端口；加载器做端口拓扑校验，非法接线（消费尚未产出的端口）在数据层被拒绝。验证式（假设→判别式方案）与探索式（数据收集方案→事后假设）是同一元模型上的两种合法接线。

**与固定框架的对比**：固定框架下"支持一种新研究方法" = 改执行器代码；本架构下 = 注册表加一份数据声明，治理门与证据语义自动继承。这正是纪要"实现阶段与活动的高度复用"的形式化：复用的单位是治理槽位与端口，差异的单位是接线与协议字段。

## 2. 本轮实现（数据与校验进入后端）

1. **registry 0.3 → 0.4**（scripts/add_method_compositions.py）：顶层 `elements`（9 个治理要素：id/label/input_kinds/outputs[consumes→produces]/human）与 `compositions`（验证式 9 步 / 探索式 8 步接线）。
2. **method_registry.py**：SCHEMA → 0.4；PORT_TYPES 闭合端口词表；validate 对 elements（端口词表内、output 规则消费已声明输入）与 compositions（要素存在、消费端口已声明、**端口拓扑匹配**——消费的上游端口必须已产出）fail-closed；新增 `get_composition` 访问器。`tests/test_method_registry.py` 增 ElementCompositionTest（参照组合合法、非法接线拒绝含"has not been produced upstream"断言、未知端口拒绝、访问器回环），合计 45 测全绿。
3. **负例验证**（手工注入）：探索式接线里插入"方案消费候选假设"——加载器拒绝："port 候选假设（可判别） has not been produced upstream"。非法接线在数据层被拦截，这正是"顺序由依赖推导"的可执行形式。
4. **前端**：方法模型页的组合卡改为消费注册表 `compositions`（fallback 到 domain 常量以兼容旧快照）；schema 校验 0.4。

## 4. 边界与迁移路线（诚实声明）

- **`pipeline.py` 的执行编排仍为固定链**：组合层目前是"治理元模型层的数据 + 校验"，尚未成为执行器的驱动输入。迁移路线（SPEC 先行）：(a) 方法 profile 声明 composition_id；(b) PipelineRunner 按 composition 解析阶段序列（治理门语义不变）；(c) 回归：既有 fixture/CC-BY/ChemLab 纵切在组合解析下结果等价；
- 端口类型词表（12 个）是展示级分类，非类型系统；真实端口契约需绑定产物 schema；
- 组合提案租约化（agent 提出新接线）形式定义已在 154 §4，依赖本层的执行器迁移。

## 5. 设计主张（可证伪）

1. **"框架 = 元模型上的合法接线集合"是可执行的**：加载器拒绝非法接线（负例已测），不是文档性描述；
2. **加方法不改执行器**：注册表 0.4 下新增一种方法 = 数据声明（三维 + fit + 标签 + 组合），治理门与证据语义自动继承——可用"新增一个方法 profile 后既有 41 项 python 门 + readiness 全绿"验证；
3. **两种接线共享治理语义**：验证式/探索式在同一元模型上，仅在方案/假设的端口接线上不同——这证明"变与不变"的切分点选对了。
