# 97-实验定位澄清：我们测的是"智能体的产出"，不是"ESE 现象"

> 状态基线：2026-11-18。触发问题："目前测试的实验是针对 ESE（经验软件工程）领域的吗？"
> 结论先说：**不是**。我们做的是"用 ESE 的方法规范去评估科研智能体的阶段产出"，不是"对软件工程现象做实证研究"。
> 本文把三层混在一起的说法拆开，避免 demo/论文里把"方法层是 ESE"误读成"实验内容是 ESE"。

---

## 1. 三层要分开

| 层 | 内容 | 是不是 ESE |
| --- | --- | --- |
| **方法层** | 阶段×方法注册表（9 个 ESE 方法、Kitchenham/Wohlin/Runeson 等指导文献）、预注册字段、durable/operational 失败分类、14 项 rubric | **是 ESE 的方法论形式**（借用了 ESE 的方法规范） |
| **实验对象** | 被评估的是：pipeline 生成的 idea 候选、experiment 设计草稿、paper 草稿是否满足方法规范 | **不是 ESE 现象**：对象是"智能体产出"，不是缺陷/测试/开发者/仓库 |
| **证据来源** | held-out run 的语料是 4 篇 arXiv "self-improving agents" 论文（DGM/SIFT/SICA/ACE）；e2e 项目是合成 passivation fixture | **不是 SE 文献，也不是 SE 数据** |

一句话：**方法是 ESE 的，内容是"智能体评估"的。**

## 3. 如果要真的做 ESE，最少要换掉什么

| 要素 | 现在 | ESE 需要 |
| --- | --- | --- |
| 研究对象 | agent 的草稿 | SE 现象：缺陷、测试、评审、仓库、开发者 |
| 数据 | arXiv 智能体论文 / 合成 fixture | Defects4J、GitHub 仓库、开发者调查、benchmark（如 SWE-bench） |
| 执行 | 没有 S5 | 真实执行（跑测试、跑挖掘管线、跑问卷） |
| 结论 | rubric 符合性 | 区间/效应量 + 独立复现 + 适用域 + 人签 claim |
| 方法声明 | 注册表（未实际用） | 先选方法（案例/挖掘/实验），按该方法写协议并执行 |

可选路线（成本从低到高）：

1. **案例研究/设计科学**（低）：用现有管线研究一个 SE 工具问题（例如"LLM 生成的测试在 3 个 Java 项目上的可用性"），需要 SE 项目与测试执行环境；
2. **仓库挖掘**（中）：GitHub 公开数据 + 抽样框/时间切分/去重（method card 已定义），输出相关性结论，需要两个生态做复现；
3. **受控实验**（高）：Defects4J + 基线（EvoSuite）对照，预注册 + 功效 + 区间 + G2/S5b 人签。

## 4. 对现有文档与 demo 的修正

- demo 页只宣称"ESE 阶段×方法注册表"，没有宣称"做了 ESE 研究"——这一句是准确的，保留；
- 在能力指标表补一句"评估对象是智能体产出，不是 ESE 现象"，避免读者把 rubric 分数读成 SE 结论；
- 93–96 的结论仍然有效，但要按"智能体评估"来读：它们回答的是"配方改动能否让草稿更像合格设计"，不是"某个 SE 实践有效"。

---

## 5. 下一步建议

如果毕设主线是"自改进科研智能体"，当前"评估智能体产出"的实验是必要的（否则无法证明自改进）；
如果导师要求"聚焦 ESE"，则需要**另起一条真实 ESE 研究线**（建议从案例研究或仓库挖掘起步），并用本仓的 method registry + 预注册 + S5 执行 + claim 走完整链。
两条线可以并存：**一条评智能体，一条做 ESE**；但论文里不能混写。
