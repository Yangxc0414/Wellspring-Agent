# 变与不变控制表：让三列关系从描述变成约束

> 状态基线：2026-11-21。承接 156（治理元模型+组合进注册表）、160（阶段目标上屏）、161（对比表收口）与研讨纪要核心思路（"抓住变与不变"）。
> 本文新增前端控制表（`apps/web`）并补 EVIDENCE_PROFILES 的 artifactForm；治理语义未动。

---

## 0. 一句话结论

"抓住变与不变"此前是分散在各处的描述（159 的三层、152 的映射表、156 的三层 MDD）。本轮把它收敛成方法模型页顶部的一张**控制表**：五个维度（治理槽位与门 / 证据形态 / 流程顺序 / 主张 / 自改进）× 三列（不变·治理语义 / 随方法变·注册表数据 / 随内容变·任务实例），每格写明**由谁控制、控制到什么程度**——关系从描述变成约束表。

## 1. 控制表的内容（五维 × 三列）

| 维度 | 不变（治理语义，L3） | 随方法变（注册表数据，L2） | 随内容变（任务实例，runtime） |
|---|---|---|---|
| 治理槽位与门 | 槽位语义与门位置固定 | 方法声明核心槽位（fit） | 实际走过的槽位 |
| 证据形态 | 可固定/可复算/可核查（抽象要求） | RunCapsule、应答集、语料快照…（具体形态） | 本次执行的产物 |
| 流程顺序 | 端口依赖推导（拓扑） | 组合接线（验证式/探索式） | 实际执行记录 |
| 主张 | claim 三元组（主张+依据+范围） | cannot_support 能力边界 | 本次的 statement 与范围 |
| 自改进 | 租约+门+人签（治理不变） | 方法/矩阵/组合的修订提案 | 过程经验与教训 |

**关键发现（本轮审计逼出）**：证据形态是五维中"随方法变"最实质的一列——此前 S5 槽位的证据语义被硬编码为 RunCapsule+EA（run harness 形态），但调查/案例方法在同一治理槽位产出的是应答数据集/证据包——**治理的抽象要求（可固定/可复算/可核查）不变，具体形态随方法变**。本轮把这一区分显式化：EVIDENCE_PROFILES 每方法补 `artifactForm`，方法详情卡"证据类型与效力"块渲染 S5 证据形态行。

## 2. 控制层级（谁能动什么）

| 层级 | 能改 | 治理 |
|---|---|---|
| L3 治理语义 | 元模型（要素/端口/门/证据抽象要求） | 代码 + SPEC + 人签（不可经前端修改） |
| L2 方法数据 | 方法列内容（fit/协议字段/检查/标签/组合绑定/矩阵交叉点） | 组合提案租约（154 §4 roadmap） |
| L1 任务实例 | 主题、数据、本次 claim 陈述、实验记录 | runtime 产生，治理门控制 |

**回应纪要的自进化设问**："自进化系统还需要固定架构吗"——需要，但固定的是 L3 的**治理语义**，不是 L2 的**方法内容**。自改进的完整形态 = L1 改 skill + L2 在租约下改方法/矩阵/组合 + L3 经人签升级元模型——三层缺一不可。

## 3. 本轮实现

## 5. 设计主张（可证伪）

1. "变与不变"从方法论口号变成**面板结构**：五维三列的控制表让每个维度"由谁控制、能变到什么程度"一屏可读——这是纪要"探索可变内容的补充形式"在产品上的具体回答；
2. 证据形态的"治理不变/形态可变"切分是证据三元组的深化：**抽象要求不变（可固定/可复算/可核查），具体形态随方法**——切错位置（如要求所有方法产出 RunCapsule）就会把调查/案例方法挤出系统；
3. 控制表本身就是毕设创新点的**演示页**：向老师展示"这就是我们的框架如何不是固定的"——指向这张表即可。

## 6. 边界与下一步

- L2 的"组合提案租约"仍是 roadmap（154 §4 形式定义）——控制表声明的修订权需后端 SPEC 先行才能真正开放；
- 证据形态的"可固定/可复算/可核查"抽象要求目前是治理语义描述，尚未绑定到产物 schema（runtime 接入后由 SPEC 收口）。
