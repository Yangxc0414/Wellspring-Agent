# 128-模块真实可用性审计：以按钮为单位的核查

日期：2026-11-19
范围：`apps/web/src/components/settings/*`（16 个设置 section）+ 工作台左侧栏（Sidebar）

## 0. 为什么单独记这一篇

用户的要求是「各个按钮、左侧栏各个模块都需要是真实可用的」。这句话有两种误读方式，必须先排除：

- 误读一：**每个按钮都必须能执行真实后端操作**。在静态 Pages 构建里做不到，因为 runtime 在编译期就被禁用了（`vite.config.ts`）。强行"让它能跑"只能靠伪造，这恰好违反本项目的核心纪律。
- 误读二：**只要页面不报错就算可用**。这也不够——真正的问题是「点了没反应」「看起来像保存了但没保存」「把构建限制说成用户的错」。

所以这篇审计采用的判据是三条：**能打开、有内容、反馈诚实**。不满足第一条是 bug；不满足第二条是空壳；不满足第三条是误导——第三种最危险，因为它不会被报错暴露。

## 1. 核查方法

- 静态读码：逐个 section 追 UI 控件 → store action → 持久化键，确认写操作是否真的落库。
- 实机点击：headless Chromium 打开设置页，遍历全部 16 个导航条目，记录每个 section 的 `h1`、正文字符数、是否空白，同时监听 `pageerror` / console error / 所有 HTTP ≥400 的响应。

实机这一步是必要的：静态读码只能证明"代码写了"，不能证明"点进去真的有东西"。本次正是靠它抓到了一个真实缺陷（见 §3.1）。

## 2. 结论：16 个 section 全部可达、均有内容

## 3. 本轮修掉的真实缺陷

### 3.1 静态构建仍在发 runtime 请求（实测发现）

实机遍历时捕获到 `HTTP 404 /api/models`。根因：`adapters/modelRuntime.ts` 的两个请求函数（`getJson` / `requestJson`）**没有** `__STATIC_ONLY__` 保护，而 `adapters/runtimeApi.ts` 有。

后果有两层：控制台出现 404；更重要的是，这类请求会让演示者以为"服务没起来"，而实际是构建期就禁用了。

修复：两个函数在 fetch 之前直接抛 `runtime disabled in static build`；调用方（ModelBindings / ModelPicker）的既有 catch 分支负责降级。修复后实机遍历 `errors: none`。

### 3.2 静态构建把"构建期禁用"说成"你没启动"

`WorkspaceSettings.tsx` 三处、`UsageStats.tsx` 一处，原文统一是"未连接本地 runtime。启动：python -m …"。在静态 demo 里这句话是错的——用户启动任何东西都不会生效。

修复：四处都加 `__STATIC_ONLY__` 分支，静态构建下改说"静态演示构建：runtime 在构建时已禁用"，并指出真实运行应在本地 CLI 工作台。`ModelBindings` 的英文错误也换成了中文说明。

### 3.3 设置页里看不到 STATIC 横幅

`StaticModeNotice` 挂载在 `App.tsx` 的 app-grid 里，而设置页是 `role="dialog" aria-modal="true"` 的全屏层，横幅被完全遮住，只剩侧栏脚注一行小字。

修复：标题栏徽章在静态构建下显示 `STATIC · DEMO`（琥珀色），非静态仍是 `LOCAL · WORKSPACE`。

### 3.4 左侧栏"自动化"的失败文案不准确

`Sidebar.tsx` 的 catch 分支说"runtime 离线"——静态构建下不是离线，是编译期禁用。已按模式分开措辞。

## 4. 明确不改的项（附理由）

- **usage 的图表数值**：它基于种子任务的固定值 + 字符估算，页面已在三处标注"估算 / 不是 API 计费"。要变成真实用量需要 runtime 记账，属于产品化工作。
- **plugins 的"提议只读调用"**：目前生成硬编码 args 与标注"演示数据，未联网"的结果。接真实 MCP transport 是独立任务，且涉及网络与鉴权，不能在静态构建里做。
- **lineage 快照不刷新**：`lineage-demo.json` 是真实产物导出的一次性快照，`runtimeApi` 里没有 lineage 接口。做实时刷新需要先有后端接口。
- **FeedbackModeSettings**：它写 localStorage 且当前无消费者，但卡片标题与描述已明确"选择是声明层，测量命令仍由本地 CLI/MCP 执行"，属于诚实声明而非假保存。

## 5. 反思：这次审计暴露的方法问题

1. **"按钮可用"必须分层定义**。真实可用 / 演示可用 / 需要 CLI，三者在同一个界面里共存是合理的，但不能让用户自己去猜。判断标准应该是"点了之后，用户是否知道发生了什么、以及下一步该去哪"。
2. **编译期能力缺失必须显式传播到 UI**。`runtimeApi` 做了，`modelRuntime` 漏了——同一类约束在代码里没有统一入口，就容易漏。这类"能力开关"应集中判定，而不是每个 adapter 各写一遍。
3. **全屏 modal 会遮住全局提示**。`StaticModeNotice` 的设计假设"它总能被看到"，但设置页一开就不成立。这类全局横幅需要每个全屏层自带等价声明。

## 6. 下一步

1. 把"静态构建能力判定"收敛到一个 `capabilities.ts`，adapter 只查询不各自判断（根治 §3.1 的同类问题）。
2. 给设置页每个"半真"section 加统一角标（真实 / 演示 / 需 CLI），让用户不用读正文就能分辨。
3. 若要让 usage 与 lineage 变实时，先补后端接口，再改前端——顺序不能反。
