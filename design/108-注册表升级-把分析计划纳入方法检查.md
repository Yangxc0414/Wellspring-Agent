# 108-注册表升级：把"分析计划"纳入方法检查

> 状态基线：2026-11-18。承接 103（方法检查只查字段存在）、104（分层分析落地）、107（ESE 断言可重算）。
> 本轮做一件小事：repository-mining 的检查项增加 analysis.stratification / analysis.permutation，让"分析计划"也成为方法协议的一部分。
> 边界：仍是 advisory；不改变任何 gate/claim/signature。

---

## 1. 改了什么

`modules/method-registry/registry.json` 的 repository-mining 增加一条检查：

```json
{
  "id": "mining.analysis",
  "severity": "warn",
  "requires": ["analysis.stratification", "analysis.permutation"]
}
```

现在 6 条检查：sampling_frame（blocker）、time_split（blocker）、dedup（blocker）、license（warn）、label_source（warn）、**analysis（warn）**。

实测：

- 协议 v3（含 stratification + permutation）→ `advisory_ok`，6/6 pass；
- 缺 analysis 字段的协议 → mining.analysis 报 missing（warn，不改变 status）。

---

## 2. 为什么用 warn 而不是 blocker

- 方法注册表是**数据不是门禁**（registry 自己的 boundary 也这么写）；
- 分析计划缺失是"研究可复算性"的缺陷，但它不该阻止人继续做设计；
- 如果升 blocker，就会变成"没写分层计划就不许提交设计"，那是门禁语义——需要人工决策，不在本轮范围。

---

## 3. 反思：方法检查的能力边界

这次改动再次确认三件事：

1. **检查只能约束"有没有写"，不能约束"写得对不对"**：`analysis.stratification` 存在也可能是一句空话；执行器自己的分析实现才是真的约束。
2. **检查项应该跟执行器同步演化**：分层分析在 104 才落地，注册表滞后了三轮才补字段；说明"协议字段"与"执行能力"需要有同步机制（下一版可在 registry 加 `implemented_by` 指明执行器）。
3. **advisory 的价值在于可见性，不在于阻止**：它让 G2 的人一眼看到"这份协议缺分析计划"，而不是替人做决定。
