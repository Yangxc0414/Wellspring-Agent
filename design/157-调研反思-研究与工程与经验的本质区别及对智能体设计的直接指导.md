## 0. 一句话结论

纪要里被驳回的"基于过程建模"点破了一个我们自己也犯过的错：**按过程建模分不清研究与工程**。本质区别不在步骤，在**终产物与效度主张**：研究以"带范围的知识主张"为终点（证据 → 可否证主张 → 审查 → 公共记录）；工程以"满足需求的制品"为终点（功能验证，不做知识主张）；经验工作以"启发式教训"为终点（无效度主张）。用这个标尺自查本系统四条会话：**只有 ESE 够格叫（窄口径的）实证研究**——E2E 是协议验证（工程味），教学演示是机制演示（演示味）——而我们的 scope 标注恰好都如实说了这一点。本轮再把方法差异落成**对智能体设计的直接指导**（基线策略 + Prompt 纪律），完成纪要 insight 的最后一个落点。

## 1. 本质区别的调研（概念边界）

| | 研究 | 工程开发 | 经验（启发式）工作 |
|---|---|---|---|
| 终产物 | 带范围的知识主张（claim） | 满足需求的制品 | 教训/启发式 |
| 效度主张 | 有：可否证、可核查、范围明确 | 无知识主张，只有功能验证 | 无 |
| 证据角色 | 证据与主张的**判别关系**是一等公民 | 测试只验证制品功能 | 经验即结论，无判别设计 |
| 终止条件 | 主张经审查并进入公共记录 | 制品通过验收 | 教训被记住 |
| 反例（越界） | 无判别设计的"研究" = 工程或经验 | 宣称知识效度的"工程报告" | 把教训写成普适规则 |

文献依据：Popper（可否证性把科学与非科学分开）；Creswell（研究设计 = 问题→证据→主张的效度框架）；Easterbrook 2008（实证策略按证据类型选择）；Runeson & Höst 2009（案例研究的效度）。**判别关系**（design 可以区分假设真假）是研究区别于工程的枢纽：工程的测试验证"制品能用"，研究的证据区分"假设真假"。

## 2. 用这个标尺自查本系统的会话（严格模式）

| 会话 | 终产物 | 本质判定 | 系统是否如实 |
|---|---|---|---|
| ESE（仓库挖掘） | 真实执行的合并读数 + 起草的 claim（三仓库口径） | **窄口径的实证研究**（观察性、便利样本、启发式标签——但有效度主张与判别数据） | ✓ scope 如实写"不可外推"；min_delta not_verifiable 如实阻断"超过基线"宣称 |
| E2E（iris 协议验证） | 真实执行 + 委托签，claim scope"本地协议验证 · 不可外推到科学结论" | **协议/机制验证**（工程味），不是知识生产研究 | ✓ 转录明言"不能作为科学结论"；标签=闭环·待签 |
| 完整闭环（教学演示） | 演示数据（无真实签名） | **机制演示**，不是研究 | ✓ 标注"演示数据 · 代理指标" |
| 写作/命题示例 | 流程示例 | 非研究 | ✓ 标注"示例" |

结论：**系统承载的是研究治理（governance harness）；哪条会话算研究，由其主张的效度决定，而不是由我们的意愿决定**。这条边界我们已经用 scope/标签如实执行——152 的本质定义与这条自查互为印证。要产出真正的知识主张，需要让真实任务在系统里走完"人签 claim + closure"（G5 needs_human 的存在正是为此）。

## 3. Insight 落地：方法差异 → 对智能体设计的直接指导

纪要 insight：「厘清这些差异能直接指导智能体 Prompt 的设计与基线对比」。落点（方法详情卡新增**对智能体设计的含义**）：

1. **基线策略**（按证据类型推导，与 run contract 语义一致）：受控实验→配对基线+功效分析+预注册主比较；准实验→识别策略+敏感性分析；基准评测→污染检查+多重比较校正；仓库挖掘→**无配对基线读数——只报差值/相关与检验，不宣称超过基线**（E2E/ESE 实测口径）；SLR→证据地图不排名；案例→机制理解不报效应量；调查→自报分布不宣称行为因果；DSR→按评估策略；行动研究→情境性知识。
2. **Prompt 纪律**（从 cannot_support 逐字推导）：每方法的 agent Prompt 必须内置"不得宣称"清单——挖掘智能体的 Prompt 必须声明"标签启发式，因果机制/跨生态泛化/实时预测不可支持"；调查智能体不得宣称行为因果。**方法差异由此直接变成 Prompt 的负面约束与基线选择**，不再靠提示词工程师的直觉。

## 5. 设计主张（可证伪）

1. 研究任务的本质判定标准是**终产物的效度主张**：E2E 的"本地协议验证"scope 与 ESE 的"三仓库口径"是诚实执行该标准的实例——若未来某会话宣称知识效度而无判别证据，即违反本标准（可被脚本检查）；
2. 基线策略必须从证据类型推导而不能自由选择：ESE 的"无配对基线"是数据形态决定的，不是偏好——run contract 的 not_verifiable 是它的机器判例；
3. Prompt 的负面约束（不得宣称清单）直接取自 cannot_support，是"方法差异指导 Prompt 设计"的最小落地形式。
