# 研究内容 → 方法 → 编排：把"识别"做成可解释的推荐，而不是猜测

> 状态基线：2026-11-21。承接 162（组合计划）、164（pipeline advisory 层）、165（计划可变≠流程可变）、166/167（效力模型）。
> 目标：让智能体**识别不同的研究内容，给出不同的方法与阶段编排**；本文实现"识别 + 选择 + 计划"这一段，并明确执行层仍未完成。

---

## 0. 一句话结论

现在这条链是通的：**研究内容 → 命中注册表信号 → 候选方法排序 → 该方法的阶段计划**，全过程可解释、可复算，并且**信号不足时拒绝推荐**。

但必须说清：这只做到"选择与计划"，**没有做到"按计划执行"**。pipeline 仍会跑全部阶段块（165 的结论未变）。所以现在的准确表述是：

> 智能体能识别研究内容并编排**计划**，但执行器还没按计划跳过/重排阶段。

---

## 1. 实现的三段

### 1.1 识别：注册表里的选择信号（schema 0.7）

每个方法新增 `selection_signals`：6 条短语 + 权重 1..3。它们不是拍脑袋的关键词，而是方法本身的判别特征：

| 方法 | 信号示例 |
|---|---|
| SLR | 系统综述 / 文献综述 / PRISMA / 检索策略 / 纳入排除 / 研究空白 |
| 受控实验 | 随机 / 对照实验 / A-B / 因果 / 干预 / 实验组 |
| 准实验 | 准实验 / 无法随机 / 自然实验 / 政策 / 前后对比 / 选择偏倚 |
| 仓库挖掘 | 仓库 / commit / 提交历史 / 缺陷修复 / 版本历史 / 代码库 |
| 案例研究 | 案例研究 / 访谈 / 三角验证 / 现场 / 单个团队 |
| 调查 | 问卷 / 调查 / 量表 / 受访者 / 无应答 |
| DSR | 设计科学 / 原型 / 系统设计 / 构建 / 效用评估 |
| 行动研究 | 行动研究 / 组织变革 / 介入 / 循环 / 研究者参与 |
| ML 迭代 | 模型训练 / 消融 / 超参 / 深度学习 / 多种子 |
| 基准评估 | 基准 / 榜单 / SOTA / 评测集 / 污染 |

提示词的匹配是**数据**，所以 Python 与前端读同一份注册表，结果一致；改信号不需要改代码。

### 1.2 选择：三态输出，拒绝在弱信号上猜

`recommend_methods(brief)` 返回：

- `ok`：最高分 ≥ 3 且领先第二名 → 给出 `proposed`；
- `ambiguous`：前两名同分 → **不选**，返回并列候选；
- `insufficient`：无人命中或最高分 < 3 → **不选**，返回空候选。

`pipeline --method auto` 只在 `ok` 时采纳第一名，并且**始终写 `needs_human=true`**；`insufficient` / `ambiguous` 时不设置方法、不生成 composition plan，运行照常但记录"需要人来定"。

这不是保守，而是治理一致性：**方法选择是设计决策，不是分类任务**。自动选错方法的代价比不选高得多。

### 1.3 编排：计划由组合解析，不由代码写死

选中方法后，`pipeline_stage_plan` 把组合的 slot_map 投影为阶段集合，`stage_plan` 给出带顺序的槽位计划。实测：

- 仓库挖掘（探索式）：`S4 → S1 → S5 → S5b`
- 受控实验（验证式）：`S2–S3 → S4 → S5 → S5b → S8–S12`

同一份元模型，不同方法解析出不同顺序——这正是 162 的设计，现在由"识别内容"自动触发。

## 3. 为什么不是"让 LLM 直接选"

用 LLM 做分类可以更"聪明"，但在这个系统里会引入三个问题：

1. **不可复算**：同样的 brief 两次可能不同，违背"判定可重放"。
2. **不可解释**：说不出"为什么是案例研究"，就无法在 G1 让人确认。
3. **会掩盖信号不足**：模型倾向于给一个答案，而不是说"信息不够"。

所以这里选的是**可解释的规则排序 + 明确拒答**。规则可以由文献信号扩充，但每一步都能指出命中了什么。

代价也很清楚：**同义词、否定句、隐含语境会漏**（"不是随机分配" 会命中"随机"）。这正是它只能是 advisory、必须人确认的原因。

---

## 4. 与"最终目标"的距离

用户的目标是：智能体识别研究内容 → 选择不同方法 → 编排不同阶段 → **按不同流程执行**。

| 环节 | 状态 |
|---|---|
| 识别内容 | ✅ 信号排序 + 三态拒答 |
| 选择方法 | ✅ 可解释候选 + 人确认标记 |
| 生成计划 | ✅ 组合解析出顺序 |
| **按计划执行** | ❌ 仍跑全部阶段块（164 的 advisory 层只发事件） |

第四步需要的不是再加一个 if，而是 165 说的三件事：跳过阶段的证据替代形态、门依赖不随顺序漂移的证明、负结果可审计。这三件都要先写进 SPEC。

---

## 5. 边界与下一步

1. **信号是粗粒度的**：只做短语命中，没有否定/同义词处理。下一步可以给信号加 `negative` 与 `synonyms`，但仍保持规则可解释。
2. **推荐没有校准**：权重是人工给的，没有用真实 brief 评估过准确率。可做一个小评测集（20 条 brief × 金标方法），报告 top-1/top-3，而不是宣称"推荐准确"。
3. **选择结果没有进入产品前端**（只在方法模型页演示与 pipeline modules 里）；下一步可以把"新建任务"接到推荐，让用户确认后写入 method_id。
4. **执行层未动**：这是下一阶段的主线，且必须先改 SPEC。
