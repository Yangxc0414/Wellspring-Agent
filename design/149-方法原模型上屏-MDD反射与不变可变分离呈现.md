# 方法原模型上屏：MDD 反射与"不变/可变"分离的呈现形式

> 状态基线：2026-11-21。承接 148（ESE 按产物丰富）、135（方法对照）、ARCHITECTURE.md（不变内核）。
> 本文含一处 python 改动（workspace export 增 method-registry.json，只读投影）与前端新视图（`apps/web`）；方法注册表本体（`modules/method-registry/registry.json`）一个字未改。

## 0. 一句话结论

导师的三条设计要求——研究方法原模型驱动、共性与差异分离、架构图"变与不变"的呈现创新——在本仓库里**已经有一半的实现基底**：`modules/method-registry/registry.json` 就是一个数据形态的方法原模型（10 个治理槽位 × 9 种研究方法，每种声明 fit_stages / protocol_fields / artifacts / checks / cannot_support / 方法学文献）。缺的是**上屏与直通**。本轮：workspace export 把注册表原样导出为前端快照；设置新增「方法模型」视图（共性槽位 + 方法×槽位矩阵 + 方法详情卡）；会话路径显示该方法的方法 chip。

## 2. 本轮实现

1. **数据直通**（python，一处小改）：`workspace export` 新增 `method-registry.json`——用 `method_registry.load_registry()` 原样导出，前端消费与 CLI 相同的数据源；`tests/test_workspace.py` 同步（文件清单 + schema 断言 + 提交快照漂移检查）。
2. **设置 → 方法模型**：注册表边界声明（原文）→ 共性槽位（10 个，治理不变）→ 方法×槽位矩阵（9 行，fit 点亮）→ 方法详情卡（须冻结的协议字段 / 产物 / 检查 blocker 占比 / 不能支持 / 方法学依据）。数据缺失时给"运行 workspace export 重导"的诚实空态。
3. **会话路径方法 chip**：ESE 会话的 SESSION PATH 显示"方法 · 软件仓库挖掘"，指向设置的方法模型页；映射声明在 `SESSION_METHOD`（演示关联；runtime 任务应由任务元数据携带方法 id）。

## 4. 设计主张（可证伪）

1. 方法原模型应当是**数据**（registry.json），编排消费它——这正是 MDD 的落地形态；本轮把"前端与 CLI 同源消费"补齐（此前注册表只有 CLI 能查）；
2. "不变/可变"的呈现答案是**两层视图**：不变层用契约表（STAGE_MODULE_CONTRACTS）与槽位卡，可变层用 SESSION PATH（每会话 stage 标签派生）+ 方法矩阵（每方法 fit 声明）——静态架构图表达不了的动态编排，由这两层按需派生；
3. 会话↔方法的关联在演示期是声明式映射，runtime 接入后应升级为任务元数据字段（acceptance：任务投影携带 method_id，本映射退役）。

## 5. 边界与不做

- 不改注册表本体一个字（它是 method-registry 模块的契约源）；不动编排执行逻辑（方法 profile 驱动编排 = roadmap，验收：pipeline 按 SESSION_METHOD/profile 解析阶段活动而非硬编码——需后端 SPEC 先行）；
- 矩阵只呈现 fit 与协议字段，不呈现每方法每槽位的活动名（90 格手写有发明风险；等真实多方法会话积累后按 148 的"逐字有据"方式补）。
