# 元模型三层对齐审计：过程模型不等于元模型，三态决策不等于二态门禁

**状态基线（2026-11-22）**：承接 design/175（护栏/策略空间二分）。
本文用两段外部框架（模型驱动智能体设计；Research Process Metamodel）对照现有系统做**对齐审计**，
并把 §5 的最小一步**落地为代码**（`researchVerdict.ts` + 7 例测试 + ContextPanel advisory 投影）。
不改后端代码、不改数据、不改 SPEC、不改门禁。核心要回答老师那条最硬的界线：

> "元模型负责定义规则，过程模型负责定义方案，执行引擎负责真正执行。不能把三者混为一谈。"

我们的 `registry.json` 同时装着 elements / compositions / methods，且 pipeline 从同一份数据取计划——
**这算不算混为一谈？** 逐条核查后，结论是：**职责边界其实分开了，但表达形式没分开；
真正缺的不是"三层分离"，而是三态决策与动态重排**。

## 1. 三层对齐核查（逐条，带代码证据）

| 老师的层 | 我们的对应物 | 判定 |
|---|---|---|
| Research Method Metamodel（定义规则） | `registry.elements`（9 个：问题/假设/方案/证据/判定/图表/写作/闭包/经验，带 input_kinds/outputs/human）+ `method_registry.validate()` 的 fail-closed + 175 的 LOCKED_SCOPES/strategy guard | **✓ 有**，但 elements 只描述"端口契约"（consumes/produces），没有规范化为 UML/Ecore 元类与基数——是**轻量元模型** |
| Research Process Model（定义方案） | `registry.compositions`（2 种接线，每步带 `consumes` + `rationale`）+ `stagePlanFor(method, registry)` 的 stage 投影 | **✓ 有**，且 SPEM"方法内容与过程分离"已实现：composition 是过程模板，method 通过 `composition_id` 引用，10 方法共享 2 模板 |
| Process Instance（具体项目的过程） | 一次 `PipelineRequest` + `composition_plan` 写入 modules + 174 的 `stage_plan` 决定跑哪些阶段 | **✓ 有**（advisory 部分）；但实例状态机没有一等表达——174 只做"跑/不跑"，不做"按结果分支" |
| Agent Execution Runtime（执行） | `pipeline.py` 的 `run()` + `RunAgent/LiteratureAgent/...` + SSE events | **✓ 有**，但它是**线性函数**，不是图执行器——老师的"BPMN 式条件分支/事件触发/子流程"我们一个都没有 |
| 执行引擎 ≠ 元模型 | `registry.json` 是数据，`pipeline.py` 是代码，`validate()` 在加载时拒绝坏数据 | **✓ 分开了**——registry 不调度 agent；和老师"元模型不会自动调度 Agent"一致 |

**结论**：三层在**职责**上分开了（数据/校验/执行各司其职），没有"混为一谈"；
但在**表达形式**上压在一个 JSON 里，且缺一个显式的 Process Instance 状态机。这是可读性与可验证性的债，不是架构错。

## 2. 老师强调的三个"必须"，我们各缺什么

### 2.1 "三态决策"——我们只有二态门禁 + 一个 cannot_support 声明

老师说"不能把科研过程建模成只有成功/失败两种状态"，并给出：
`SUPPORTED / REFUTED / INCONCLUSIVE` → 分别触发"继续分析 / 修正理论 / 补充实验"。

核查我们的状态词表：

| 我们的状态 | 在哪 | 对应老师三态吗 |
|---|---|---|
| `GateStatus = pass / needs_human / pending / not_started / blocked` | `types.ts:26` | 这是**治理门**状态（谁签、走没走），不是**研究判断**状态 |
| `EvidenceSignal.state = positive / negative / undecidable / unavailable` | `types.ts:311` | ✓ 有四态，但只在前端证据信号类型里，**不驱动任何过程路由** |
| `method.cannot_support`（"不能支持什么"） | registry 10 方法全覆盖 | 是静态边界声明，不是运行时决策输出 |
| `study arm: undecidable / directional_supported` | `pipeline.py:932` | 有，但只写进 warning 文本，不改后续流程 |

**真实缺口（修正后的准确措辞）**：`StudyComparison.state` 的四态**不是死类型**——
`ContextPanel.tsx:1386` 已经消费 `undecidable` 并显示"区间跨零：没有方向，不算结果"，
还带 `seeds_for_80pct`（"约需 N 种子才可能判定"）——这已经是**下一步建议**的雏形。
缺的是：它只**显示在文本里**，没有一等对象把 `(state, seeds_for_80pct) → 下一步动作`
变成可路由、可测试的决策（advisory 也行）。即：**有四态、有建议文字，但没有决策函数**。

这是老师指出的最准的一刀：我们的过程是线性的，判断结果只进报告，不驱动过程。

### 2.2 "Evidence 一等 + PROV 溯源"——我们有 lineage，但不是 PROV

- 我们有 `research_agent/lineage.py`：产物节点 + 依赖边 + stale 传播（14 下游节点 stale 的实测），
  以及 `manuscript provenance`（数字回溯到 artifact）——**这是派生链，功能上覆盖 PROV 的 Derivation**。
- 但 `lineage.build()` 的 docstring 自己写着："It is not a semantic proof of the claim."——
   honest，但也说明它只做**结构依赖**，不做 `Entity/Activity/Agent/Association` 的 PROV 四元组。
- 老师要求 `Conclusion → supported_by → Evidence → generated_by → Experiment → executed_with → Code Version`
  这样的显式关系链。我们的 `ClaimRecord.evidence_refs` 只引用 EA id，
  EA 再引用 metrics sha——链条有，但不是一等建模、不查询化。

**判定**：功能上有 70%，形式上 0%（没有 PROV 词表）。这是"够用但不可宣称对齐 PROV"的状态——
论文里不能写"采用 PROV"，只能写"实现了派生溯源"。

### 2.3 "动态图 vs 固定 DAG"——174 只做了剪裁，没做重排

这个缺口 design/174 §5 已诚实记录：阶段"跑/不跑"按方法编排，**顺序仍按 pipeline 物理序**。
老师框架进一步要求：证据触发分支（REFUTED → 回到假设；INCONCLUSIVE → 补实验），
这是**循环 + 条件分支**，比"重排顺序"更难——它要求把 `run()` 拆成可重入的阶段节点。

## 3. 哪些我们已经做对了（不能自我贬低）

1. **SPEM 的方法内容/过程分离**：`composition`（过程模板）与 `method`（方法 profile）通过 `composition_id` 解耦，
   10 方法共享 2 模板——这正是老师说的"Task Definition 可复用"。
2. **元模型一致性校验**：`method_registry.validate()` fail-closed + 175 的 strategy guard，
   对应老师"Agentic Model Transformation 的 LLM 生成必须锚定元模型一致性"——我们已经在做"生成受元模型约束"。
3. **元模型先行**：design/156 起先建 elements/端口，再建 composition/wiring，再建 method——
   和老师的"元模型先行，再设计智能体"顺序一致。
4. **三态的治理层对应**：`GateStatus` 有 `blocked / needs_human / pass` 三态，
   174 又加 `not_applicable`——治理判断不是二态，这点我们比老师要求的更细。
5. **RSI 分层**：我们有 Agent-level（Harness2 组件面）、预算面（seeds/budget lease）、
   175 的策略空间（流程级可优化点）——老师的 Process-level RSI 我们**已经建好了建模对象**，只差接上反馈闭环。

## 5. 下一步收敛（按老师的优先级，不写新文档）

老师给的落地路线前两步我们已经走过（统一元模型 ✓、方法模板 ✓）。
真正没做的是第 3–5 步：**实例化状态机 / 证据分支 / Process-level RSI 闭环**。

最小可验证的一步（不碰 schema、不拆巨型函数）：

> 把 `StudyComparison.state`（positive/negative/undecidable/unavailable）从"只出文字"变成
> **过程决策的输入**：新增一个只读纯函数 `researchVerdict(comparison) → { action, reason }`，
> 输出 `continue_analysis | revise_hypothesis | add_evidence | needs_human` 四选一，
> 对应老师的 SUPPORTED / REFUTED / INCONCLUSIVE 三态 + 治理例外。
> 先在 RESEARCH FLOW 的"判定"节点上把分支建议显示出来（advisory），
> 不改执行器、不改门禁。只有这条建议被历史会话验证一致，才考虑接进 pipeline。

**本轮已落地这一步**：`apps/web/src/domain/researchVerdict.ts` 实现 `researchVerdict` 与
`overallVerdict` 两个纯函数（三态 + 治理例外 → 四条 advisory 分支），
`tests/researchVerdict.test.ts` 7 例钉住「undecidable 不算支持、反驳不被正向结果掩盖、
纯函数不改输入」；`ContextPanel` 在比较列表下显示「过程分支建议（advisory · 不改门禁）」
并按 SUPPORTED/REFUTED/INCONCLUSIVE 着色。web test:unit 82/82。

这与项目一贯的纪律一致：**先 advisory 投影 → 验证一致 → 再驱动执行**（164→174 走过的路）。
仍未做：把 advisory 分支接进 pipeline 的条件路由（需拆 `run()` 为可重入阶段节点）。
